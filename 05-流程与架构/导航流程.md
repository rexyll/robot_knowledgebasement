# 导航流程（运行期）

> "从 A 到 B"在机器人内部发生的全部事情。上游 [[建图流程]]（地图），算法细节见 [[多传感器融合定位]] / [[路径规划算法]] / [[局部规划与避障]]，本页串流程。

## 一次导航任务的完整时序

```
0. 任务下发: 调度器/App → 目标点位 (MQTT cmd → 车端FSM) → [[多机调度流程]]
1. 任务校验: 点位存在? 车状态OK(非充电中/非故障)? 电量够? 路径区域开放?
2. 启动定位: 确认 map 定位有效(重定位成功/连续性检查) → [[多传感器融合定位]]
   └─ 失败分支: 盲区? → 触发重定位行为(原地旋转扫描/回已知点位)
3. 全局规划: 起点→终点 A*/Hybrid-A* → Path → [[路径规划算法]]
   └─ 失败分支: 无解 → 上报调度器(区域封锁? 改道?)
4. 路径跟随: 局部控制器(RPP/DWA/TEB/MPPI) 沿路径输出 Twist @20Hz → [[局部规划与避障]]
   ├─ 动态障碍: 减速/绕行/等待 → [[视觉感知算法]]
   ├─ 偏航检测: 离全局路径 >50cm → 触发局部重规划
   └─ 周期重规划: 每 5-30s 或事件触发
5. 到点判定: xy 误差 <tolerance(±5-10cm) + 角度 <±10° + 速度 <0.05m/s 持续 0.5s
6. 停靠精对齐(可选): 对接任务 → 慢速 0.05m/s + 地标(AprilTag/反光板)微调 ±5mm
   → [[充电桩与自动充电]] · 货架对接
7. 动作执行: 到位信号 → 业务动作(顶升/货叉/开门/播音) → FSM 状态推进
8. 上报完成: 车端FSM → 云端(事件流) → 调度器派下一任务
9. 异常路径: 超时/卡死/定位丢失/急停 → 恢复行为(旋转清除/后退/重规划×N)
   → 仍失败 → 故障上报 → 远程接管/人工介入 → [[功能安全体系]]
```

## TF 坐标树（导航的坐标系纪律）

```
map ──(定位层发布, 可跳变)── odom ──(航位推算, 连续)── base_link ── 传感器/轮子
- 控制器只在 odom 帧算(连续平滑), 定位只在 map↔odom 修正
- 时间戳纪律: 全链 sim_time/真实时钟统一, TF 插值容差 ~100ms → [[ROS与ROS2]]
```

## 速度分级策略（安全与效率平衡）

| 场景 | 速度 | 触发 |
|---|---|---|
| 直道空旷 | 100%（1.5-2 m/s） | 前方净空 >5m |
| 转弯 | 30-50% | 曲率/朝向变化 |
| 人流区/窄道 | 30% | 限速区/检测到人 3m 内 |
| 对接近距 | 5-10% | 距目标 <0.5m |
| 保护区入侵 | 0（停车） | 安全扫描仪保护区 → [[安全防护器件]] |

## 导航性能指标（→ [[性能指标体系]]）

| 指标 | 典型目标 |
|---|---|
| 到位精度 | ±5-10cm（对接 ±5mm） |
| 到位时间 | 50m 距离 ≤45s（含加减速） |
| 任务成功率 | >99.5%（含恢复行为后） |
| 平均速度利用率 | 实际/理论 ≥70%（频繁避障说明调度问题） |
| 重规划频率 | 稳态 <0.1Hz（过高=感知抖动或参数不当） |

## 细节加深（V2）
- **BT 行为树调试法**：Nav2 导航异常先看 BT 黑盒（Groot2 可视化）而不是翻代码——「哪棵子树失败」比「哪个节点报错」快 10 倍定位。
- **速度分级表要写进验收**：转弯 30-50%/人流 30%/对接 5-10% 的降速策略是客户可感知项，验收时逐条演示。

## TF 坐标变换专节（V3 · 附件整合）

> 来源：用户附件 PDF（Google Search 会话，2026-11-01 导出）。TF（Transform）= ROS/ROS2 的**坐标系变换系统**，管理机器人各部件与环境间的空间位姿关系（"你在哪、我在哪、隔多远、转多少度"）。

**为什么必须有 TF**：雷达说"墙在我前方 1 米"（雷达坐标系）；底盘要导航，得知道墙离**底盘中心**多远——雷达装在车头前 0.2m、高 0.5m，则墙距底盘中心实为 1.2m；再进一步画到全局地图还需底盘在 map 中的位姿。若每个算法自己减偏移，代码必乱——TF 自动完成这些换算。

**TF 树纪律**：每个坐标系（Frame）有唯一 frame_id，每个子坐标系只有一个父——任意两系间有唯一变换路径。典型树：

```
map → odom → base_link → laser_frame / imu_link / camera_link
```

**两种广播器（关键角色分工）**：
- **静态广播器（Static Transform Broadcaster）**：发布**永不改变**的安装关系（雷达/IMU/相机装在底盘哪个螺丝孔位）——出厂装配即固定，来自 [[09-04-传感器选型与标定]] 的外参。
- **动态广播器（Transform Broadcaster）**：发布随时间变化的关系——里程计节点持续发 `odom→base_link`（车在动），定位节点（AMCL）持续发 `map→odom`（修正累积误差）。

**开发者只做两件事**：① 监听（Listen）——向 TF 树查询"时间戳 X 时 laser_frame 下这点在 map 系坐标多少"；② 转换（Transform）——用 TF 库 API 把整个 LaserScan/Point 一键投影到目标系。

**版本演进**：ROS1 早期叫 `tf`，因性能与设计缺陷演进为 `tf2`；ROS2 全盘采用 **tf2 库**且底层借 DDS 通信，多机协同/时间同步/缓存性能更优（→ [[ROS1与迁移]] · [[DDS专题]]）。

**排障入口**：`ros2 run tf2_ros tf2_echo map base_link`、`ros2 run tf2_tools view_frames`（生成 TF 树 PDF）；超时报 Extrapolation 先查时间戳与时钟源（→ [[09-09-网络通讯设计]]）。
