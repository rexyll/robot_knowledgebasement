# 机器人系统故障诊断与闭环处理：从症状到根因、验证和预防

> 本文面向零基础学习者和机器人项目工程团队，介绍通用故障诊断方法。它不是设备维修授权、带电检修规程或功能安全程序。遇到电池、高压母线、伺服驱动器、机械储能、悬挂负载、激光/光学危险源或安全回路异常时，必须先停止设备并按照制造商手册、现场能源隔离程序和组织授权流程处理。不得绕过急停、门锁、限位或安全控制来“验证故障”。

## 1. 学完后应该能做什么

完成本文后，你应能够：

1. 区分现象、报警、故障模式、失效机理、根因和影响。
2. 在不破坏现场和不制造新危险的前提下，记录可复现的故障证据。
3. 按电源、机械、电气、传感器、嵌入式、网络、软件、算法、制造和现场条件分层隔离故障。
4. 通过假设、试验和反证，而不是“换件碰运气”，逐步缩小原因范围。
5. 用统一记录将问题连接到设计版本、BOM 批次、测试用例、客户现场和 CAPA。
6. 判断何时应停止排查并升级给安全负责人、设备制造商、专业维修人员或实验室。

## 2. 先理解六个词

| 词 | 含义 | 示例 |
|---|---|---|
| 症状（Symptom） | 人或系统直接观察到的表现 | 机器人突然停在走廊中间 |
| 报警（Alarm） | 设备或软件报告的状态/阈值异常 | 电机驱动器报告过温 |
| 故障模式（Failure Mode） | 某个功能以什么方式失效 | 左轮驱动器停止输出扭矩 |
| 失效机理（Failure Mechanism） | 导致故障模式的物理/电气/软件过程 | 连接器接触电阻增大造成局部发热 |
| 根因（Root Cause） | 有证据支持、解释故障发生及为何未被预防/发现的原因 | 线束压接工艺窗口未受控，抽检方法无法发现间歇性高阻 |
| 影响（Effect） | 故障对系统、人员、产品和客户造成的后果 | 机器人停机、任务中断、批次产品存在相同风险 |

**重要区别：** 报警码通常是症状线索，不一定等于根因；“重启后恢复”是一次恢复现象，不等于根因已消除；更换一个部件后正常，也不能单独证明该部件就是根因。

## 3. 故障处理的标准流程

### 3.1 先控制风险，再诊断

1. 识别人员、设备、工件、环境和客户现场风险。
2. 按设备规程进入安全停止状态；必要时隔离能源、限制区域和挂牌。
3. 记录急停、安全门、保护装置和安全控制器状态，禁止短接、屏蔽或改变安全参数。
4. 由有授权的人员判断是否允许恢复、低速调试、台架测试或拆检。
5. 对可能涉及批量或安全风险的问题，隔离相同批次、型号或软件版本，启动升级通报流程。

排查效率不能优先于人员安全和证据保全。设备已造成伤害、险情、冒烟、异味、异常温升、绝缘损坏或电池变形时，停止自行试验并升级处理。

### 3.2 固化配置与现场证据

诊断前先记录“这台机器人当时是什么状态”，否则复现结果可能无法比较。

| 类别 | 必须尽量记录的字段 |
|---|---|
| 设备身份 | 产品型号、序列号、硬件版本、生产日期、BOM/关键物料批次 |
| 软件配置 | OS/内核、ROS 发行版、软件 commit、容器镜像、固件版本、配置参数、地图/模型版本 |
| 运行工况 | 时间与时区、环境温度、地面/坡度、载荷、速度、任务、运行时长、电池 SOC/温度 |
| 外部条件 | 网络拓扑/信号、光照、灰尘/水汽、地面反光、工件变化、操作流程 |
| 现象 | 首次发生时间、频率、持续时间、发生步骤、报警原文、指示灯、声音/温升等 |
| 证据 | 原始日志、事件时间线、rosbag、照片/视频、测试数据、拆检结果、测量仪器与校准状态 |
| 处置 | 谁在何时做了什么、改变了哪些参数/部件、是否重启、结果如何 |

记录原始文件及其校验值，保留采集时间、来源和访问权限。不要在客户数据、人员图像、定位轨迹或网络凭证未脱敏的情况下把完整日志上传到公开仓库。

### 3.3 建立故障描述，不写猜测

建议采用一句话格式：

> 在 **配置 C**、**工况 E** 下，执行 **步骤 A** 后，设备在 **时间/条件 T** 出现 **可测量症状 S**；重复 **N 次**，其中 **K 次**发生；当前安全状态为 **状态 R**。

反例：“导航算法不稳定”“电机坏了”“ROS 有问题”。

较好的描述：“配置 FW-1.4.2 / ROS 2 Jazzy，在载荷 35 kg、速度设定 0.6 m/s、同一路段连续运行 20 分钟后，左轮编码器反馈出现间歇性跳变；10 次运行中 3 次发生；设备已停止并保留故障前后日志。”

这里的数字只是示例写法，不是任何机器人产品的通用阈值。

## 4. 分层诊断：从外到内、从低风险到高风险

| 层级 | 典型观察 | 优先检查（只做有授权、低风险检查） | 常见误判 |
|---|---|---|---|
| 现场与任务 | 只在某个工位/路线/班次发生 | 地面、光照、网络覆盖、工件、任务参数、操作步骤 | 把环境变化一律归因算法 |
| 能源与供电 | 重启、掉电、欠压、随机复位 | 电量/温度记录、供电事件、连接器外观和制造商允许的测量记录 | 只看电池电量百分比 |
| 机械与传动 | 异响、卡滞、偏移、振动、间隙变化 | 载荷、固定件、轮胎/轴承/联轴器/减速器、润滑与装配记录 | 一出现噪声就调软件滤波 |
| 电气与执行器 | 过流、过温、无响应、抖动 | 驱动器诊断、限流/限压状态、接线图和授权检验记录 | 在未知状态下反复使能电机 |
| 传感器与标定 | 数据丢失、跳变、偏置、漂移 | 时间戳、频率、单位、坐标系、污染/遮挡、标定版本 | 直接改滤波参数掩盖坏数据 |
| 嵌入式与计算 | 启动失败、CPU/GPU/内存异常、看门狗复位 | 系统日志、温度/降频、资源、固件版本、启动链 | 把偶发复位当作“偶然” |
| 网络与时间同步 | 多机断连、延迟、乱序、时间不一致 | 链路状态、丢包/延迟、QoS、时钟源、子网和防火墙 | 只重启交换机或切换 QoS |
| 软件与中间件 | 节点崩溃、服务超时、生命周期错误 | 节点状态、异常栈、topic/service/action、参数与版本差异 | 只检查进程是否存在 |
| 算法与模型 | 定位漂移、误检、规划失败、任务失败 | 输入数据质量、模型假设、边界工况、置信度、可复现数据集 | 只调参不验证数据分布 |
| 制造与供应链 | 同批次、同工位、同供应商聚集 | 序列号/BOM/批次/供应商/工艺参数/检验数据 | 只修现场单台机器 |
| 云端与调度 | 任务分配错误、远程不可用、地图配置不一致 | 服务健康、接口契约、版本兼容、数据权限、网络和回滚 | 将云端故障归咎机器人本体 |

**排查顺序不是固定的故障树。** 应结合风险、系统架构、失效影响和已有证据决定；安全相关故障优先升级，不按此表让初学者自行拆机。

## 5. 证据驱动的根因分析方法

### 5.1 先做时间线

将关键事件统一到可比较的时间基准：

- T-60 s：系统处于何种工况；
- T-5 s：首个异常信号；
- T0：症状出现；
- T+1 s：报警/保护动作；
- T+10 s：操作员执行的处置；
- T+30 s：设备恢复或进入锁定状态。

不同设备时钟未同步时，先标注时间偏差和时间来源；不能把相差数百毫秒的多机日志当作严格先后因果。

### 5.2 建立假设表

每个假设要写出支持证据、反对证据、区分性试验和风险。

| 假设 ID | 可能原因 | 支持证据 | 反证/未知 | 区分性试验 | 风险与批准人 |
|---|---|---|---|---|---|
| H1 | 传感器供电间歇中断 | 同时出现设备重连日志 | 供电记录尚未证实 | 台架记录电压与设备状态关联 | 由授权电气人员制定 |
| H2 | 网络丢包导致数据超时 | 异常发生时 topic 频率下降 | 本地记录未证实掉包 | 在隔离网络中记录链路和消息时间戳 | 网络变更需批准 |
| H3 | 上游数据时间戳错误 | 多源数据时间差异常 | 设备时钟精度未知 | 对比硬件时间戳与统一时钟记录 | 不改变安全控制参数 |

一次试验尽量只改变一个变量，同时保持其他条件和测量方法一致。若同时换传感器、重装系统、改参数、换线缆，就算问题暂时消失，也无法知道哪个改变起了作用。

### 5.3 用多种方法而不是单一工具

- **5 Why：** 逐层追问为什么发生，直到找到可采取措施且有证据支持的系统原因；不能为了凑“五层”制造故事。
- **鱼骨图（因果图）：** 从人员、设备、材料、方法、测量、环境等维度系统列出候选因素。
- **故障树分析（FTA）：** 从顶层不期望事件向下分解逻辑组合，帮助理解多因素触发路径。
- **FMEA：** 事前识别潜在失效模式及其影响，用于优先安排预防和检测措施；不是已经发生故障的根因证明。
- **8D / CAPA：** 组织团队、围堵、根因和逃逸原因分析、纠正预防措施、效果验证和标准化的闭环框架。
- **FRACAS：** Failure Reporting, Analysis and Corrective Action System，用于持续记录失效、分析、纠正措施和状态，便于跨批次/跨现场识别重复问题。

## 6. 机器人数据诊断：以 ROS 2 为例

ROS 2 生态提供 diagnostics 相关包。官方 ROS diagnostics 项目说明：诊断信息通过 `/diagnostics` topic 传输，消息类型为 `diagnostic_msgs/DiagnosticArray`；`diagnostic_updater` 可用于发布传感器、硬件驱动状态和超范围数据，聚合组件可汇总各来源状态（链接台账 #172–#174）。

可以从只读观察开始：

```bash
# 查看节点与话题是否存在
ros2 node list
ros2 topic list

# 查看某话题发布频率（把 /scan 换成目标话题）
ros2 topic hz /scan

# 观察诊断状态（需要系统已发布 /diagnostics）
ros2 topic echo /diagnostics

# 采集诊断话题到 rosbag；需先确认存储和隐私策略
ros2 bag record /diagnostics
```

注意：

1. 诊断 topic 不存在可能表示未实现、未启动、命名空间不同或 QoS 不匹配，不自动说明硬件坏了。
2. 有 `OK/WARN/ERROR` 状态不代表该监控覆盖了所有危险失效；普通 ROS diagnostics 不是安全认证或安全控制器。
3. 数据时间戳、单位、频率、设备身份、故障码定义必须由驱动和系统设计者明确。
4. 所有 CLI 命令应在只读、授权的环境中执行；不要在故障现场贸然发运动命令或修改控制参数。
5. ROS 发行版和 package API 有版本差异，使用时要查选定发行版的官方文档并锁定包版本。

## 7. 从开发台架到客户现场的不同处理边界

| 阶段 | 主要目标 | 重点证据 | 关闭方式 |
|---|---|---|---|
| 开发调试 | 快速隔离设计/实现缺陷 | 代码版本、调试日志、仿真/台架复现 | 缺陷修复、单元/集成/回归测试 |
| EVT/DVT | 证明设计满足需求并覆盖失效场景 | DVP&R、极限工况、故障注入、失效分析 | 设计更改、重新验证、残余风险评审 |
| PVT/试产 | 识别制造/供应链问题 | 批次/序列号、工序、设备、物料、检验数据 | 工艺修订、PFMEA/Control Plan 更新、复测 |
| 量产 | 识别共性、批次和趋势性异常 | FRACAS、SPC、良率、供应商和退货数据 | 围堵、CAPA、必要时停线/召回评估 |
| 客户部署/售后 | 恢复客户服务并防止复发 | 现场配置、任务日志、网络/地图/工况、维修记录 | 客户确认、版本回归、服务知识库、批次影响分析 |

**单台恢复不等于产品问题关闭。** 对于可能影响同一批次或软件版本的失效，必须判断受影响范围，追踪在制品、库存、已交付设备和供应商来料，并由有权限角色决定停发、隔离、现场措施或客户通知。

## 8. 故障等级与升级原则

| 级别 | 示例定义（由组织按产品风险裁剪） | 处理方式 |
|---|---|---|
| S0 安全/法规/重大事件 | 伤害、险情、保护功能失效、冒烟/起火、电池热事件、可能违法/不符合认证条件 | 立即停止/隔离，启动安全和管理层流程；专业调查，不让初学者复现 |
| S1 关键功能中断 | 关键任务不可完成、系统无法安全恢复、同批次可能存在共性失效 | 限制使用，及时升级，围堵和根因分析 |
| S2 一般功能降级 | 非关键功能可用替代方式完成，存在受控临时方案 | 登记问题、设责任人和期限，修复后回归 |
| S3 轻微/体验问题 | 不影响安全和核心功能的显示、提示或非关键体验缺陷 | 进入版本计划并保留追踪 |

级别仅为示例，组织须依据风险评估、合同、法规和安全事件程序建立正式分级。任何人发现潜在安全隐患都有权按现场制度停止工作并报告。

## 9. 纠正措施与有效性验证

好的纠正措施不仅针对“坏掉的零件”，还要针对造成问题以及问题未能被提前发现的系统原因。

| 层次 | 问题 | 措施例子 |
|---|---|---|
| 纠正（Correction） | 当前设备出现故障 | 经授权更换失效部件，恢复设备状态 |
| 纠正措施（Corrective Action） | 为什么这个原因导致了失效 | 修订压接工艺、工具校验与关键参数监控 |
| 预防/系统性措施 | 为什么其他产品也可能发生 | 更新供应商控制、PFMEA、Control Plan、培训和进料检验 |
| 有效性验证 | 如何证明措施真有效 | 定义样本范围、暴露工况、观察周期、复发阈值与独立审核 |

只有当措施按预先定义的判据完成验证、相关批次/现场影响已评估、文件和培训已更新、重复发生的风险已得到评审，问题才可以按组织流程关闭。不要用“已发新版软件”“已培训”“已换件”直接代替效果证据。

## 10. 一个假设性案例：机器人运行一段时间后偶发停机

> 以下是教学构造案例，不是真实项目数据。

**现象：** 同一台移动机器人连续工作一段时间后偶发停机；重启后短时间恢复。

初始猜测有：电池欠压、驱动器过温、网络超时、传感器节点崩溃、急停链状态变化。不要一开始就修改导航参数。

诊断步骤：

1. 围堵：停止继续执行客户任务，记录设备序列号和现场配置，确认保护链状态；不旁路任何安全功能。
2. 时间线：对齐主控日志、驱动器日志、电池 BMS 记录、网络监控与任务记录。
3. 分层：确认是系统级断电、应用停机、任务取消还是安全控制触发；这几种状态的证据和处理方式不同。
4. 假设比较：若主控仍运行而驱动器报告过温，优先检查热路径和负载；若所有节点同时失联则检查供电和主控重启；若仅单一 topic 频率归零则调查驱动与网络。
5. 区分性试验：在批准的台架/受控环境复现，保持硬件、软件和任务负载一致，一次改变一个变量并记录原始数据。
6. 根因验证：用测量、拆检、日志和可重复试验证明根因；不能只根据报警时间相近就认定因果。
7. 纠正预防：修复后进行回归、耐久/边界条件验证，分析同批次/同配置是否受影响，更新知识卡和生产/售后检查项。

案例没有给出具体根因，因为没有真实证据时，不能替读者编造结论。

## 11. 初学者练习与检查

### 练习 A：报警码是不是根因？

某驱动器报告过温。你能否直接把“驱动器坏了”写进根因栏？

**检查答案：** 不能。过温是状态/报警。需要核对负载、环境温度、散热、安装、风扇/散热器状态、参数、温度测量和驱动器自身故障记录，之后才能形成经验证的根因结论。

### 练习 B：重启恢复说明什么？

机器人重启后恢复运行，是否可以关闭故障单？

**检查答案：** 不能。重启是处置动作，可能清除现场状态。需要保留重启前日志、记录恢复条件、排查状态丢失原因，并确定回归/监控和影响范围。

### 练习 C：同时换部件和软件后故障消失

是否已证明软件或某个部件是根因？

**检查答案：** 没有。多个变量同时改变，无法区分因果。需要按风险和可复现条件设计单变量试验，或使用能够区分各假设的受控试验。

### 练习 D：只有一台机器发生

是否可以排除批次质量问题？

**检查答案：** 不可以。检查相同 BOM/供应商批次、工艺、版本和环境暴露；样本不足时要记录不确定性并制定监控或抽查策略。

## 12. 可复用故障记录应包含什么

使用 [故障诊断与 FRACAS 记录模板](../../docs/templates/verification/fault-diagnostic-and-fracas-record.md) 建立统一记录，至少包括：

- 唯一故障 ID、设备/客户/产品版本与严重度；
- 发生时间、现场工况、复现步骤和安全状态；
- 原始日志、测试数据、时间同步偏差、附件哈希；
- 候选假设、排除证据、区分性试验和批准人；
- 根因与“逃逸原因”（为何预防/检测机制没有挡住）；
- 围堵、纠正、预防、回归与有效性证据；
- 序列号/BOM/批次/软件版本影响范围和客户通知；
- 关闭批准、经验教训和知识库更新链接。
