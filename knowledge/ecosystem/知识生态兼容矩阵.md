### 2.1 选发行版前先确认的五个边界

1. **Ubuntu/CPU 架构等级：** ROS 发行版的 Tier 1/2/3 平台说明的是 ROS 基础层支持，不代表传感器、GPU、厂商 BSP、实时内核和载板已同时支持。
2. **Gazebo 配对：** 优先采用官方推荐组合；跨版本配对必须记录额外补丁、构建方法和回归测试。
3. **ROS Index 与上游 release：** 同一包的上游 GitHub tag、ROS Index 分发行版二进制版本、操作系统 apt 包可能不同步。
4. **源代码和预编译包：** “有 README 构建指令”不等于有该发行版的官方二进制包；“ROS Index 已发布”也不等于传感器固件和 SDK 兼容。
5. **供应商支持期限：** ROS LTS 生命周期不能替代相机/雷达固件、SDK、GPU 驱动或控制器厂商的产品生命周期承诺。

#### 5.7.1 PLC—ROS 2 接口工程准入清单

厂商能力表只说明“存在某种通信能力”，不能替代项目接口设计。进入详细设计前，至少冻结以下内容：

1. **身份与配置**：PLC CPU/订货号/固件/runtime/license、ROS distro/OS/内核/CPU、驱动 tag/commit、协议版本、网络拓扑、端口与 ACL。
2. **协议安全**：ADS 双方 AMS Net ID/route；OPC UA endpoint、SecurityPolicy、证书信任和用户认证；S7/Modbus 访问保护与读写权限。测试用匿名/None security 不得直接进入生产。
3. **数据契约**：逐点登记 PLC symbol/NodeId/寄存器、方向、类型/宽度、单位/缩放/字节序、ROS interface、采样周期、质量位、时间戳、范围与权限。
4. **命令语义**：前置条件、确认/完成状态、序列号、幂等性、取消、超时、重试、PLC 重启后残留命令清理；“写入成功”不等于“动作完成”。
5. **时序预算**：测量 PLC scan、ROS read/write 周期、端到端 P50/P95/P99/max 延迟、抖动、批量轮询负载、丢包、超时和恢复时间；不可从协议标称带宽推断硬实时。
6. **失效与安全**：网络分区、PLC/ROS 重启、证书失效、坏质量数据、重复/乱序命令、超范围值和过载均须故障注入；急停、STO、人员保护和安全联锁由独立安全设计负责。
7. **证据闭环**：保存配置导出、PLC trace、抓包、ROS bag、测试日志与签署记录，区分 SIL、HIL/FAT、SAT 和安全验证结论。

可复用的逐字段映射表、命令状态机、性能预算和故障测试记录见 [PLC—ROS 2 ICD 模板](../../docs/templates/PLC-ROS2-ICD.md)。本仓库当前只有静态资料审查，目标 PLC 的互操作、周期性能和现场安全验证均未完成。

### 6.1 三个常见的版本“假兼容”

- **ROS 发行版兼容 ≠ SDK/固件兼容：** realsense-ros 的 ROS 分支可构建，不代表任意 librealsense SDK、D400 固件和相机 SKU 都可互换。
- **源码可以编译 ≠ 官方推荐/生产就绪：** Livox Driver 2 有 Jazzy 构建命令，但上游明确不建议将当前代码直接用于量产；ROS 2 CANopen 也明确仍在开发中。
- **仿真器配对兼容 ≠ Sim2Real 通过：** Gazebo 推荐配对只确认软件发行版集成关系；传感器噪声、时钟、动力学、摩擦、接触、执行器延迟和故障模式仍需实机标定与验证。

## 7. 产品级兼容验收门

新设备或软件栈变更进入产品基线前，至少归档：

1. **精确版本锁：** Ubuntu/内核、ROS distro、Gazebo、RMW/DDS、驱动 tag/commit、厂商 SDK、设备固件、GPU/CUDA/TensorRT、载板 BSP、容器 digest 与依赖锁文件。
2. **构建与包来源：** 区分 apt 二进制、ROS Index、厂商 deb、源码构建、内部 fork；记录仓库地址、commit SHA、构建器、编译选项和许可证。
3. **设备互操作：** 实测枚举/连接、时间同步、TF/frame_id、QoS、丢包、数据完整性、温度/供电、设备重连、断电恢复、热插拔和并发资源。
4. **系统集成：** 验证 sensor → driver → preprocessing → localization/perception → planner/controller → hardware interface 的数据契约、频率、延迟、超时、降级和故障传播。
5. **运行验证：** 目标硬件长时间运行、CPU/GPU/内存/温度、最大负载、网络拥塞、进程重启、资源耗尽和异常数据注入；性能统计应留原始数据。
6. **安全与法规：** 开源软件通过构建或测试不等于具备功能安全等级；保护停机、制动、人员检测、急停和网络安全必须走产品风险评估与适用标准验证。
7. **PLC 协议桥专项：** 建立 PLC tag/寄存器/OPC UA NodeId 到 ROS interface/topic/service 的双向映射表；验证读写权限、数据类型/缩放/字节序、质量位/时间戳、轮询负载、超时与断线重连、重复命令/幂等性、PLC 重启和网络分区后的安全状态；保留抓包、PLC trace、ROS bag 与故障注入记录。任何安全功能不得依赖普通 OPC UA/Modbus/ROS 通道作为唯一保护路径。

**本轮测试状态：** 仅完成官方文档/仓库/ROS Index 静态兼容信息汇总。未在实际 SO-101 控制板、相机、雷达、底盘、飞控或目标量产计算平台上完成上述兼容验收。

## 8. 更新维护规则

- 每次 ROS distro 新发布、EOL 前 6 个月、驱动主分支迁移、相机 SDK/固件重大版本、Gazebo LTS 切换、GPU BSP 变化或关键依赖漏洞披露时触发复核。
- 每条矩阵状态保留来源 URL、核验日期、版本/tag/commit 和状态变化；不能静默覆盖过去状态。

**ICube ROS 2序号流增量风险：** C++ subscriber的16位回绕丢包公式对65535→0正常回绕多计1包；任意较小序号会被当作回绕并接受，重复帧虽标记new_message=false，RobotDriver读取路径仍不拒绝且接收时间戳刷新。乱序/重复可能回退序号基准或削弱staleness新鲜度判断；未运行故障注入。详见专项报告§9.3.2、来源#1496–#1500。

**VAL3状态帧协议一致性风险：** initRobotStateMsg将RobotState payload设为124字节，但encodeHeader最后2字节写的是nMsgSequenceNumber而非nPayloadSize；当前ICube C++ RobotState解析器未校验该字段，可能掩盖错误。需做VAL3→C++与C++→VAL3黄金帧互操作测试。静态证据尚未通过实机抓包验证。详见专项报告§9.3.3、来源#1501–#1506及#1486。
**VAL3命令帧payload_size校验风险：** decodeRobotCommandMsg在decodeHeader前使用对象中上一次保留的nPayloadSize做数据长度检查；decodeHeader读取当前头字段后会清除既有错误标志，命令解析路径没有再检查当前payload_size是否等于47。55字节的实际UDP帧即使声明错误payload_size也可能按固定字段解析；实际短/长UDP数据报由readDataOnce另行拒绝。详见专项报告§9.3.4、来源#1505、#1507–#1510。

**诊断重复帧与staleness处理（条件性静态风险）：** RobotDriver::read_diagnostic_data不检查status.new_message；RealTimeSocketSubscriber对重复序号只标记new_message=false但仍返回true，且每个成功解析的数据报刷新接收时间戳。重复/重放诊断包可能让旧数据被持续报告成功并刷新staleness。当前随附VAL3 app未提供诊断发送端，故此为外部诊断发送端接通后的接收路径风险，未进行网络注入。详见专项报告§9.3.7、来源#1525–#1527。
**诊断数据发布端缺失（高优先级集成缺口）：** 固定ICube VAL3 userapp中sio.cfx虽定义diagnostics UDP endpoint（11001），但ros2_server.dtx只绑定control socket，ros2_server.pjx没有DiagnosticData类型/编码程序，start.pgx把supervision/diagnostics task留作TODO，controlTask.pgx只发RobotState。C++ mock和test_driver自行合成诊断数据，故不能证明真实VAL3发送端存在。RobotDriver::connect()又将diag readiness硬编码true，未等待首个诊断报文。结论限于所审查仓库快照，不排除用户另加VAL3任务。详见专项报告§9.3.6、来源#1516–#1524。

**诊断报文Header校验缺口（静态发现）：** `DiagnosticDataMessage::deserialize()`先以对象构造默认值（type=DIAGNOSTIC_DATA、payload_size=66）做校验，再读取当前Header，读取后未检查当前payload_size。subscriber每包新建消息对象，因此不是常规路径复用上一包Header；`read_diagnostic_data()`另检查type/staleness但不检查payload_size，connect()目前仍未调用诊断读取。小于74字节的包会被最小长度检查拒绝。尚未确认真实CS9诊断发送链路或运行测试。详见Stäubli专项报告§9.3.5、来源#1511–#1515。

**控制器软件边界：** Stäubli官方CS9另有VAL 3、uniVAL plc和uniVAL drive路线。uniVAL plc是PLC功能块client—机器人server现场总线架构；uniVAL drive是外部多轴控制器/drive profile路线。它们不应与ROS 2 HardwareInterface混写成同一驱动或同一运动控制权威。uniVAL drive页面的Cat.3/PL d为厂商公开声明，证书/适用SKU/集成条件仍待核验。

**验收边界：** GitHub Release、CI工作流、mock测试、真实控制器连接和安全/实时验证属于不同证据层。本轮只进行公开资料和源码静态审查；未构建目标工作区、未运行上游单元测试、未连接CS9/机器人/PLC、未测周期/抖动/WCET/轨迹误差，也未执行网络故障注入、HIL/FAT/SAT/功能安全验证。


**跨语言协议布局与端序基线（2026-11-07）：** C++要求little-endian目标；宿主double字段在线上统一转换为float32。VAL3使用2l/4.0l小端编码。RobotState为132字节（payload 124）、RobotCommand为55字节（payload 47）、DiagnosticData为74字节（payload 66）；DiagnosticData wire顺序是10个error_code后接10个timestamp，不是结构体逐条交错。状态Header重复写sequence的已知缺陷仍存在；随附VAL3应用没有诊断发送器，因此DiagnosticData仅有C++侧参考向量，未有VAL3互操作证据。F/T尾部和DI/AIO写入仍为TODO，当前有效标志为false。详见专项报告§9.3.8、来源#1528–#1534。
