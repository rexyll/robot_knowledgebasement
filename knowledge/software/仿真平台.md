# 仿真平台

> 仿真是机器人开发中的模型化试验环境，不是真实世界的替代品。它可用于运动学/动力学分析、算法开发、软件集成、虚拟调试、合成数据、强化学习和测试自动化；仿真结果的可信度取决于模型、参数、求解器、传感器、时间同步、软件接口和真实数据校准。**通过仿真不等于通过实机安全验证、法规认证或现场验收。**

## 1. 仿真任务分层：先明确要回答的问题

| 层次 | 主要问题 | 合适工具/方法 | 不可据此直接证明 |
|---|---|---|---|
| 数学/运动学模型 | 坐标变换、运动学、轨迹几何是否正确 | 单元测试、解析模型、数值计算 | 真实接触力、摩擦、结构强度 |
| 刚体动力学 | 质量、惯量、关节、驱动和接触响应是否合理 | Gazebo、MuJoCo、PhysX、CoppeliaSim | 未建模柔性、磨损、热和真实材料特性 |
| 传感器/环境 | 算法面对噪声、遮挡、光照和场景变化是否稳健 | Gazebo Sensors、Isaac Sim、Webots等 | 真实传感器完整误差分布与所有环境效应 |
| 软件集成 | ROS 2节点、TF、控制器、导航和任务状态机是否协同 | Gazebo/Isaac Sim/CoppeliaSim与真实软件栈 | 目标硬件实时性、驱动稳定性和现场安全 |
| SIL/PIL/HIL | 软件/处理器/控制器与外部对象的接口和时序是否正确 | 软件在环、处理器在环、硬件在环 | 未覆盖工况、真实机械负载和最终产品合规 |
| 训练与策略评估 | 学习策略是否收敛、对随机化参数是否鲁棒 | Isaac Lab、MuJoCo/MJX、其他训练框架 | 未经实机迁移验证的真实世界性能 |
| 虚拟调试/数字孪生 | 设备布局、流程、节拍、接口和生产逻辑是否满足假设 | 仿真场景、工艺/物流模型、现场数据映射 | 没有校准数据和持续同步的“真实数字孪生” |

应在开始建模前写明仿真目的、决策风险、输出指标、有效范围、精度需求、真实数据来源和验收准则。用于UI演示的视觉模型、用于导航算法的传感器模型、用于机械设计的接触模型、用于安全论证的模型，其精度要求并不相同。

## 2. 主流平台与版本状态（核验快照：2026-11-05）

版本会变化；项目必须锁定确切发行版、依赖、插件、操作系统、GPU驱动和ROS发行版，不要只记录“最新版”。

| 平台 | 主要用途/特点 | 版本与适配边界 | 选择时注意 |
|---|---|---|---|
| Gazebo Sim | ROS生态集成、刚体/传感器仿真、系统测试 | Jetty（2025-09，LTS至2031-05）；Harmonic（2023-09，LTS至2029-05）；Ionic预计2026-12 EOL。ROS 2 Jazzy推荐Harmonic；Jetty对应更新的ROS/Ubuntu组合 | 核对ros_gz、gz_ros2_control、SDF、插件ABI及ROS版本矩阵；Gazebo Classic与新Gazebo不是同一代产品 |
| NVIDIA Isaac Sim | RTX渲染、传感器/合成数据、USD场景、虚拟调试 | 6.2.0（2026-10）；支持Linux/Windows工作站，容器仅支持Linux；Ubuntu 22.04支持已标记弃用 | 对RTX GPU、驱动、VRAM、磁盘和在线资产有较高要求；按6.2交叉兼容表锁定ROS workspace、Newton、Isaac Lab |
| NVIDIA Isaac Lab | 强化学习、模仿学习、机器人策略训练/评估 | 3.0.0 GA（2026-10）；兼容Isaac Sim 6.2.0，支持多物理/渲染后端与kit-less工作流 | 不等于单一物理引擎；不同backend、renderer、任务配置的结果不可默认等价 |
| MuJoCo | 机器人动力学、接触、控制与学习研究；MJX/MuJoCo Warp用于加速工作流 | 3.17.0（2026-10-22） | 建模与求解器参数影响接触和稳定性；GPU/批量运行结果仍需对照CPU基准及实机 |
| CoppeliaSim | 多机器人、机械臂、运动学、控制脚本和快速原型 | 官方下载页列出V4.10.0 rev0 | 支持不同动力学后端；Pro/Lite/Edu使用条件不同，Edu仅限学校/大学教学研究且不可商用 |
| Webots | 教学、原型、移动/机械臂仿真和ROS集成 | 稳定发行版R2025b；仓库也发布nightly，不应将nightly视为稳定版 | 区分稳定发行版与nightly；核对控制器API、设备模型和目标操作系统 |
| AirSim / Colosseum | 无人机/自动驾驶视觉与环境仿真遗留生态 | AirSim原仓库与Colosseum fork应分别核对维护/归档状态；Colosseum仓库于2026-07-11归档 | 不把历史教程等同当前受支持平台；新项目需评估引擎版本、构建依赖、ROS接口和安全补丁 |
| 轻量自研仿真 | CI冒烟、状态机/接口契约、调度与故障注入 | 由项目自行维护 | 简化模型只能回答模型覆盖的问题；不可将简化运动学仿真包装成高保真物理验证 |

官方版本来源见链接台账#917–#924。Gazebo版本与ROS组合应按官方兼容表逐项选取，而不是笼统写“Gazebo配ROS 2”；Isaac Sim/Isaac Lab也应按NVIDIA交叉兼容表配套，不得仅凭相同主版本号推断兼容。

## 3. 物理模型与数值求解

### 3.1 刚体与机构参数

机器人模型至少需要核验：
- link/joint拓扑、关节轴方向、零位、限位、速度/力矩限制和传动比；
- 质量、质心、惯性张量、惯性坐标系和单位；
- 碰撞几何与视觉几何分离；简化碰撞体不能无意改变通道宽度、接触面或碰撞位置；
- 电机/驱动器的扭矩-速度曲线、限流、死区、饱和、制动和控制周期；
- 关节摩擦、阻尼、回差、柔性、结构变形、轮胎/履带与地面接触等适用模型。

URDF/SDF/USD/MJCF等模型文件并不保证语义完全相同。转换工具可能改变惯性、碰撞、材质、关节轴、传感器或插件属性；转换后应做结构化差异检查与基准场景回归。

### 3.2 求解器与接触

仿真步长、控制周期、接触求解迭代、碰撞检测、约束求解器和积分方法共同影响稳定性与结果。高速碰撞、薄障碍、刚性接触、关节限位、摩擦锥和多点接触可能出现穿透、抖动、能量注入或数值不收敛。不得仅靠减小步长就宣称模型可信；应对关键工况做步长/求解器收敛性分析，并与解析解、公开基准或实测数据对照。

Gazebo Sim采用插件化物理引擎架构，DART为默认实现；Bullet和TPE等有各自适用范围。TPE侧重规模化实体的快速运动学/车队级近似，不提供完整重力、力和约束动力学。不能把不同引擎称作可互换或物理精度等价。

### 3.3 传感器模型

传感器仿真至少应按目标设备与任务考虑以下误差源，而不是笼统地“加高斯噪声即可”：

| 传感器 | 重要建模维度 |
|---|---|
| 相机/深度相机 | 内外参、畸变、视场、分辨率、曝光/增益、动态范围、滚动快门、运动模糊、光照/材质、深度空洞与量化 |
| LiDAR | 线数/扫描模式、角分辨率、量程、回波/强度、发散角、遮挡、反射率、雨雾尘、丢点和运动畸变 |
| IMU | 零偏、噪声密度、随机游走、比例因子、轴不正交、饱和、带宽、采样率、温漂与时间同步 |
| 编码器 | 分辨率、量化、丢计数、方向/安装偏差、回差、采样和通信延迟 |
| GNSS/磁力计 | 遮挡、多路径、漂移、磁干扰、更新率、失锁和恢复 |
| 超声/毫米波 | 波束形状、盲区、反射材质、虚警/漏检、多径、距离/速度噪声与目标RCS |

Gazebo Sensors提供多种传感器模型和可配置噪声模型，但“支持某传感器类型”不等于准确复现某个厂商型号。应将传感器datasheet、标定文件、实测噪声分布和驱动输出格式作为建模输入；用静态标定靶、已知轨迹、时间戳和真实bag数据对照。

## 4. ROS 2集成、仿真时间与确定性

- Gazebo使用`ros_gz`桥接ROS 2消息；桥接topic的消息类型、QoS、方向、频率和命名空间必须形成接口清单。控制器插件和`gz_ros2_control`需锁定匹配版本。
- Isaac Sim使用ROS 2 Bridge；6.2的ROS workspace应使用对应`IsaacSim-6.2.0`版本。官方文档推荐Ubuntu 24.04 + ROS 2 Jazzy；Humble在Ubuntu 24.04不受支持。
- `use_sim_time=true`需要对所有相关节点、TF、传感器驱动、bag记录和测试工具统一配置。检查`/clock`是否发布、暂停/重置时是否正确处理、消息时间戳是否使用仿真时钟。
- 区分仿真时间、墙钟时间和单调时钟。实时因子（real-time factor）小于1表示仿真慢于墙钟；高于1不代表物理模型更准确。硬实时/HIL场景需测量调度抖动、周期超时、传输延迟和丢帧。
- 记录随机种子、线程数、GPU/CPU、求解器、步长、驱动、容器镜像digest和模型版本。GPU并行、异步渲染和多线程求解不保证跨硬件逐位确定性。
- 对命令/状态接口定义超时、故障码、重置行为、急停状态和仿真/实机模式隔离，防止仿真控制指令误发到真实机器人。

## 5. Sim-to-Real：缩小差距而不是声称消除差距

仿真到现实（Sim2Real）存在模型误差和分布差异，常见来源包括质量/惯量误差、摩擦与接触、执行器动力学、传感器噪声、延迟、环境材质、照明、地面变化、通信抖动和未建模故障。

建议流程：
1. **参数辨识**：测量真实机器人质量、惯量、轮径/轮距、关节摩擦、驱动响应、制动距离、传感器噪声和系统延迟；保留数据与拟合误差。
2. **基准场景**：建立可复现的直线/转弯、坡道、台阶、载荷变化、接触、避障和传感器标定场景。
3. **域随机化**：对有物理依据的参数分布采样，覆盖实测置信范围和合理工况；保留参数相关性、边界和采样记录。质量±20%、摩擦±30%、延迟0–50ms只能作为某个项目经论证的实验配置，不能成为通用模板。
4. **系统辨识与校准**：使用实机日志更新参数，分开训练集、校准集和留出验证集，避免对同一数据既拟合又宣称泛化。
5. **分级迁移**：先离线回放/软件在环，再仿真闭环、低风险实机、受控场地和目标工况；设置安全员、限速、急停和回退方案。
6. **差异报告**：对位置/姿态误差、轨迹误差、碰撞/接触、感知指标、控制周期、成功率、能耗和恢复行为报告仿真与实机差值及置信区间。

域随机化不自动保证Sim2Real成功；随机化范围过窄会漏掉真实情况，过宽可能使训练任务失真。需要用实机分布、任务风险和验证数据选择随机化范围。数字孪生也必须持续校准、标注数据时效和模型不确定性。

## 6. SIL / PIL / HIL 与测试分层

| 类型 | 被测对象 | 关键验证点 |
|---|---|---|
| MIL（模型在环） | 控制/算法模型与被控对象模型 | 方程、状态机、边界条件、模型误差 |
| SIL（软件在环） | 编译后的软件或节点与仿真对象 | 接口、消息、逻辑、回归、资源和异常处理 |
| PIL（处理器在环） | 目标处理器/编译器上的软件 | 指令集、数值差异、执行时间和资源占用 |
| HIL（硬件在环） | 真实控制器/IO/驱动硬件连接实时仿真对象 | I/O电平与时序、总线、实时性、故障注入、看门狗和安全状态 |
| VIL（车辆/机器人在环） | 实际机器人/车辆与虚拟场景/环境组合 | 传感器/执行器闭环、场景覆盖、定位/感知/控制集成 |

HIL不是“运行一个仿真程序”就成立：需明确真实硬件清单、实时仿真器、I/O接口、总线时延、同步方案、采样周期、故障注入和安全隔离。未接入真实控制器/IO的纯软件测试不能标记为HIL。SIL/HIL测试应保存配置、源码/固件版本、场景、随机种子、原始日志、测试结果和失败复现步骤。

## 7. 仿真测试体系与CI

建议将仿真测试分成可快速反馈的层级：
- PR级：模型文件解析、URDF/SDF/USD/MJCF静态检查、TF/接口契约、最小世界加载、节点启动和短时冒烟。
- Nightly级：多场景回归、传感器数据管线、导航/操控任务、随机种子批量运行、性能与资源趋势。
- 发布前：长时运行、故障注入、参数边界、版本升级回归、SIL/PIL/HIL、目标硬件和实机验证。
- 现场验收：目标地图/载荷/工况、人员共域、网络干扰、环境变化、恢复流程和安全功能实测。

每个测试用例定义：ID、需求追踪、场景版本、初始条件、参数分布、随机种子、软件/固件commit、仿真器/插件版本、运行环境、观测指标、通过阈值、日志位置、失败分类和复测状态。阈值必须来自需求、风险分析或实机基线，不能用任意“到位精度/耗时/碰撞次数”替代产品验收要求。

性能指标建议包括：任务成功率、碰撞/近失事件、轨迹偏差、定位误差、感知Precision/Recall、控制周期抖动、消息延迟、CPU/GPU/内存、仿真实时因子、测试覆盖率和故障恢复时间。报告平均值以外，还应保留分位数、极值、样本量和失败案例。

## 8. 选型建议：以工作负载和证据为准

- ROS 2移动机器人系统集成、传感器话题和导航回归：优先评估Gazebo Sim与目标ROS发行版的官方配套版本。
- RTX视觉传感器、合成数据、复杂场景渲染和GPU训练：评估Isaac Sim；强化学习/模仿学习工作流再评估Isaac Lab。
- 接触动力学、机械臂/足式机器人控制算法和快速批量动力学试验：评估MuJoCo；根据需要使用MJX/MuJoCo Warp，并验证加速后数值与基准的一致性。
- 多机器人教学/快速原型和脚本化场景：评估CoppeliaSim或Webots，先核对许可、API和目标硬件接口。
- CI只需验证状态机、消息契约或调度逻辑：可用轻量自研模型，但应明确它没有覆盖真实接触、传感器和实时性。

不要以“4096环境并行”“十万点实时”或“合成数据降低标注成本10–100倍”等单个宣传数字直接选型。并行数、吞吐量和成本收益高度依赖任务、模型复杂度、GPU、渲染/传感器开销、批大小和评估方法；应使用目标任务的可复现benchmark验证。

## 9. 项目实例边界

仓库内清洁机器人`SIM_VERIFICATION`、AMR smoke脚本等属于项目级仿真/自动化测试线索。复用时必须查看脚本、输入场景、被测代码、断言和CI运行记录，确认它实际覆盖的是运动学、软件状态机、ROS接口还是物理接触。存在脚本不代表测试已执行成功，更不代表真实机器人通过验证。

## 10. 未关闭事项与验收状态

本文为平台和方法论层的主张边界审查，不是对某台机器人或仿真模型的验证报告。仍需：
- 为目标项目确定机器人型号、控制器、传感器、操作系统、ROS发行版和部署硬件；
- 锁定Gazebo/Isaac/MuJoCo等确切版本、插件、容器digest、驱动与许可证；
- 采集真实参数与传感器数据，完成系统辨识、标定和模型误差评估；
- 建立需求追踪的场景库、回归基线和统计验收阈值；
- 对目标控制器执行PIL/HIL、故障注入和实机对照；
- 对Sim2Real策略在目标工况进行分级验证并记录安全措施。

在这些证据齐备前，仿真结果不得用于宣称真实性能、安全等级、法规符合性或量产可交付性。
