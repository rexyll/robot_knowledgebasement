# 实时系统与嵌入式（Real-Time Systems & Embedded）

> 实时系统的核心不是“尽可能快”，而是**在规定时间约束内，可靠地产生正确响应**。平均执行速度高，并不代表满足实时要求；抖动、最坏执行时间、调度延迟、通信时延、硬件中断和故障响应都需要纳入系统预算。实时性能与功能安全相关，但二者不是同一个概念：具备 PREEMPT_RT、RTOS 或 watchdog 不代表产品已通过功能安全认证。

## 1. 实时性基础：先定义 deadline

### 1.1 常用术语

| 术语 | 含义 | 工程使用方式 |
|---|---|---|
| Deadline | 任务/控制动作必须完成的最晚时间 | 从控制需求、执行器带宽、机械响应和风险分析得到 |
| Latency | 输入事件到任务开始/结束或执行器响应的时间，必须明确测量起止点 | 区分唤醒延迟、任务执行时间、端到端延迟 |
| Jitter | 周期任务实际启动时间/完成时间相对理想周期的变化 | 记录最小/最大/分位数和时间窗口，不能只报平均值 |
| WCET（Worst-Case Execution Time） | 特定硬件/编译/输入与执行环境下可证明或可信估计的最坏执行时间 | 测量最大值不等于证明 WCET；需要结合静态分析、系统约束和覆盖场景 |
| Throughput | 单位时间能处理的任务/数据量 | 高吞吐不一定低延迟，也不一定满足 deadline |
| Response Time | 从事件/任务释放到任务完成或系统响应的时间 | 与调度、阻塞、执行时间、中断和资源竞争一起分析 |

### 1.2 硬实时、软实时与非实时

- **硬实时（Hard Real-Time）**：错过 deadline 可能导致不可接受的系统/安全后果；需要有可信的最坏时序分析和故障响应。
- **软实时（Soft Real-Time）**：超时会降低质量或服务水平，但不一定造成灾难性后果；例如部分感知、规划、交互任务。
- **Firm Real-Time**：结果超过 deadline 即失去价值，但偶发错过不一定直接造成安全事故；应按系统需求定义。
- **非实时**：任务没有严格响应时间约束，主要优化平均性能/吞吐。

不能把“1 kHz 就是硬实时、20 Hz 就是软实时”当成定义。频率是任务周期；是否硬/软实时由 deadline、错过期限后果和可验证时序保证决定。

## 2. 控制系统的任务周期与分层

机器人通常存在多个不同带宽的控制/估计任务，但其频率取决于被控对象、执行器、传感器、控制器和应用需求。不要把电流环、轮速环、导航控制、感知和云端任务写成所有机器人的固定频率层级。

典型分工可能是：

| 层级 | 可能处理的任务 | 主要时序约束 |
|---|---|---|
| 驱动器/伺服内部 | 电流、速度、位置内环；PWM/FOC | 由电机、电流采样、功率器件、驱动器和执行器能力确定 |
| MCU/实时控制器 | 轮速/关节闭环、运动学解算、编码器采样、接触/限位监控 | 由机械带宽、传感器采样、通信和硬件接口确定 |
| 主控实时任务 | 底盘/机械臂控制器、状态估计、同步和硬件接口更新 | 由控制模型、ros2_control 等框架配置及目标硬件测量确定 |
| 导航与感知 | SLAM、局部规划、图像/点云感知、动态目标预测 | 需在算法时延、刷新率和运动速度之间平衡；不一定硬实时 |
| 任务/云端 | 任务分配、日志、地图管理、RMS、数据上传 | 更重视可靠性、吞吐和服务响应；不能用于替代本地保护链 |

闭环采样周期需要结合系统带宽、离散化误差、相位裕度、执行器延迟和传感器噪声设计。外环通常比内环低速，但“低多少”不是固定倍数。若使用 ROS 2，Controller Manager 的 update_rate 是配置参数；硬件驱动和电机控制器可能另有内部更新周期，两者不能简单等同。

## 3. 实时 Linux：PREEMPT_RT 与系统调优

### 3.1 标准 Linux 与 PREEMPT_RT

PREEMPT_RT 通过可抢占锁、优先级继承和线程化中断等机制，减少内核中不可抢占执行区间，让高优先级实时任务更可预测。Linux 内核官方文档解释了其对 locking、SCHED_FIFO 和 IRQ 线程的处理方式。<Cite refs={["turn329160search1","turn329160search3"]}/>

需要注意：

- PREEMPT_RT 主要改善调度可预测性和响应延迟，不会自动给整个机器人提供硬实时证明。
- 驱动、固件、总线、DMA、中断风暴、CPU 频率/深度休眠、SMI、内存换页和锁竞争仍可能造成抖动。
- 支持的内核版本、架构、配置项和厂商补丁因发行版/设备而异；部署前要核对目标内核实际带有的 RT 配置和驱动兼容性。
- 线程采用 SCHED_FIFO/SCHED_RR 需要权限与合理优先级规划；错误的高优先级忙循环可能饿死普通系统任务。

### 3.2 Ubuntu Real-time 的安装与版本

Ubuntu 官方 Real-time 文档说明其实时内核包含 PREEMPT_RT patchset。Ubuntu Server/Desktop 的安装入口为 ubuntu-realtime；Raspberry Pi 等特定平台有不同包。实时内核/HWE 版本随 Ubuntu 发行版和硬件平台变化，应对照官方 release matrix 选择。<Cite refs={["turn496355search0","turn496355search2","turn496355search3","turn496355search5"]}/>

**不要使用 Debian 的 linux-image-rt-amd64 作为 Ubuntu 24.04 的通用安装命令。** Ubuntu 24.04 的官方安装/启用步骤、Pro 服务状态、HWE 内核和受支持架构，均以目标设备当前官方文档为准。实时内核还需要与 GPU、网络、相机、CAN/EtherCAT 驱动和固件一同验证。

### 3.3 实时 Linux 常见调优项

| 项目 | 目的 | 代价/注意事项 |
|---|---|---|
| SCHED_FIFO / SCHED_RR 优先级 | 让关键线程按实时优先级调度 | 必须分析优先级关系、锁阻塞和优先级反转；不能给所有线程相同高优先级 |
| CPU affinity / isolation | 将实时线程和 housekeeping/非实时工作分配到不同 CPU | 还需考虑 IRQ、workqueue、RCU、SMT 兄弟线程和跨 NUMA 访问；隔离不当会降低系统总体性能 |
| IRQ affinity / threaded IRQ | 控制硬件中断的 CPU 位置和处理优先级 | 不能把高频 DMA/网络/存储中断随意放到实时 CPU |
| mlockall / 预分配内存 | 降低 page fault、内存回收和运行期动态分配引入的抖动 | 内存预算必须可控；避免实时路径上动态分配、阻塞日志和不可预测 I/O |
| CPU frequency / C-state | 控制频率切换和深度休眠唤醒延迟 | 功耗、温度、性能和电源设计会变化；须在代表性热稳态条件下实测 |
| 锁与共享资源 | 减少锁竞争、优先级反转和长时间临界区 | 使用适当优先级继承锁或无锁/单写者设计；仍要验证内存一致性和数据新鲜度 |

Linux 内核 CPU isolation 指南特别指出，异步中断/定时器、workqueue、page fault、SMT、CPU 频率与深度 C-state 都可能影响低抖动任务。CPU isolation 是有成本的系统调优，不是开一个内核参数即可保证 deadline。<Cite refs={["turn964949search5","turn964949search10","turn964949search3"]}/>

## 4. RTOS 与 MCU 固件

### 4.1 常见选择

| 系统 | 特点 | 常见适用场景 | 注意事项 |
|---|---|---|---|
| FreeRTOS | 小型实时内核，任务/队列/定时器等基础机制；可配置到多类 MCU | 电机控制辅助任务、传感器采集、网关/外围控制器 | 中断优先级、任务优先级、堆实现、临界区和第三方库需逐项目核验 |
| Zephyr | 开源 RTOS，设备驱动、设备树、网络与构建系统较完整 | 需要组件化驱动、联网与多架构适配的嵌入式产品 | 需固定版本、板级支持包、Kconfig/设备树和安全/许可范围；官方安全工作组的目标/路线不等于整个 Zephyr 已获 IEC 61508 SIL 3 认证 |
| RT-Thread | 面向嵌入式设备的 RTOS 和组件生态 | MCU/SoC 控制、通信与设备应用 | 内核、组件、第三方包及商业支持范围需按实际版本/模块核查 |
| 裸机（bare metal） | 不使用通用 RTOS 调度器，控制逻辑直接基于中断/主循环实现 | 功能极简、资源受限、时序结构非常清楚的固件 | 模块化、任务隔离、升级、诊断和复杂并发管理的维护成本可能提高 |

选择 RTOS 不是单看“微秒级响应”宣传：应比较芯片架构、BSP/驱动成熟度、工具链、网络栈、调试、升级、内存/安全机制、供应链和长期维护策略。

### 4.2 FreeRTOS 与 Zephyr 的许可/安全声明

- FreeRTOS kernel 官方许可为 MIT；其官方说明也提示 demo/示例中可包含独立许可的第三方库。MIT 许可不代表所有示例、厂商驱动和集成依赖都自动为 MIT。<Cite refs={["turn496355search1","turn496355search4"]}/>
- Zephyr 仓库根 LICENSE 为 Apache-2.0，但依赖/模块可能有不同许可。Zephyr Safety Overview 当前描述的是针对**限定源代码范围**以 IEC 61508 SIL 3 / SC3 为目标的安全流程，并标出其阶段推进状态；不能写成整个 Zephyr RTOS 已经获得 SIL 3 认证。<Cite refs={["turn329160search0"]}/>
- 若产品需要安全认证，应按实际使用的 RTOS 版本、配置、代码范围、工具链、硬件、开发流程和安全手册进行独立评估；普通 RTOS 许可与功能安全认证是两件不同的事。

## 5. 实时控制、watchdog 与主控—MCU 分工

### 5.1 主控 + MCU 是一种架构，不是所有机器人的标准答案

常见移动平台可以将高层导航/感知与底盘低层闭环分开：

~~~text
主控 SoC / Linux / ROS 2
  ├─ 定位、导航、任务与日志
  ├─ 输出速度/关节/技能目标
  └─ 接收底盘状态、故障和确认
                │
       UART / CAN / Ethernet / EtherCAT
                │
MCU / 实时控制器 / 驱动器
  ├─ 接收并验证命令（版本、序号、时间戳、有效期）
  ├─ 运动学/逆运动学与限幅
  ├─ 本地速度/位置/力矩闭环（按设备架构）
  ├─ 故障状态和超时处理
  └─ 反馈编码器、电流、温度、电池和驱动器状态
                │
           电机/制动器/机械本体
~~~

架构设计要明确哪些环路已在驱动器内完成，哪些在 MCU，哪些在主控；避免将同一个变量在不同层重复闭环导致争用和振荡。并非所有平台都需要独立 MCU；集成式伺服、智能驱动器或安全 PLC 可能承担部分职责。

### 5.2 命令协议与失联状态

协议字段建议至少考虑：
- 消息版本、机器人/设备 ID、命令类型和序号；
- 发送时间戳/时钟基准、命令有效期或 lease；
- CRC/校验、长度、限值、模式与错误码；
- 命令接受/拒绝确认、实际执行状态和反馈时间戳；
- 重发/重复命令的幂等语义、乱序/过期命令的拒绝规则；
- 心跳、通信质量、故障状态和复位条件。

**心跳超时不能一律设为 200ms，也不应无条件“自动刹车”。** 失联检测阈值和动作应基于最坏通信延迟、命令有效期、当前速度/载荷、停车距离、风险评估和制动器特性设计。某些场景需要受控减速；某些故障需要独立硬件保护停止；在位置/占用不明时还需防止自动重启。

### 5.3 Watchdog 分层

- **软件 watchdog**：监视任务执行周期、状态机、队列、控制器更新和程序心跳；
- **硬件 watchdog**：由独立时钟/芯片监控 MCU 固件是否按期刷新；
- **驱动器/安全控制器**：监控使能、通信、速度/力矩限制、制动与保护输入；
- **安全功能**：安全急停、保护停止、STO/SS1 等功能按风险评估和适用标准设计，并验证硬件/软件/线路。

普通 MCU watchdog 只能检测特定程序失效，不能自动证明制动器、接触器、双通道输入或安全控制器达到所需 PL/SIL。

## 6. 通信总线与实时性边界

| 总线/接口 | 常见用途 | 实时性与约束 |
|---|---|---|
| UART | 主控↔MCU、低速设备协议、调试 | UART 本身只定义串行收发；帧格式、仲裁、确认、超时和时钟由上层协议设计。吞吐/时延受波特率、帧长、缓冲和调度影响 |
| RS-485 | 多点差分物理链路 | 它是物理层/电气接口，不自带统一总线调度协议；需定义主从轮询、仲裁、帧校验和超时 |
| Classical CAN | 电机、BMS、分布式节点通信 | 非破坏性仲裁按标识符优先级进行；实时响应受报文优先级、总线负载、帧周期、错误重发和拓扑影响 |
| CAN FD | 增大单帧数据量，支持仲裁阶段与数据阶段不同速率 | 数据长度可扩展到 64 字节；标称/数据阶段 bitrate 要结合控制器、收发器、线缆长度、拓扑、采样点和节点兼容性确定，不存在跨设备统一的 5Mbps/8Mbps 保证 |
| EtherCAT | 多轴伺服、分布式 I/O | 支持 Distributed Clocks 等时钟同步机制；ETG 给出特定实现下远低于 1μs 的同步抖动描述，但实际取决于主站/从站硬件、拓扑、时钟和周期配置，不能将其写作端到端控制时延保证 |
| SPI / I²C | 板级传感器、ADC、EEPROM 等 | 适合板内/短距离连接；总线速率、仲裁、线长、驱动实现和设备响应决定时序，不是通用实时网络 |
| Ethernet / TSN | 主控、工业网络与多设备通信 | 普通 Ethernet 不自动提供确定性；TSN 需网络设备/终端支持并进行时间同步、队列整形和流量规划；100BASE-T1 是物理层类型，不等于已配置 TSN |

Bosch 对 CAN FD 的说明指出其相对 Classical CAN 扩展了帧数据长度并支持更高速的数据阶段；EtherCAT Technology Group 对 Distributed Clocks 的说明强调硬件时钟校准及系统条件。总线的链路层能力不能替代应用层实时响应分析。<Cite refs={["turn964949search0","turn964949search1","turn964949search12"]}/>

## 7. 实时测量与验证

### 7.1 测量工具

| 工具 | 能观察什么 | 不能替代什么 |
|---|---|---|
| cyclictest（rt-tests） | 周期线程从计划唤醒到实际运行的 latency 统计（min/max/avg/histogram） | 不等于应用 WCET、通信端到端时延或机械制动响应 |
| rtla timerlat | 定时器/线程唤醒延迟与相关内核时序问题 | 不等于完整控制任务的 end-to-end 验收 |
| ftrace / trace-cmd | 调度切换、中断、定时器、软中断和事件时序 | 需要正确选择 tracepoint、工作负载和 CPU 亲和性 |
| 逻辑分析仪/示波器 | GPIO 打点、总线消息、PWM/编码器/制动器信号的外部时序 | 需明确探测点、电平/负载、同步和测量精度 |
| HIL / 实机故障注入 | 通信丢包、驱动失效、任务超时和状态机恢复 | 需要完整测试场景、风险评估和受控硬件环境 |

Linux Foundation cyclictest 文档说明输出的最小/最大/平均值来自测量线程的定时唤醒延迟；Ubuntu Real-time 指南还建议按实际 CPU 隔离与工作负载配置 cyclictest、trace-cmd 或 rtla。因此，测试结果必须记录线程优先级/亲和性、周期、运行时长、负载、内核、驱动、CPU 频率/温度和测量工具版本。<Cite refs={["turn496355search11","turn496355search12","turn964949search3","turn964949search5"]}/>

### 7.2 验收矩阵

至少验证：
1. **任务周期**：目标周期、deadline miss 次数/比例、唤醒延迟分布、执行时间分布、最大观测抖动；
2. **端到端控制**：传感器采样→状态估计→控制输出→通信→驱动器接收→有效机械响应；
3. **CPU/系统负载**：满负载感知、日志、网络、磁盘 I/O、启动/更新和后台任务；
4. **异常条件**：CPU 争用、IRQ 高负载、网卡/USB/CAN 错误、内存压力、温度变化、电源波动；
5. **掉线恢复**：心跳丢失、乱序/重复/过期命令、驱动器错误、MCU 重启与参数回滚；
6. **安全功能**：安全停止输入、STO/制动器反馈、复位防误启动、硬件故障和人工接管。

实测最大延迟只是被测场景和时长内的观测值，不自动构成严格 WCET 或最坏工况证明。硬实时/安全相关系统必须把需求、分析、测试覆盖、故障场景和证据链结合起来。

## 8. 常见工程问题

| 现象 | 可能原因 | 检查方向 |
|---|---|---|
| 控制周期偶发超时 | CPU/IRQ 争用、锁阻塞、page fault、内存分配、驱动/总线阻塞 | trace-cmd/rtla 追踪线程、IRQ、锁和时间戳 |
| PREEMPT_RT 下仍有抖动 | BIOS/SMI、CPU 频率/C-state、IRQ 亲和性、SMT、固件/驱动 | 对照实际内核配置和 CPU isolation；逐项调整并重测 |
| MCU 命令断续/状态错乱 | 波特率、总线负载、协议超时、序号/重发、缓存溢出、时钟偏移 | 记录总线原始帧、序号、错误计数和端到端时间 |
| watchdog 误触发 | 阈值与真实通信抖动不匹配、心跳和任务执行状态耦合、阻塞 I/O | 统计高分位延迟、独立心跳路径、区分控制任务与监控任务 |

## 11. 本轮定向复核与未关闭事项（2026-11-03）

本轮纠正：

- 删除“电流环 1kHz 硬实时、底盘 100–1kHz、导航 10–50Hz”等固定层级；强调 real-time 由 deadline 和错过期限的后果定义，不由频率标签决定。
- 删除标准 Linux “毫秒级抖动”、PREEMPT_RT “<100μs”、Xenomai “<50μs”、调度延迟“<50μs”和急停“<10ms”的通用性能保证；改为按 CPU/内核/驱动/负载/仪器测量。
- 纠正 Ubuntu 安装命令：Ubuntu Real-time 官方入口为 ubuntu-realtime 等发行版/平台相关包；linux-image-rt-amd64 是 Debian 包命名，不是 Ubuntu 24.04 通用命令。
- 纠正 PREEMPT_RT 主线化表述：避免把某一内核版本写成所有架构/发行版/驱动通用支持；实际 kernel config、架构和供应商补丁必须核验。
- 纠正 Zephyr “安全认证版/已认证”表述：官方安全文档目前说明的是限定源代码范围向 IEC 61508 SIL3/SC3 推进的目标与阶段，不是整个 Zephyr OS 已认证。
- 补充 FreeRTOS kernel MIT 许可与 demo/第三方库许可的区别；RTOS 许可证与功能安全认证分开。
- 纠正 CAN FD、EtherCAT、RS-485 和 100BASE-T1 的通用速率/确定性陈述：CAN FD 标称/数据阶段与物理层配置相关；EtherCAT Distributed Clocks 的亚微秒描述是特定硬件时钟同步能力，不等于端到端控制时延；RS-485 是物理层，TSN 也不是 100BASE-T1 自动具备。
- 删除 UART/CAN 50–100Hz、串口/CAN+FOC 1kHz、心跳超时 200ms 自动刹停等双脑通用固定配置，改为消息有效期、错误/重发、失联状态和风险评估。
- 明确普通 watchdog、PREEMPT_RT、Collision Monitor、MCU 固件和安全额定功能的区别；删除“L2 固件安全层”这种无标准依据用语。
- 区分 cyclictest/timerlat 的唤醒延迟与应用 WCET、端到端机械响应；补充代表性负载和 CPU/IRQ/温度等测试条件。
