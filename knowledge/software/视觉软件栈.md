# 视觉软件栈

> 机器人视觉是一条从光学成像、相机采集、时钟与标定、图像/点云处理、模型推理到感知决策的端到端数据链。算法FPS、单帧推理延迟或标定重投影误差中的任何单一数字，都不能独立代表整机视觉能力。必须同时记录传感器型号/固件、曝光与触发方式、数据格式、时钟域、驱动、运行时、模型、硬件和现场工况。

## 1. 分层架构与数据流

```text
场景/光学：镜头、光源、滤光片、曝光、景深、运动模糊
    ↓
传感器与采集：CMOS/全局或滚动快门、触发、ISP、帧缓存
    ↓
传输与驱动：USB3 Vision / GigE Vision / MIPI CSI-2 / Camera Link
    ↓
采集运行时：厂商SDK、GenICam/GenTL、V4L2、libcamera、GStreamer
    ↓
消息与缓存：图像编码/零拷贝、时间戳、CameraInfo、队列背压
    ↓
几何与传统视觉：OpenCV、Eigen、PCL、Open3D、Halcon等
    ↓
模型推理：PyTorch训练 → ONNX交换 → TensorRT / OpenVINO / ORT EP
    ↓
感知输出：检测/分割/跟踪/深度/位姿/缺陷/置信度
    ↓
机器人应用：TF坐标变换、融合定位、抓取、导航、控制与安全策略
```

必须将“相机接口”“相机SDK”“图像处理库”“模型运行时”和“ROS驱动”分开选型。它们处于不同层次：GenICam不是USB/GigE物理接口，OpenCV不是相机硬件驱动，ONNX不是推理引擎，ROS image_transport也不是传感器时钟同步协议。

## 2. 相机接口、标准与采集驱动

| 接口/框架 | 主要用途 | 工程边界 |
|---|---|---|
| USB3 Vision | 工业相机USB链路 | 检查主机控制器/带宽、线缆、供电、设备枚举、驱动与厂商兼容列表；多相机共享总线会争用带宽 |
| GigE Vision | 工业以太网相机 | 检查网卡、交换机、MTU/Jumbo Frame、包大小/间隔、丢包重传、网络隔离和PoE预算 |
| GenICam | 跨厂商相机功能描述与访问框架 | GenApi描述相机功能节点；GenTL定义传输层接口。具体可用功能取决于相机、传输层和厂商实现 |
| MIPI CSI-2 | 嵌入式SoC相机传感器链路 | 依赖SoC CSI接收器、lane数/速率、设备树、sensor驱动、ISP和板级设计 |
| V4L2 | Linux视频设备用户态/内核接口 | 适合内核支持的采集设备；厂商高级功能、触发和元数据能力可能仍需专有SDK |
| libcamera | Linux相机管理与pipeline框架 | 由平台pipeline handler和sensor/ISP支持决定，不是所有工业相机都能直接使用 |
| 厂商SDK | 设备发现、参数、触发、chunk数据、固件升级等 | 应锁定SDK版本、固件、驱动、运行库和许可；厂商SDK不能默认跨型号/OS兼容 |
| GStreamer | 多媒体采集、处理、编码和流转 | 适合构建pipeline；必须测量端到端延迟、队列、时钟和丢帧，而不是只看管线是否启动 |

### 2.1 工业相机软件标准

- **GenICam**是一组机器视觉相机软件接口标准族。GenApi以XML功能描述文件暴露相机参数节点；GenTL定义从传输层设备发现、数据流到缓冲区交付的标准接口。不同厂商实现的功能节点、事件、Chunk数据和性能仍可能不同。
- **GigE Vision**与**USB3 Vision**定义相应传输接口的设备/主机通信规范；它们不意味着相机在任何网卡、USB控制器、线缆、操作系统或SDK上都能达到标称吞吐。
- 选型时要求供应商提供标准版本、认证/兼容信息、GenTL Producer、相机XML、固件版本、操作系统支持矩阵和已知限制。不要把“支持GenICam”误写成“所有参数和触发能力完全一致”。
- GigE多相机部署要测量实际帧率、包丢失、重传、主机CPU和网卡队列；USB多相机要验证拓扑、控制器共享和持续负载。带宽计算需计入像素位宽、行/帧开销、打包方式、元数据和协议开销。

### 2.2 采集链路设计

采集线程与算法线程应解耦。常见结构：

```text
Camera SDK callback / V4L2 dequeue
    → DMA/SDK buffer pool
    → timestamp + frame metadata
    → bounded ring buffer
    → image transport / intra-process loan or copy
    → preprocess / inference worker
    → result queue + watchdog
```

- 缓冲队列必须有界，并定义满队列策略：丢最旧帧、丢最新帧、阻塞或降采样；策略取决于实时性和业务语义。
- 对实时避障/控制，旧帧积压可能比丢帧更危险；对质量追溯/缺陷检测，丢帧可能直接造成漏检，应采用完整性计数、触发计数和丢帧报警。
- 明确buffer所有权、生命周期和跨线程同步。SDK回调返回后若缓冲区可被复用，异步算法不能继续持有裸指针。
- 记录帧序号、设备时戳、主机接收时戳、曝光时间、增益、触发ID、丢帧/重传计数和相机温度等可用元数据。
- 零拷贝并非“没有代价”：DMA内存、对齐、stride、像素格式、生命周期和消费者兼容性都需验证；复制一次可能比复杂共享内存更稳定。

## 3. 图像与点云基础库

| 工具 | 定位 | 典型能力 | 选择注意事项 |
|---|---|---|---|
| OpenCV | 通用2D视觉与几何 | 图像变换、滤波、特征、标定、立体视觉、传统算法和部分DNN功能 | 按版本核对模块/API和编译选项；OpenCV 5有API/模块调整 |
| PCL | 3D点云处理 | 滤波、特征、关键点、配准、分割、表面重建和可视化 | 大型C++依赖；关注Eigen/Boost/VTK、编译器ABI和目标架构 |
| Open3D | 3D数据处理与研究/应用工具 | 点云/网格、配准、可视化、重建和张量运算 | 评估CPU/GPU后端、版本、Python/C++接口及目标设备部署情况 |
| Eigen | 线性代数 | 矩阵、向量、四元数和几何变换 | 注意对齐、编译选项和ABI；不要在模块边界随意混用不同编译配置 |
| Sophus | 李群/李代数 | SO(3)/SE(3)及优化中的位姿表示 | 版本和Eigen兼容性需固定 |
| Ceres / g2o / GTSAM | 非线性优化 | Bundle Adjustment、位姿图、因子图和状态估计 | 依赖、求解器、线性代数后端及实时资源要按项目验证 |
| HALCON | 商业机器视觉平台 | 工业检测、匹配、测量、OCR等 | 商业许可、运行时部署、版本/硬件授权和功能模块需逐项确认 |
| GStreamer | 多媒体流水线 | 采集、转换、同步、编码和传输 | 实时pipeline要关注时钟、队列、buffer和端到端latency |

### 3.1 OpenCV版本与许可

- OpenCV 5.0于2026-06发布；官方资料说明5.x与4.x分支均在维护，5.x清理旧API并以C++17为最低标准。旧代码从4.x迁移时必须对照迁移指南，不能假定源码兼容。
- OpenCV 5调整了模块边界：例如G-API和Classic ML迁移到opencv_contrib，calib3d能力拆分为geometry/calib/stereo/ptcloud等模块；特征与检测相关旧算法也有迁移。构建时应锁定opencv与opencv_contrib相同兼容版本和模块清单。
- OpenCV主仓库和opencv_contrib当前代码库采用Apache-2.0许可声明，但第三方算法、模型权重、样例数据、外部codec和单独集成组件可能有各自许可。必须对实际分发的源码/二进制依赖做SBOM和许可证审查；不能笼统声称“所有OpenCV组件许可完全一致”。
- 不要将“OpenCV是视觉事实标准”当成技术指标或唯一选型依据。工业测量、相机供应商SDK、GPU流水线和专用算法可能需要其他工具组合。

### 3.2 PCL与点云处理边界

PCL官方文档列出Filters、Features、Keypoints、Registration、Segmentation、Sample Consensus、Surface、I/O和Visualization等模块，覆盖常见点云处理任务。常用算法包括VoxelGrid降采样、StatisticalOutlierRemoval、ICP/NDT配准、RANSAC模型拟合和欧式聚类。

- ICP/NDT的收敛依赖初值、点云重叠、场景几何、噪声和外点；“配准成功”不等于得到全局正确位姿。
- 体素尺寸、邻域大小、外点阈值和聚类容差必须按传感器量程、点密度和任务尺度设置，不能跨传感器照搬固定参数。
- PCL官网文档当前显示1.15.1-dev，是开发文档版本标识，不代表已发布稳定版。生产选型应查正式release/tag、发行版包版本和编译依赖。
- PCL按BSD许可发布；仍应核对随产品分发的其他依赖许可和第三方代码。

## 4. 标定：模型、数据采集与验收

标定不是只运行一个脚本得到一组矩阵。应保留原始数据、标定板/靶标尺寸和测量记录、相机设置、软件版本、优化参数、结果协方差/残差、温度和复测结果。

### 4.1 相机内参与畸变

针孔模型可表示为：

[
segin{bmatrix}u\v\1end{bmatrix}
=
K,[Rmid t]egin{bmatrix}X\Y\Z\1end{bmatrix}
]

其中 (K) 为内参矩阵，畸变模型需与镜头和相机模型匹配。常见径向/切向畸变并不适合所有鱼眼、全景或折反射镜头。

- 标定板需有可追溯的实际尺寸、平面度和打印/加工误差；板材翘曲会引入系统误差。
- 采集图像应覆盖全视场、不同距离和倾角，避免角点只集中在图像中心。
- 检查每张图的角点数量、覆盖度、重投影残差分布和异常帧；平均重投影误差不能掩盖边缘系统偏差。
- 对自动对焦、变焦、镜头拆装、温度变化、保护窗更换和相机支架变形建立重新标定条件。

### 4.2 双目与深度

双目标定需要内参、畸变、左右相机外参和同步采集。理想针孔近似下深度：

[
Z = rac{fB}{d}
]

其中 (f) 为焦距像素值、(B) 为基线、(d) 为视差。误差随视差误差和距离变化，不能把“1–2%@2m”写成所有双目系统通用精度。实际深度性能还取决于纹理、曝光、基线、镜头、匹配算法、遮挡、温度和标定质量。

### 4.3 相机-IMU、LiDAR-相机与手眼标定

- Kalibr可处理多相机内外参、相机-IMU空间/时间标定、多IMU标定和滚动快门参数标定。相机-IMU数据需保证时间戳质量、足够运动激励、合理曝光和已知IMU噪声参数；IMU intrinsic错误不能靠外参优化自动修复。
- Kalibr文档明确提示检查IMU时间间隔；缓存后突发发送、时间戳抖动和时钟不一致会造成标定问题。应检查原始采集时序，不只看最终估计的时间偏移。
- LiDAR-相机外参需定义坐标系方向、时间偏移、点云运动畸变补偿、相机曝光时间和靶标可观测性；不同方法适用于不同传感器与场景，不存在通用的“2–5cm/1–2px”保证。
- 手眼标定AX=XB需要足够多、方向多样且几何条件良好的机器人运动；近似共轴或运动激励不足会使解病态。需用独立姿态/目标点验证，而不是只报告训练样本残差。
- 标定结果应以带单位和坐标系定义的版本化文件保存，附传感器序列号、安装位、软件版本、日期、温度、数据集hash和复测差异。

## 5. 时间同步、时间戳与延迟

### 5.1 时钟域

必须区分：
- 相机/传感器设备时钟；
- 主机系统时钟（wall clock）；
- 单调时钟（monotonic clock）；
- PTP同步后的网络时钟；
- ROS消息时间与仿真时间。

消息到达主机的时间不等于曝光时刻。驱动应明确header.stamp对应曝光开始、曝光中点、帧结束、设备传输完成还是主机接收时间。滚动快门还存在逐行曝光时间差，单一帧时戳可能不足以准确表达每行观测时刻。

### 5.2 PTP与硬件触发

- GigE Vision相机可支持IEEE 1588 PTP，但能力依型号、固件和网卡而异；PTP启用不自动保证亚毫秒或微秒精度。
- 必须核对Grandmaster、Boundary/Transparent Clock、网卡硬件时间戳、交换机、网络拓扑、PTP profile、同步状态和时钟偏差统计。
- 多相机硬件触发可提高曝光事件对齐，但还要测量触发分配延迟、线缆差异、曝光开始延迟、相机内部延迟和帧丢失。
- PTP用于时钟同步；硬触发用于触发事件同步；两者作用不同，可组合使用。
- ROS `message_filters::TimeSynchronizer`按消息时间戳匹配消息，ApproximateTime在设定容差内匹配；它们不会校正错误的设备时间戳，也不会让传感器时钟自动同步。

### 5.3 延迟预算

端到端视觉延迟可拆分为：

[
T_{e2e}=T_{exposure}+T_{readout}+T_{transport}+T_{queue}+T_{preprocess}+T_{infer}+T_{postprocess}+T_{publish}
]

必须在真实负载下测量平均值、P95/P99、最大值、抖动、丢帧和队列深度。GStreamer官方延迟模型强调live source、多个时钟、缓冲和sink同步都会影响全局延迟；只测模型推理时间会遗漏采集、传输和排队成本。

## 6. 深度学习训练、模型交换与端侧推理

### 6.1 训练与模型格式

- PyTorch通常用于模型训练、微调和实验；部署前应固定模型代码、权重、预处理、标签映射、输入尺寸、动态shape、后处理和训练数据版本。
- ONNX是模型交换格式，不是运行时。导出后必须检查opset、动态shape、算子覆盖、量化参数、外部权重和数值差异。
- 模型部署需版本化保存：模型hash、框架版本、导出参数、预处理配置、类别表、阈值、后处理、标定参数和运行时版本。
- 评估不能只看mAP或离线准确率，还应按目标工况测量召回率、误报率、漏检风险、距离/角度/光照分桶、遮挡、运动模糊和温度漂移。

### 6.2 推理运行时与执行后端

| 运行时/后端 | 典型目标 | 重要约束 |
|---|---|---|
| ONNX Runtime CPU | 通用CPU部署 | 关注算子覆盖、线程配置、内存和目标CPU指令集 |
| ONNX Runtime CUDA EP | NVIDIA GPU | CUDA、驱动、cuDNN及ORT版本必须兼容 |
| ONNX Runtime TensorRT EP | NVIDIA GPU/Jetson等 | TensorRT EP可能将部分节点交给其他EP；必须检查partition/fallback，不能假定整图都跑在TensorRT |
| TensorRT | NVIDIA GPU/DLA（依平台和版本） | Engine构建与GPU架构、TensorRT/CUDA/驱动版本相关；序列化engine默认不能跨操作系统/平台任意移植 |
| OpenVINO | Intel CPU/GPU/NPU及支持平台 | 设备插件、驱动、OS、模型算子与精度支持依版本/硬件而异 |
| 其他NPU SDK/EP | Rockchip、Qualcomm、Huawei等设备 | 常见存在算子子集、量化格式、编译器和驱动绑定；按具体SoC SDK矩阵验证 |

ONNX Runtime官方列出CPU、CUDA、TensorRT、OpenVINO、DirectML、QNN、XNNPACK等多个Execution Provider，并明确部分EP处于preview。选型必须查具体EP状态和平台支持，不能把“ORT支持某EP”理解为每个模型都能完整下沉到该加速器。

### 6.3 TensorRT与OpenVINO兼容边界

- NVIDIA TensorRT官方支持矩阵当前列出11.4.1；序列化engine不跨Linux/Windows平台通用。默认也不能跨不同GPU架构任意移植，需启用并验证相应hardware compatibility模式，或按目标设备重新构建engine。
- TensorRT版本兼容有明确范围和前提：官方列出的跨主版本例子为TensorRT 10 version-compatible engine在TensorRT 11 runtime运行、TensorRT 8 version-compatible engine在TensorRT 10 runtime运行；不能外推为任意版本组合兼容。
- Jetson设备应优先使用对应JetPack/平台SDK提供并验证的CUDA/TensorRT组合，不应将x86主机生成的engine直接拷贝到Jetson作为默认部署方式。
- OpenVINO 2026.4官方发行说明列出CPU/GPU/NPU插件能力变化；GPU/NPU仍依赖相应驱动和系统组件，NPU操作系统支持范围与CPU/GPU不同。必须按具体硬件、驱动和OS核对系统需求。
- FP16/INT8/INT4量化会改变精度和性能；INT8需校准数据/量化感知训练或经过验证的量化流程。应对机器人安全相关输出建立精度回归和异常输入测试。

### 6.4 推理性能验收

不要使用“YOLO 15–30 FPS@Orin”这类脱离模型、输入尺寸、精度、batch、预处理和后处理的通用数字。至少记录：
- SoC/GPU/NPU型号、功耗模式、频率/温度、内存带宽和系统负载；
- OS、驱动、CUDA、TensorRT/OpenVINO/ORT版本；
- 模型hash、输入分辨率、batch、动态shape、精度、算子下沉情况；
- 预处理、推理、后处理和端到端延迟的P50/P95/P99；
- 峰值内存、功耗、温升、持续运行时钟降频和帧丢失；
- 量化前后任务指标、关键类别漏检率和置信度校准。

## 7. ROS 2视觉接入

- 常见包包括`image_transport`、`camera_info_manager`、`image_pipeline`、`vision_opencv/cv_bridge`和厂商相机驱动。必须按ROS发行版、RMW、消息类型和驱动版本锁定依赖。
- `sensor_msgs/Image`需正确填写encoding、step、height、width和data；注意stride、endianness、Bayer格式、NV12/YUYV/RGB/BGR转换及压缩传输的CPU/延迟成本。
- `sensor_msgs/CameraInfo`的内参、畸变、R/P矩阵和ROI/binning必须与当前分辨率、裁剪、缩放和相机模式一致；图像变换后不能沿用未更新的CameraInfo。
- `image_transport`提供不同图像传输插件（如compressed等）；压缩会引入编码延迟和有损/无损差异，不能默认用于对像素精度敏感的测量任务。
- 对同进程组件可评估intra-process通信、loaned message和共享内存，但需确认消息类型、RMW实现、驱动buffer生命周期和插件支持。不要把ROS 2 loaned messages描述为所有图像驱动都能直接零拷贝。
- TF坐标系需明确camera_optical_frame、camera_link、base_link和机器人世界坐标关系；光学坐标轴约定与机器人机体坐标不同，必须防止轴方向和左右手系错误。
- 多相机与图像/IMU/LiDAR融合要检查时间戳、frame_id、TF有效时间和队列策略。ApproximateTime只匹配时间戳，不修正时钟偏移。

## 8. 工业视觉应用框架

```text
设备适配层(Camera SDK/V4L2/GStreamer)
    → 采集与时间服务(触发、时钟、buffer、监控)
    → 数据规范化(Image/PointCloud/CameraInfo)
    → 算法插件(检测、测量、OCR、分割、定位)
    → 结果契约(坐标系、单位、置信度、版本、质量码)
    → 业务编排(PLC/机器人/HTTP/TCP/ROS 2)
    → 追溯服务(原图、参数、模型hash、结果、日志)
```

- 算法与设备解耦，但设备抽象层必须暴露曝光、触发、像素格式、时戳、丢帧和错误状态等关键能力，不能只抽象成一个`getImage()`。
- 结果契约要明确坐标系、单位、时间戳、目标ID、置信度、测量不确定度、质量码和模型版本。
- 产线缺陷检测需考虑光源、曝光、工件姿态、节拍、误报/漏检代价、样本漂移、追溯和人工复判流程。
- 视觉结果进入运动控制前应做有效性、时效性、坐标变换和置信度检查；过期帧、无效TF或低质量结果应触发受控降级，而不是继续输出旧目标位置。

### 11.2 PTP 时钟同步验收不能只看“已启用”

Basler公开文档说明其GigE相机PTP采用IEEE 1588-2008（PTPv2），同步精度高度依赖网络硬件与配置；设备上电后PTP默认关闭，需显式启用并等待时钟状态收敛。其文档建议读取设备PTP状态与相对Grandmaster的offset，并在指定时间窗口内验证偏差是否持续低于应用阈值。

因此，工程验收至少应记录：

- Grandmaster身份、时钟是否锁定UTC/TAI或仅在局部网络内使用任意epoch；
- PTP profile、E2E/P2P机制、交换机/网卡/边界时钟能力、拓扑和固件；
- 每台相机的PTP状态、offset样本序列、最大绝对偏差和观测窗口；
- 曝光时刻与设备timestamp的对应关系、触发输入到曝光的延迟、触发抖动及丢触发；
- PTP时钟同步与硬件触发分别验证，不能用“PTP锁定”替代曝光事件同步验收。

Basler的参数名和示例阈值属于其产品文档，不能直接推广到其他相机厂商；目标系统阈值必须由运动速度、视场、测量误差预算和融合算法反推。

### 11.3 OpenCV 5.0 迁移检查补充

截至本次复核，OpenCV上游将4.x描述为稳定维护分支，5.x也已进入稳定分支状态。5.0最低要求C++17，并移除旧C API；G-API和Classic ML模块移至opencv_contrib，原calib3d拆分为geometry、calib、stereo及点云相关模块。项目迁移不能只修改版本号：

- 固定opencv与opencv_contrib相互匹配的tag/commit，核对模块移动、头文件、命名空间和Java/Python绑定变化；
- 扫描旧C API、旧Features2D/Objdetect路径、G-API/ML模块依赖及外部第三方算法；
- 重建并运行标定、立体匹配、几何估计、点云处理和DNN回归数据集；
- 重新审查第三方模块、算法实现、模型、codec和样例数据的独立许可证；主仓库LICENSE不能代替整套发行物SBOM。

### 11.4 TensorRT 11.4.1 与 Jetson/ORT 的版本边界

NVIDIA TensorRT 11.4.1公开支持矩阵与发行说明给出以下重要限制：

- TensorRT 11.4.1不支持JetPack 6.x上的Jetson Orin部署；该平台应使用其JetPack版本支持的TensorRT 10.x组合，而不是强行替换为11.4.1。
- TensorRT 11.4.1的JetPack支持列为JetPack 7.2.2及以后对应平台包；必须按具体Jetson型号、JetPack、CUDA、驱动和TensorRT安装包核对。
- TensorRT序列化engine默认不跨Linux/Windows等平台通用，也默认不跨GPU架构通用。版本兼容、硬件兼容和跨平台构建是不同选项，各自有前提和性能代价。
- 11.4.1文档明确硬件兼容模式不支持NVIDIA JetPack；因此不能把桌面GPU上构建的hardware-compatible engine视为Jetson通用部署产物。
- TensorRT官方支持矩阵列出跨主版本兼容的特定组合：启用版本兼容的TensorRT 10 engine可在TensorRT 11 runtime运行，以及TensorRT 8 version-compatible engine可在TensorRT 10 runtime运行；不能外推为任意跨主版本组合兼容。

另一个容易混淆的边界是ONNX Runtime TensorRT Execution Provider。其官方兼容表目前列出的主线/ORT 1.22组合对应TensorRT 10.9及CUDA 12.0–12.8；这不能证明ORT TensorRT EP已支持TensorRT 11.4.1。若采用ORT+TensorRT，必须锁定ORT版本、EP构建来源、TensorRT/CUDA/驱动版本，并检查TensorRT子图划分和CUDA/CPU fallback；不能仅凭TensorRT独立支持矩阵推断ORT EP兼容。

### 11.5 OpenVINO 2026.4 NPU 支持与文档差异

OpenVINO 2026.4发行说明记录NPU新增Ubuntu 26.04支持，并将NPU动态shape标注为preview/experimental；目前限于视觉模型和有界动态维度，已验证的示例包括超分辨率模型。NPU设备文档进一步列出NPU40XX平台、特定Windows/Linux NPU驱动版本和Compiler-In-Plugin路径等条件。

但同一版本的System Requirements页面所列NPU操作系统范围仍显示Ubuntu 24.04（preview）、Ubuntu 22.04和Windows 11，未同步列出Ubuntu 26.04。故两处官方页面存在版本/页面更新时间上的不一致。部署决策应按实际下载包、驱动版本、设备代际和当前release notes复核，并向Intel支持渠道确认目标组合；不得只凭release note一行文字宣称所有Ubuntu 26.04/NPU组合均已正式支持。

动态shape也不能理解为任意模型、任意动态维度均可在NPU运行：当前文档限定有界shape，且功能为预览状态。生产项目应固定输入shape或验证边界覆盖、重新编译、内存峰值、延迟和数值精度，并保留CPU/GPU fallback方案。
