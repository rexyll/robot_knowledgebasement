# 云平台与 IoT 通信

> 本章说明机器人与云端/边缘平台之间的设备接入、遥测、事件、远程命令、文件传输、OTA 和运维链路。协议选择必须服从实时性、可用性、弱网、网络边界、安全、成本和产品部署方式；下文给出常见模式，不构成所有机器人必须采用的固定架构。

## 1. 端云职责与典型架构

端侧负责本地运动控制、安全相关功能、断网自治、命令校验和必要的数据缓存。云端负责设备身份与注册、车队管理、任务编排、遥测存储、告警、用户/租户权限、OTA编排和运维审计。**急停、碰撞保护、速度/力限制和实时闭环不得依赖公网往返或云服务可用性。** 远程命令应作为有时效、可撤销、需端侧状态机确认的业务请求，而不是绕过本地安全链的执行器直控。

常见分层：
- 设备层：机器人控制器、边缘计算机、传感器、执行器与本地安全控制。
- 边缘层：协议适配、缓存、身份凭据、断网自治、局域网设备发现与局部服务。
- 接入层：MQTT Broker、HTTPS API、WebSocket/WSS 网关或专用媒体服务。
- 平台层：设备目录、命令/任务服务、消息处理、时序/对象存储、告警与审计。
- 集成层：WMS/MES/ERP、工单系统、数字孪生、第三方应用和运维门户。

## 2. 协议选型

| 协议/机制 | 常见用途 | 主要权衡 |
|---|---|---|
| MQTT 3.1.1/5.0 | 遥测、事件、异步命令、设备状态 | Broker与会话状态、QoS语义、主题权限、消息积压和弱网策略 |
| HTTPS/REST | 注册、配置、文件/OTA下载、管理API | 请求响应易调试；大文件需断点续传、校验与授权设计 |
| WebSocket/WSS | 浏览器实时状态、双向应用消息 | 适合交互通道；不等同于视频媒体传输方案 |
| WebRTC/专用媒体协议 | 实时音视频、远程操作媒体链路 | NAT穿透、带宽、时延、媒体加密和接管权限需单独设计 |
| DDS/ROS 2 middleware | 机器人局域网内数据分发、实时/发现需求 | QoS、发现机制、网络拓扑、防火墙和跨网段配置复杂度需评估 |
| gRPC | 服务间RPC、流式API | 强类型IDL与代码生成；网络代理/版本兼容需设计 |
| CoAP/LwM2M | 受限设备管理与轻量遥测 | UDP/NAT/可靠性和云平台支持情况依实现而异 |
| Zenoh/其他专用传输 | 跨网络数据/查询/发布订阅 | 依赖具体实现、路由、安全和部署测试，不能仅凭协议名认定适用 |

不存在“DDS绝不出车”或“所有车云都必须MQTT”的通用铁律。常见架构会让本地实时数据留在ROS 2/DDS域，云端遥测与管理走MQTT/HTTPS；但是否跨边界桥接、使用Zenoh或其他协议，须按时延、带宽、NAT、防火墙、发现、弱网、安全和运维能力决定。视频连续媒体通常走WebRTC或专用媒体链路，MQTT更适合信令、控制、状态和媒体会话元数据。

## 3. MQTT QoS、会话与消息语义

OASIS MQTT 5.0定义的QoS是协议交付等级：
- **QoS 0：At most once**，最多一次；不等待协议确认，适合允许丢失的高频遥测或可由新状态覆盖的数据。
- **QoS 1：At least once**，至少一次；发送方未收到PUBACK时可能重发，因此订阅端必须容忍重复，业务处理需使用事件ID/命令ID实现幂等。
- **QoS 2：Exactly once**，指MQTT协议交付流程的恰好一次语义；不等于跨Broker、数据库、业务服务、机器人执行器和外部设备的分布式业务事务恰好执行一次。跨系统仍需事务边界、幂等键、状态机、去重持久化和结果确认。

QoS不是“越高越好”，也没有通用的“QoS 2官方不推荐”规则。按消息丢失后果、重复处理代价、链路质量、客户端/Broker实现、持久化能力和资源开销选择。AWS IoT Core是具体服务实现，只支持QoS 0/1；这是服务能力限制，不是MQTT标准取消QoS 2。[OASIS MQTT 5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)；[AWS IoT Core MQTT支持](https://docs.aws.amazon.com/iot/latest/developerguide/mqtt.html)。

MQTT 5.0提供Session Expiry、Message Expiry、Receive Maximum、Reason Code等会话、过期和流控机制，但不保证消息永不丢失，也不替代设备侧持久队列、磁盘空间/配额管理、断电恢复、重连退避、死信/补偿和端到端确认。Broker持久会话有容量上限、过期策略和服务实现差异；必须阅读目标Broker的配额与持久化说明，并实测断网时长、积压量、恢复速率和消息过期行为。[OASIS MQTT 5.0规范](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)。

Retained消息适合为新订阅者提供某主题最近一次保留的状态，不是可靠心跳或实时在线证明。可结合Last Will and Testament（LWT）、Keep Alive、Broker连接事件、状态时间戳、序列号和Message Expiry；消费端应判断数据新鲜度，不能把历史retained状态直接当成当前在线。

MQTT固定头最少为2字节，但完整报文还可能包含Remaining Length、Topic Name、Packet Identifier、属性、载荷等；带宽估算必须按真实消息大小、发布频率、QoS、TLS/TCP/IP开销和重传测量，不能把“2字节头”当成总开销。

## 4. 主题树与消息契约示例

以下仅为可调整的命名示例：
```
robot/v1/{tenant}/{site}/{robot_id}/state
robot/v1/{tenant}/{site}/{robot_id}/telemetry/{stream}
robot/v1/{tenant}/{site}/{robot_id}/event/{event_type}
robot/v1/{tenant}/{site}/{robot_id}/command/{command_type}
robot/v1/{tenant}/{site}/{robot_id}/ota/{job_id}/status
```

消息契约至少定义：schema版本、消息ID、设备ID、租户/站点、产生时间与时钟来源、序列号、单位/坐标系、质量标记、过期时间、追踪ID、命令目标状态、超时、确认与错误码。命令应具有唯一ID、幂等键、有效期、授权主体、允许状态前置条件和结果状态；端侧需拒绝过期、重复、越权或当前状态不允许的命令。事件和状态消息应区分“事实发生”与“当前快照”。

1–5 Hz可作为某些低带宽状态遥测的初始实验值，不是通用频率。频率应由控制/运维用途、变化速率、网络预算、数据保留成本和故障诊断价值决定；高频原始传感器数据通常在端侧筛选、聚合或按需上传。

## 5. 身份认证、授权与传输安全

TLS保护传输通道，不是QoS的一部分，也不能替代身份认证和授权。至少区分：
1. **身份认证**：确认连接方是谁，可用每设备X.509证书、受控短期令牌或适合目标平台的身份机制。
2. **授权**：决定身份能读写哪些租户、站点、设备和主题；实施最小权限ACL，并限制通配符订阅/发布。
3. **凭据生命周期**：安全注入、轮换、吊销、设备报废、密钥泄露响应和审计。
4. **连接约束**：按产品能力绑定clientId与设备身份，避免多个设备共享长期凭据；设置连接/发布速率、消息大小、订阅数量和会话配额。
5. **App接入**：若移动App直连Broker，必须使用用户认证后签发的短时效/可撤销凭据，按租户、设备和操作范围授权，并进行速率限制与审计。App不得持有设备长期私钥或通用Broker管理员凭据。也可由业务API代理App访问。

设备命令链应校验签名/来源、权限、时效、重放、状态前置条件和审计关联；OTA需独立校验固件签名、目标型号/硬件版本、版本回滚策略、分批发布、失败恢复和升级结果。不能仅因使用TLS或MQTT QoS就宣称端到端安全。

## 6. Broker与客户端项目：按版本核验许可证和能力

| 项目 | 适合评估的角色 | 需特别核验 |
|---|---|---|
| Eclipse Mosquitto | 轻量自建MQTT Broker | 目标版本配置、持久化、插件、ACL、监控、集群/高可用外部方案与压测；上游LICENSE声明EPL-2.0 OR BSD-3-Clause |
| EMQX | 功能较丰富的Broker/集群方案 | **5.9.0及以后采用BSL 1.1源码可用许可**；单节点生产附加授权有条件，集群及托管/嵌入第三方产品等用途需按许可取得商业授权；5.8.x及更早Apache 2.0社区版本继续原许可 |
| Eclipse Paho Python | Python MQTT客户端 | v2.0有breaking API change；上游项目LICENSE为EPL-2.0 OR BSD-3-Clause；核对目标tag、API版本和会话持久化能力 |

来源：[EMQX许可FAQ](https://www.emqx.com/zh/content/license-faq)、[Mosquitto LICENSE](https://github.com/eclipse-mosquitto/mosquitto/blob/master/LICENSE.txt)、[Paho Python仓库](https://github.com/eclipse-paho/paho.mqtt.python)。许可证须针对实际使用的发行包、tag/commit、依赖、插件、NOTICE和分发/托管方式做审查；不能只依据当前main分支或产品宣传页推断旧版本。

不设置“Mosquitto是首选”“单机万级连接”或“超过某连接数必须换EMQX”的通用结论。容量与可用性取决于CPU/内存、TLS、消息大小/速率、QoS、订阅扇出、持久会话、磁盘写入、网络、插件、集群拓扑、重连风暴和运维目标。选型必须用目标硬件和目标配置压测并保留可复现脚本、指标与故障注入结果。

## 7. 可靠性、可观测性与验收

- 断网：设备侧有界持久队列，明确满载时丢弃/覆盖/降采样策略；恢复后限速补报，避免重连风暴。
- 命令：命令ID/幂等键、过期时间、端侧状态机、执行结果和超时补偿；“已投递”不等于“已执行”。
- 时间：明确UTC时间戳、单调时钟、NTP/PTP/GNSS来源和时钟失准处理；不可把未同步时钟当作精确事件顺序。
- 数据：Schema版本兼容、单位/坐标系、质量位、采样频率、保留期限、隐私分级和删除策略。
- 监控：连接数、连接/认证失败、重连速率、发布/订阅吞吐、消息延迟、丢弃/过期、积压、磁盘、CPU/内存、Broker队列和租户配额。
- 测试：断网/弱网/高延迟/丢包、Broker重启、客户端断电、证书吊销、重复/乱序/过期命令、时钟偏移、磁盘满、消息洪峰、重连风暴、权限越界和OTA失败恢复。
- 验收：定义端到端延迟分位数、消息丢失/重复容忍度、命令执行成功率、恢复时间、离线缓存容量、最大设备规模、故障隔离和审计完整性；阈值由产品ODD、SLA和风险分析给出，不套用通用数字。

## 9. 项目实例边界

既有清洁机器人项目中的`ros_iot`、Node.js/aedes Broker和App直连仅作为某项目实现线索，不应外推为通用推荐架构。正式复用前应补充其准确版本、部署拓扑、身份与ACL配置、消息契约、持久化、负载、断网恢复、许可证和实际测试证据。

本文是协议与架构层知识，不是特定云平台、Broker、机器人产品或安全架构的验收报告。尚需对目标Broker具体版本、云服务配额、设备端库版本、生产部署拓扑、证书生命周期、租户隔离、端到端命令链、OTA和弱网恢复进行逐项验证；任何容量、SLA、安全等级和法规符合性结论都必须绑定具体配置与测试证据。
