# 多机调度流程

> 本页以多台工业移动机器人共享场地、设施和任务资源为主要示例，描述业务任务进入、车队分配、交通协调、执行监控与异常恢复的端到端流程。系统能力见 [[调度系统RMS]]，算法见 [[多机协同与调度算法]]。本页不是VDA 5050实施规范，也不是通用机器人交通安全规范；实际设计必须绑定机器人类型、运行设计域（ODD）、场地拓扑、混行人员、设施接口、网络架构和风险评估。

## 1. 系统边界与控制层次

多机系统至少需要区分以下职责，不能将它们统称为“调度算法”：

| 层次 | 主要职责 | 不应替代的能力 |
|---|---|---|
| 业务/WMS/WES/MES | 产生订单、工单、物料与业务约束，确认业务结果 | 不负责实时车辆避障或安全停止 |
| 车队任务管理（RMS/Fleet Control） | 任务拆解、优先级、车辆选择、任务状态与资源协调 | 不替代车端定位、局部避障和独立安全系统 |
| 交通管理/资源协调 | 对共享路段、交叉口、窄道、门、电梯、充电位等资源进行授权和冲突协调 | 不应以普通数据库锁直接代替现场安全防护 |
| 车端导航与任务执行 | 接收授权路线/区域，完成定位、规划、控制、动作与状态反馈 | 不应自行假设未获授权的共享资源可用 |
| 独立安全相关控制 | 按风险评估处理人员/设备保护、急停、速度/方向监控和重新启动条件 | 不得依赖RMS网络可用性或普通任务状态来承担安全功能 |
| 设施控制 | 门、升降机、输送线、自动充电等设施的状态与互锁接口 | 业务“预约成功”不等于设施安全条件已满足 |

部署形态可以是集中式RMS、分层控制、区域控制器或混合架构。选型应考虑网络分区、故障域、车队规模、实时性、现场维护和单点故障影响；不能仅凭机器人数量选择某种架构。

## 2. 端到端任务流程

### 2.1 任务接入与校验

业务系统提交任务后，RMS应校验：

- 任务ID、来源身份、权限、幂等键、有效期和取消/修改语义；
- 起终点、路网/地图/语义版本、区域开放状态和设施可达性；
- 货物、载荷、尺寸、夹具、机器人能力和工艺动作要求；
- 优先级、截止时间、依赖任务、交接点和业务确认条件；
- 任务是否重复、冲突、过期，或与当前车辆/设施状态不兼容。

任务拆解可形成有向无环依赖图（DAG），例如取货、运输、交接、放货等子任务。拆解必须保留父子任务关联、取消传播、部分完成和补偿处理语义。任务入池前应完成业务字段与物理点位/资源ID映射，不得只依赖显示名称。

### 2.2 候选车辆筛选与任务分配

先进行硬约束筛选，再进行软目标优化。

**硬约束**通常包括机器人能力/载荷匹配、区域许可、尺寸与通道限制、当前故障/维护状态、地图版本兼容、能源可行性、任务互斥和设施约束。

**软目标**可以包括预计完成时间、空驶距离、队列等待、任务优先级、能耗、车队负载均衡、拥堵外部性和后续任务衔接。目标函数和权重须由运营目标及数据验证确定，不能将某一评分公式视为行业通用规则。

分配方式可采用单任务即时分配、批量匹配、滚动时域优化或事件触发重算。匈牙利算法、贪心、MILP、CP-SAT、车辆路径问题（VRP）等只是可选建模/求解方法；任务分配不等于交通冲突解决。求解时间、重算周期、候选车预测窗口和算法切换条件应通过目标车队规模、任务分布、硬件和现场负载测试确定。

车辆预计完成当前任务后可参与候选集，但预测必须带有置信度/有效期，并考虑动作持续时间、排队、充电、交通拥堵、设施等待与故障概率。不能将“60秒内完成”一类固定窗口推广为通用标准。

### 2.3 交通资源预约与路径授权

将场地表示为适合本项目的拓扑/资源模型，例如路段、节点、交叉口、单向通道、窄道、区域、门、电梯和充电位。对每项资源明确：

- 资源唯一标识、空间边界、方向/通行规则和适用机器人类别；
- 容量、互斥关系、进入/退出条件、占用确认和释放条件；
- 预约时间窗、预计行驶时间、保护裕量和超时策略；
- 预约撤销、车辆失联、定位不可信、人工接管和紧急处置规则；
- 资源状态的权威来源、版本、时钟域和审计记录。

可采用中央预约、令牌/区段授权、时空预约表、区域许可或分层混合策略。资源授权应与车辆实际位置和执行进度闭环：下发授权不等于资源已被占用，车辆离开也不应仅凭超时自动推断资源已释放。对于定位丢失或车辆失联，需按风险策略将相关资源置为未知/受限状态并进行现场确认或受控恢复，防止“幽灵车辆”造成错误放行。

路径授权与车端局部避障需明确边界。中央系统负责共享资源和车队级冲突；车端负责其ODD内的实时感知、局部规划和执行。车端发现障碍、路径不可行或授权失效时，应反馈并进入定义好的等待/暂停/重新规划流程，不得擅自穿越未授权资源。

### 2.4 执行、状态与业务确认

运行中至少关联任务ID、机器人ID、订单/路线版本、地图/配置版本、当前资源授权、动作ID和时间戳。监控数据应区分：

- 业务任务状态：待分配、已分配、执行中、部分完成、完成、取消、失败；
- 机器人运行状态：空闲、执行、等待、充电、维护、故障、失联等；
- 交通资源状态：空闲、预约、占用、受限、未知/待核查；
- 设施状态：可用、预约、运行、故障、人工模式或安全互锁未满足。

消息频率、心跳周期、状态刷新、告警延迟和超时应依据链路时延、带宽、数据新鲜度需求与失效检测目标确定，不使用固定的“1–2Hz状态回报”作为通用要求。应监测数据年龄、序列/版本、乱序、重复、丢失和状态跳变。

业务完成必须由任务定义的动作证据确认，例如货物交接传感器、工位握手、称重/视觉检查或设施返回状态。车辆到达目的点不等于装卸、清扫、充电或生产工艺已经完成。对于非幂等动作，需使用动作ID、状态持久化、重复请求保护和故障恢复对账，避免断线重连后重复执行。

### 2.5 任务取消、抢占与重派

任务优先级变化不能简单等同于“立即中断当前车”。执行取消/抢占前应判断：

- 当前动作是否处于不可中断阶段（载荷悬空、货叉伸出、正在过门/电梯、装卸中等）；
- 当前车辆是否占用单车道、交叉口、门/电梯或其他共享资源；
- 任务是否可暂停、可回滚、可安全交接或必须完成当前原子步骤；
- 原任务部分完成的业务状态、货物所有权和补偿动作；
- 资源释放、路径授权撤销与新任务生效的先后关系。

车辆故障后的任务重派要先确定载荷/货物状态、车辆位置、占用资源和任务检查点。只有在业务和物理状态确认一致后才能创建接续任务；禁止仅因心跳超时就把任务无条件分配给另一台车。

## 3. 死锁、拥堵与异常恢复

### 3.1 死锁与活锁

申请等待图中的环可作为死锁检测线索，但不代表所有环都能安全地通过“强制解锁”消除。应结合资源容量、车辆实际位置、路径可达性、等待依赖和时间进展判断。

恢复策略按现场拓扑和风险选择：停止新任务进入、撤销尚未执行的预约、重新规划未进入区域的路线、按授权顺序释放资源、选择经过验证的退让点，或请求现场人工处理。任何倒车、旋转、脱困、清空预约或重新分配动作，都必须确认空间可行性、载荷稳定、人员/设备状态和安全许可；不得在资源实际占用未知时强行释放互斥锁。

应记录死锁检测原因、资源等待链、车辆状态快照、恢复决策、人工介入和恢复后复盘结果。对周期性拥堵还应分析拓扑瓶颈、任务潮汐、资源容量、路径偏好和设施服务时间，而不只调低区域车辆密度阈值。

### 3.2 异常处理矩阵

| 异常 | 检测与确认 | 处置原则 |
|---|---|---|
| 机器人故障/维护 | 车端诊断、状态失效、人工确认 | 标记车辆不可分配；确认载荷和占用资源后再接续任务 |
| 定位丢失/位置跳变 | 位姿质量、数据年龄、地图/坐标版本 | 相关区域资源转未知或受限；禁止按旧位置继续发放冲突授权 |
| 路径阻塞/拥堵 | 车端障碍反馈、资源等待和进展停滞 | 等待、改道、入口限流或调整任务释放节奏；阈值需按现场验证 |
| 交通死锁/活锁 | 等待图、无进展检测、周期性轨迹 | 冻结相关资源与新进入流量，执行经过验证的恢复策略 |
| 电量/能源不足 | 电池状态、任务能耗模型、充电设施状态 | 按安全余量和任务阶段安排回充或交接；不得用固定“1.5倍/20%”通用阈值 |
| 门/电梯/输送线异常 | 设施权威状态、握手/互锁反馈和超时 | 暂停依赖该设施的任务，保留资源状态并通知运营人员 |
| 网络/云端中断 | 多层链路监测、消息年龄、连接状态 | 根据车端已缓存授权、任务阶段、ODD和风险策略选择继续、暂停、受控停止或人工接管；不得默认完成当前任务 |
| RMS重启/主备切换 | 持久化任务、租约、序列号和资源快照 | 恢复后先对账机器人/设施/资源真实状态，再开放新任务；避免重复授权 |
| 业务系统重复/乱序命令 | 幂等键、任务版本、序列和状态机校验 | 拒绝过期/冲突请求，保留可审计响应，不重复执行物理动作 |

### 3.3 断网与降级策略

断网行为必须按控制层分开设计：

- 业务系统到RMS中断：车队可能继续执行已确认任务，也可能暂停新任务；由业务一致性和运营策略决定。
- RMS到机器人中断：车端只能依据仍有效且已缓存的授权、任务边界和安全策略运行；不能把“本地自治”理解为无限制继续执行。
- 机器人到设施中断：依赖设施握手的动作应按接口失效策略等待或停止，不得推断门已开、电梯已到或充电已完成。
- 安全相关链路异常：由独立安全设计定义安全状态和复位条件，不能依赖普通MQTT心跳或云端指令。

恢复通信后，应进行任务、动作、资源占用、地图/配置版本和设施状态对账。对状态不确定的车辆或资源先隔离/限制，再恢复车队运行。

## 4. 多楼层、共享设施与充电

多楼层系统需为电梯、自动门、升降机、输送线和跨区域通道建立显式资源状态机与接口契约。典型流程包括申请资源、排队/预约、设施确认、进入许可、车辆进入、运行/跨层、退出确认、资源释放和异常回退。每一步需定义超时、取消、人工模式、门状态矛盾、人员阻挡、车辆未完全进入/离开及通信中断时的处理。

设施控制接口的“开门/选层成功”只代表业务命令被接受或设备状态反馈，不能替代光幕、门锁、急停等安全功能。设施安全互锁及人员保护由适用的安全系统负责，RMS只能消费其授权/状态接口。

充电策略需要结合电池化学体系、BMS限制、充电曲线、任务需求、充电桩兼容性、排队、热管理和运营班次设计。可采用机会充电、任务间充电或集中充电，但充电阈值、预计能耗裕量、充电位分配和电池健康约束必须由电池供应商资料及目标系统实测确定。

## 5. VDA 5050 接口边界（版本锁定）

截至本次审查，VDA官方页面列出的当前推荐版本为VDA 5050 3.0.0（2026年3月）。项目引用时应锁定规范PDF、JSON Schema、实现版本和互操作测试记录。

- VDA 5050定义车队控制与移动机器人之间的任务/状态通信结构，包括order、instantActions、state、connection、factsheet等Topic；Topic方向和必选/可选属性应以锁定版本规范为准。
- 3.0.0增加对自由导航移动机器人能力的支持，包括区域（zone）概念和路径共享（path sharing）等机制；具体项目需核对规范章节、消息字段、设备支持和测试结果。
- 规范中的order可包含节点/边段及释放状态；车队控制持有完整路网并决定下发给特定机器人的路径部分。采用区域式自由导航时，机器人可在获准区域内自主规划，但仍需按项目约定共享路径/交通信息。
- instantActions用于特定即时动作，不能与当前order中的动作语义冲突。业务取消、暂停、恢复、动作终止和物理状态对账仍需在系统设计中明确定义。
- VDA 5050是通信接口，不自动提供任务分配优化、共享资源预约算法、死锁消解、网络安全配置、功能安全或现场验收。协议兼容不等于不同厂商机器人在同一场地已实现安全互操作。
- MQTT QoS、连接状态和消息送达不能替代业务事务完成、车端执行确认、资源占用确认或安全停止。

混合车队项目应为每家机器人建立factsheet/能力映射、动作语义、地图/坐标、区域/边约束、状态码、异常处理和协议版本矩阵，并执行订单生命周期、暂停/恢复、断线重连、路径更新、设施动作、异常码和并发交通场景的互操作测试。

## 6. KPI、容量与验证

车队KPI必须有定义、分母、时间窗口、过滤规则和原始数据来源。至少区分：

| 维度 | 指标示例 | 统计/验证边界 |
|---|---|---|
| 业务交付 | 任务完成率、按时交付率、取消/重派率 | 明确任务类型、取消原因、部分完成和业务确认条件 |
| 车队效率 | 吞吐量、空驶率、利用率、等待时间 | 区分执行、等待、充电、维护、设施等待和人工接管时间 |
| 交通质量 | 区域占用、排队时延、阻塞时长、死锁/活锁事件 | 按拓扑区域和时间窗口分析，不用单一车辆密度阈值代表拥堵 |
| 可靠性 | 故障率、MTTR、任务恢复时间、人工介入率 | 记录故障分类、暴露时间、样本量和恢复口径 |
| 实时性 | 状态数据年龄、分配/规划时延、消息延迟和抖动 | 区分平均值、分位数、最大值和丢失/过期数据 |
| 能源 | 单任务能耗、充电等待、能源可用率 | 绑定载荷、路线、地面、温度、电池状态和充电策略 |
| 安全 | 保护停止、近失事件、授权违规、设施互锁异常 | 不得用任务成功率或普通日志替代安全验证 |

容量规划应使用真实任务到达分布、服务时间、交通瓶颈、设施能力、网络负载和故障恢复模型，并通过仿真、压力测试及现场分阶段验证。不能将固定的1–5秒分配周期、1–2Hz状态频率、P95任务时长×2等待阈值、区域车辆数/m²阈值、3→5→10台扩容步骤或特定电量公式写成行业通用验收标准。

建议验证层次：

1. 单元测试：任务状态机、幂等、优先级、资源预约和释放条件。
2. 模型/仿真测试：交通拓扑、交叉口、窄道、单向通道、设施等待、拥堵、死锁/活锁与网络分区。
3. 接口测试：WMS/WES、RMS、机器人、设施、VDA 5050 JSON Schema和协议版本。
4. 故障注入：车辆失联、定位漂移、设施状态矛盾、RMS重启、消息重复/乱序、资源状态未知。
5. 现场验证：逐步扩大车队规模和任务负载，记录工况、地图/软件版本、机器人型号、载荷、原始轨迹、事件日志及人工干预。
6. 安全验证：由适用风险评估和安全工程计划定义，独立验证保护装置、停止行为、设施互锁和重新启动条件。

灰度扩容可以作为风险控制手段，但每个阶段的车辆数、运行时间、负载和退出条件必须由场地容量、风险分析和统计置信度制定，而非固定台数阶梯。
