# 云端协同与 OTA 流程

> 车队软件持续演进的生命线：遥测上报 → 远程诊断 → 版本构建 → 灰度升级 → 回滚兜底。OTA 失败的最大风险=变砖，流程设计的第一原则是**永远留一条能启动的路**。

## 端云协同全景（→ [[云平台与IoT通信]]）

```
车端: MQTT Client + OTA Agent + 本地缓存/断点续传
云端: 设备影子(Desired/Reported 双状态) + 版本仓库 + 灰度引擎 + 监控
安全: TLS + 签名验签(RSA/ECDSA) + SHA256 完整性 → [[标准与法规]]
```

## OTA 标准流程

```
1. 版本构建
   CI 产物: 固件(bin)+ROS2 软件包+配置+模型文件, 全量+差分包(bsdiff/xdelta)
   签名+生成 manifest(版本/依赖/SHA256/兼容硬件列表)

2. 策略制定
   灰度: 1 台试制车 → 5% → 30% → 100%; 分站点/分批次
   前置条件: 电量 >50% / 在充电位 / 空闲时段(非任务高峰)

3. 下发
   设备影子更新 desired_version → MQTT ota/notify → 车端 OTA Agent 拉取
   下载: HTTP 断点续传, 校验 SHA256 → [[云平台与IoT通信]]

4. 安装(A/B 双分区, 核心设计)
   写入备用分区 → 标记 boot flag → 重启切换
   新分区自检(服务全起+传感器在线+定位有效, 3-10min) → 确认成功

5. 确认与回滚
   自检失败/运行期崩溃率超阈值 → 自动回滚旧分区(看门狗计数器)
   回滚事件上报云端 → 停止灰度扩散

6. 收尾
   版本对账(云端 vs 车端版本一致性巡检) → 报表
```

## 分组件升级差异

| 组件 | 方式 | 风险与对策 |
|---|---|---|
| MCU 固件（底盘/BMS） | 主控经串口/CAN 引导烧写（IAP/双 bank） | 烧写中断电=变砖 → 只在充电位升级+CRC 双确认 |
| ROS2 应用 | A/B 分区或容器镜像层 | 契约兼容检查（接口包版本）→ [[ROS与ROS2]] |
| 地图/路网 | 增量覆盖+版本回滚 | 语义配置（围栏）与地图版本强绑定 → [[建图流程]] |
| DL 模型 | 文件热替换+在线 A/B | 精度回归集验证 → [[视觉感知算法]] |
| 配置参数 | 影子即时生效/重启生效 | 参数 schema 校验（防手滑） |

## 远程诊断闭环（OTA 的上游）

```
遥测(错误码/崩溃日志/性能指标) → 云端聚合分析(告警规则) → 工单
→ 远程日志拉取(按需) → 远程复现(视频流+状态注入) → 修复 → OTA 推送
常见: 磁盘水位/CPU 过热/定位质量退化趋势 → 预测性维护
```

## 契约与版本治理（大型车队的关键工程）

- 接口契约版本化：IDL/protobuf + SHA256 指纹（[[项目-amr]] 的 CONTRACT_IDL 实践）
- 兼容矩阵：车端组件版本组合白名单，混合版本车队允许存在（灰度期常态）
- 回滚演练：每季度模拟升级失败→自动回滚（流程可靠性本身也要测）

## 安全合规要点（→ [[标准与法规]]）

- 升级须可审计（谁/何时/哪个版本/结果），保留 ≥1 年
- 签名私钥 HSM 保管；防降级攻击（版本单调计数）
- 车规参考 UN R156（软件升级管理体系 SUMS），机器人行业正借鉴

## 细节加深（V2）
- **灰度分组维度**：按「站点→批次→机型→硬件版本」四级分组，每级可独立暂停——OTA 事故的止损速度取决于分组粒度。
- **升级窗口与业务窗口解耦**：作业班表之外才有升级资格（电量>50% 且在桩）——调度器要有「勿扰模式」。
