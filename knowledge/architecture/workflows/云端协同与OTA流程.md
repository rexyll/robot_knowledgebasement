# 云端协同与 OTA 流程

> 本文是机器人产品云端设备管理、远程运维和软件/固件更新的工程流程参考，不是可直接部署的产品方案。具体设备身份、更新权限、运行安全状态、兼容矩阵、恢复机制和发布门槛，必须由产品架构、威胁模型、风险评估、硬件启动链和现场运维条件确定。**下载完成、验签通过、安装完成、启动成功、业务健康和安全功能有效是不同状态，不得合并为一个“升级成功”结论。**

## 1. 范围、参与方与责任边界

端云协同至少涉及以下角色，实际部署可以合并或拆分，但必须明确责任和信任边界：

| 角色 | 主要职责 | 不应默认承担的职责 |
|---|---|---|
| 设备/机器人 | 持有设备身份；报告状态；验证更新授权与制品；按本地策略安装、启动验证和恢复 | 不因云端下发命令而绕过本地安全联锁或运行状态检查 |
| 设备管理服务 | 设备注册、身份/证书状态、期望配置、设备分组、命令授权、状态对账 | 不直接替代车端实时控制、安全控制或独立保护回路 |
| 制品仓库/发布系统 | 保存不可变制品、manifest、签名元数据、兼容性信息和发布记录 | 不把“文件可下载”当作制品可信或设备适配 |
| OTA 编排器 | 选择目标设备、创建发布批次、推进阶段、暂停/撤销和汇总结果 | 不应绕过设备侧验证；不应把全局期望版本强制覆盖本地安全约束 |
| 身份与密钥基础设施 | 设备凭据签发/轮换/撤销；发布密钥分权、保护、轮换和吊销 | 不将设备认证密钥、制品签名密钥和传输加密密钥混为一类 |
| 运维/安全人员 | 审批维护窗口、处理异常、授权恢复、保全证据 | 不以远程操作替代现场能源隔离、危险区域管控或法定安全作业 |

逻辑链路示意：

```
研发构建与测试
  -> 制品登记 / SBOM / 兼容性声明
  -> 发布审批与签名元数据
  -> OTA 编排 / 设备分组 / 命令授权
  -> TLS 传输 / 设备侧验证
  -> 本地安全前置检查 / 安装 / 启动验证
  -> 业务健康检查 / 结果上报
  -> 云端与设备状态对账 / 审计归档
```

传输加密（例如 TLS）保护链路，不等于制品签名；哈希校验可检测内容变化，但单独使用 SHA-256 不能证明制品来源可信；制品签名也不能单独证明目标硬件兼容、运行安全或功能安全有效。

## 2. 设备身份、访问控制与命令安全

### 2.1 设备身份生命周期

- 为设备或受管理的控制单元建立唯一、可追溯的身份；身份粒度应与产品的 ECU/MCU/计算单元边界和权限模型一致。
- 设备注册流程应验证制造/部署授权，防止仅凭可猜测序列号或网络可达性完成注册。
- 设备凭据应有签发、激活、轮换、吊销、过期和报废流程；记录设备与证书/公钥、硬件身份、站点、所有者和软件基线的关联。
- 私钥优先在适当的硬件信任边界内生成和使用；若硬件不支持，应明确软件密钥的存储、访问控制、备份和泄露响应风险。
- 设备身份凭据、用户/服务访问凭据、传输会话密钥、更新签名密钥应分离管理，避免单一密钥泄露导致所有信任边界失守。
- 设备离线期间发生凭据吊销或权限变化时，必须定义设备何时、通过何种可信渠道获知；不能假设离线设备实时获得云端撤销信息。

### 2.2 云端命令与设备侧授权

每条会改变设备状态的命令，至少应能关联：
- 命令唯一标识、设备/设备组标识、发起主体和授权依据；
- 命令类型、参数 schema/版本、目标软件/配置基线；
- 创建时间、有效期或失效条件、审批/工单引用；
- 幂等键、重放防护信息、执行状态和最终结果；
- 撤销/取消语义、审计记录和失败原因。

设备端应校验主体权限、目标设备、命令有效期、签名/认证上下文、状态前置条件和参数范围。重复投递不能造成重复执行；消息 QoS、HTTP 2xx 或 broker 确认仅说明各自协议层的交付/响应语义，不等于业务动作已完成。

设备影子（Desired/Reported）或类似状态模型用于表达期望状态和观测状态，不是事务数据库，也不能仅靠字段相等证明现场状态真实。应为命令执行、配置应用、软件启动和业务恢复分别定义状态与证据。

## 3. 更新制品与软件供应链信任

### 3.1 制品与 manifest

每个可发布制品应有不可变标识和可验证的元数据，至少按产品需要记录：

- 产品/硬件型号、板卡或 ECU 标识、硬件修订版和适配范围；
- 组件名称、版本、依赖关系、互斥/协同版本约束和升级顺序；
- 制品长度、密码学摘要、签名与签名密钥标识；
- 发布渠道、构建来源、源码 commit、构建流水线和制品 provenance；
- SBOM、许可证/第三方组件声明、漏洞处置状态和安全公告引用；
- 安装前置条件、空间/电源/温度/业务状态约束；
- 安装步骤、启动验证方法、恢复路径及不可回滚变更声明。

Manifest 的签名验证必须覆盖其安全相关字段，且验证后的元数据在使用前不得被未授权修改。对多组件更新，应检查整个版本组合的兼容性，不能仅分别验证每个包的签名和哈希。

### 3.2 信任根、签名与防回滚

- 定义设备信任根、启动验证链、更新验证链和密钥轮换/撤销机制；明确 ROM、Bootloader、TEE/安全元件、操作系统和应用各层由谁验证。
- 使用受控发布密钥和最小权限审批；高影响产品可评估多角色/阈值签名、离线根密钥和分层委派。
- 版本单调计数、可信时间、元数据过期和设备持久化状态需共同考虑，以防止回滚、冻结、重放、混装和密钥轮换期间的恢复问题。
- Secure Boot 主要约束启动时加载的代码是否处于信任链中；它不能替代 OTA 授权、运行时防护、漏洞管理或安全功能验证。
- A/B 分区是一种恢复架构选择，不是所有 MCU、Bootloader、文件系统或存储布局都支持的通用方案。单分区、双 bank、恢复分区、外部编程器等方案应按硬件能力和失效分析选择。
- 差分包依赖正确的源版本和目标版本；必须校验基线、完整性、空间需求和失败回退方式。不能把差分下载成功等同于目标镜像可启动。

参考模型：NIST SP 800-193 的保护/检测/恢复原则；IETF RFC 9019 固件更新架构与 RFC 9124 manifest 信息模型；TUF 元数据更新安全机制。Uptane 是地面车辆软件更新安全框架，可作为多 ECU 威胁分析参考，不代表机器人产品自动适用或符合该标准。

## 4. 端到端 OTA 状态机

以下状态应分开记录；实际产品可以增加子状态，但不得将它们压缩为一个布尔成功标志。

| 阶段 | 设备侧关键检查 | 云端应记录的证据 | 失败处理方向 |
|---|---|---|---|
| 候选评估 | 设备身份、当前版本、硬件/组件兼容性、依赖与容量 | 候选清单、目标范围、策略版本 | 排除不兼容设备；保留原因 |
| 发布审批 | 发布签名、审批权限、维护窗口和风险评估 | 审批主体、变更单、签名元数据 | 阻止发布或退回审批 |
| 任务授权 | 目标设备、命令有效期、幂等/重放检查 | 命令 ID、授权上下文、撤销状态 | 拒绝过期、重复或越权命令 |
| 下载 | TLS 对端验证、长度/摘要、断点续传边界、存储空间 | 字节数、重试原因、制品摘要 | 保留当前可运行版本；清理不完整临时文件 |
| 制品验证 | 签名链、manifest、硬件/版本/依赖约束、反回滚策略 | 验证结果、信任根/密钥版本 | 拒绝安装并记录可诊断错误 |
| 安装准备 | 本地安全状态、能源/温度/载荷/制动/设施状态、持久化空间 | 设备本地准入结果和策略版本 | 延迟、取消或转人工处置 |
| 写入/切换 | 写入完整性、写保护、原子切换/恢复点 | 安装阶段、目标分区/组件、进度证据 | 按硬件设计恢复；禁止盲目重试破坏当前镜像 |
| 首次启动 | 启动链验证、关键服务启动、硬件/驱动兼容性 | 启动结果、启动原因、版本证明 | 保持安全状态并执行已验证的恢复策略 |
| 业务健康确认 | 传感器/执行器/定位/通信/安全相关功能和业务流程健康 | 分层健康结果、诊断日志、测试用例版本 | 暂停扩散、隔离设备、人工复核 |
| 完成与对账 | 实际运行版本、配置、组件组合与期望状态一致 | 最终结果、审计记录、异常关闭依据 | 保留差异，不得仅因设备重新上线标记成功 |

下载、验证、安装、启动、业务健康和安全功能验证是不同的证据门。设备离线、重启或超时后，云端应重新读取设备实际状态并进行幂等对账，而不是简单重发安装命令。

## 5. 机器人现场的升级准入与安全状态

机器人升级不是普通服务器滚动更新。升级前应由产品风险分析确定设备必须处于什么状态，至少检查：

- 当前任务是否结束、暂停或已安全交接；载荷是否被可靠放置/固定；
- 机器人是否处于允许维护的区域，是否存在人员、交通、坡道、升降机构或其他危险运动；
- 驱动使能、制动器、急停、安全扫描仪、门锁、限位及其他安全相关功能处于何种状态；
- 是否需要现场能源隔离、机械支撑、挂牌上锁或专业人员在场；
- 电源稳定性、剩余能量、温度、存储空间和备用供电是否满足目标设备的升级设计；
- 网络中断或云端不可达时，本地是否仍能安全完成当前状态转换；
- 更新对象是否包含安全控制器、制动/驱动固件、BMS、传感器固件或安全参数；这些对象应有独立的影响分析、授权、验证和恢复计划。

不得将“空闲”“在充电位”“电量超过某百分比”作为所有机器人都适用的升级许可。维护窗口、最低能量、温度范围、允许载荷和区域条件均需由具体硬件、风险分析和试验确定。

远程命令不得解除急停、门锁、保护停止或其他安全联锁；OTA Agent 不应成为安全功能的唯一执行者。升级导致安全相关控制功能不可用时，必须有经验证的安全状态和现场恢复程序。普通应用层自检通过，不等于安全功能仍然有效。

## 6. 分组件升级策略

| 对象 | 典型更新对象 | 必须单独定义的设计问题 |
|---|---|---|
| MCU/Bootloader | 主控、底盘、BMS、传感器控制器固件 | ROM/Bootloader信任根、双 bank/恢复入口、写入中断、调试口与防回滚 |
| OS/BSP/内核 | Linux镜像、内核、设备树、驱动、根文件系统 | 启动链、ABI/驱动兼容、内核模块、存储布局、恢复介质 |
| ROS 2/业务应用 | 节点、容器、运行时、配置 | 消息/服务/Action契约、DDS/QoS、依赖版本、进程编排与回滚兼容 |
| 地图/路网/标定 | 地图、语义层、路网、标定参数 | 机器人型号/传感器/软件版本绑定、数据迁移、旧版恢复与现场复核 |
| AI模型/数据 | 模型权重、推理引擎、词表/数据配置 | 硬件算子兼容、模型来源、性能/精度回归、数据隐私与模型回退 |
| 配置/策略 | 参数、设备影子期望值、业务规则 | schema/签名、配置迁移、范围校验、即时生效与重启生效边界 |

组件更新应建立依赖图和兼容矩阵。需要原子协同更新的组件应作为同一发布事务管理；无法原子更新的组件，应定义中间版本的安全行为、版本混用限制和恢复顺序。

## 7. 分批发布、暂停与回滚治理

发布分组可以按站点、机型、硬件修订、组件版本、网络条件、运行风险和维护能力组合；灰度比例、批次规模、观察周期和继续条件必须由产品风险、车队分布、恢复能力和实际数据确定，不使用固定行业比例。

每一批次至少定义：

1. **准入范围**：设备身份可信、硬件/软件基线明确、维护条件满足、目标版本兼容。
2. **观察指标**：下载/验签/安装/启动/业务健康分别统计；区分设备失联、主动取消、失败和未上报。
3. **停止条件**：签名验证失败、异常启动、关键服务/传感器故障、安全相关功能异常、版本混装、设备失联或现场风险事件等；具体阈值由产品和安全论证确定。
4. **暂停权限**：明确谁可暂停全局、站点、机型或单设备发布；暂停后如何撤销尚未执行的命令。
5. **恢复决策**：判断继续、重试、回滚、现场维修或隔离；不得对所有失败自动重复刷写。
6. **发布审计**：记录制品摘要、签名/密钥版本、策略、目标清单快照、审批、设备结果、异常处置和最终版本分布。

回滚不是普适的“恢复旧版本”按钮。数据库/配置 schema、地图格式、标定数据、模型、Bootloader、单调计数器和安全参数可能不可逆或存在前后向兼容限制。发布前应明确可回滚范围、不可逆步骤、恢复镜像来源、数据迁移策略和人工介入条件。

## 8. 异常与恢复设计

| 故障场景 | 设计要求 |
|---|---|
| 下载中断/网络分区 | 支持经验证的断点续传或安全重启下载；校验分块/整体摘要；临时数据不能覆盖当前可启动镜像 |
| 下载后存储不足 | 安装前检查容量与写放大/临时空间；失败时保留可运行版本和诊断信息 |
| 安装时断电 | 根据 Flash/文件系统/Bootloader 特性验证原子写入或恢复分区；不能仅靠“CRC 双确认”宣称不会变砖 |
| 新镜像无法启动 | 依赖硬件支持的启动计数、健康确认、回退分区或恢复介质；验证恢复路径本身 |
| 设备上线但状态未知 | 云端读取实际启动版本、组件状态和更新事务标识，进行状态对账；不重复执行非幂等步骤 |
| 组件版本混装 | 使用整体兼容矩阵、manifest依赖和发布锁；不允许各包分别验签后无条件组合运行 |
| 密钥泄露/证书吊销 | 暂停受影响发布通道，轮换/撤销密钥，评估离线设备暴露窗口和可信恢复路径 |
| 设备长期离线 | 定义过期元数据、证书状态、跳版本更新、依赖链和恢复介质策略；不得假设其仍可直接安装最新版本 |
| OTA服务或仓库被攻陷 | 采用分权签名、独立元数据角色、制品不可变存储、审计与客户端验证；评估冻结/回滚/混装攻击 |
| 安全相关组件升级失败 | 保持经风险分析确定的安全状态，禁止自动恢复到未经兼容验证的组合；必要时现场隔离和专业维修 |

## 9. 远程诊断、隐私与可观测性

远程诊断链路应将设备遥测、错误码、崩溃日志、更新状态、配置差异和工单关联起来。日志应记录来源、设备身份、时间基准、软件版本、配置版本和采集完整性。

- 远程采集遵循最小必要原则；视频、音频、地图、人员或场地数据应评估隐私、商业秘密、存储区域和保留期限。
- 远程 shell、文件拉取、调试接口和状态注入属于高权限操作，应单独授权、限时、留痕并可撤销。
- 不把“远程复现”理解为可在生产机器人上随意注入状态；优先在隔离仿真/测试环境复现，生产设备操作必须有风险评估和现场授权。
- 诊断数据可能不完整或延迟；云端告警不应替代设备本地保护与实时诊断。
- 记录升级失败的设备分母、结果分类、未上报数量和观察窗口，避免只统计成功回报设备造成选择偏差。

## 10. 验证计划与发布门禁

验证需按目标硬件、软件、网络和现场风险建立可复现测试。最低覆盖：

- **制品/供应链**：签名错误、错误密钥、过期/撤销密钥、错误型号/硬件版本、摘要不匹配、manifest篡改、依赖冲突、旧版本重放和元数据冻结。
- **传输/命令**：断网、限速、乱序、重复投递、重放、命令过期、设备身份失效、服务端不可用和状态对账。
- **存储/安装**：空间不足、Flash写失败、下载/解包/安装各阶段断电、分区切换失败、差分基线错误和恢复介质失效。
- **启动/业务**：启动链失败、驱动不兼容、ROS节点/容器未就绪、传感器失效、地图/标定不匹配、模型加载失败和混合版本。
- **机器人安全**：维护前置条件不满足、升级期间意外运动请求、通信丢失、安全相关控制器不可用、急停/保护停止状态、载荷和设施状态变化。
- **发布治理**：分组边界、暂停/撤销、回滚兼容、审批权限、审计完整性和异常批次隔离。
- **恢复与长期运行**：多次升级、跨版本跳跃、设备长期离线后恢复、密钥轮换、存储磨损、恢复后配置/数据一致性。

每项测试记录硬件版本、Bootloader/OS/固件/应用版本、配置、网络条件、故障注入点、预期结果、实际结果、日志/波形/镜像摘要、测试人员和复核人。SIL/HIL/实机测试的范围与相互替代关系应明确；仿真通过不能证明断电恢复或安全功能在真实硬件上有效。

发布门禁至少应有：需求与威胁模型评审、制品和签名审查、兼容性验证、故障恢复验证、安全影响评审、灰度/停止/回滚方案审批、现场维护准备和发布后证据归档。具体门槛由产品质量体系和适用法规/标准决定。

## 11. 标准、规范与适用性边界

| 资料 | 可用于什么 | 不应作何种推断 |
|---|---|---|
| NIST SP 800-193 | 平台固件保护、检测、恢复的韧性原则 | 不等于机器人产品认证或完整OTA架构规范 |
| IETF RFC 9019 | IoT固件更新架构、参与方与更新流程术语 | Informational RFC，不是Internet Standards Track强制标准 |
| IETF RFC 9124 | 固件更新manifest信息模型与安全字段 | Informational RFC，不是特定机器人产品的完整协议/实现 |
| The Update Framework (TUF) | 仓库元数据、角色分权、阈值签名、回滚/冻结风险防护 | 采用TUF不自动证明设备启动链、现场恢复或业务安全 |
| Uptane 2.1.0 | 地面车辆多ECU软件更新威胁模型与验证思路 | 车辆领域框架，不是机器人通用法规或认证声明 |
| UN Regulation No. 156 | 适用范围内道路车辆的软件更新管理体系参考 | 不得直接声称其适用于所有工业/服务机器人 |

标准/规范适用性需结合产品类型、销售地区、预期用途、合同和监管要求逐项确认。引用某项规范或采用其部分机制，不等于获得认证或声明符合性。

## 13. 维护与待确认项

- 本文不指定通用灰度比例、电量阈值、自检时长、证书保留期、日志保留期、升级频率或回滚计数；这些数值必须由目标产品与适用要求确定。
- 需按实际机器人产品补齐：设备信任根与启动链图、密钥层级/轮换策略、设备/用户/服务权限矩阵、manifest schema、组件兼容矩阵、分区布局、恢复介质、状态机、现场升级SOP和发布审批RACI。
- 需在目标硬件上验证下载/安装/切换/启动/业务恢复及安全功能；需执行网络故障、断电、存储耗尽、密钥轮换和回滚演练。
- 需明确安全控制器、驱动器、BMS、Bootloader、地图/标定和模型更新是否允许远程执行，以及其单独审批和现场验证要求。
- 本文的静态审查不构成设备身份安全评估、渗透测试、固件签名验证、Secure Boot验证、OTA实现审计、功能安全确认或现场验收。
