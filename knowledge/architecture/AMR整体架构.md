# AMR 整体架构

> 本文是**工业场景自主移动机器人（AMR）及其车队系统的参考架构视图**，用于帮助识别系统边界、接口和工程验证对象，不是所有移动机器人的标准架构，也不是可直接复制的产品设计。实际架构必须由任务、运行设计域（ODD）、载荷、底盘形式、人员共域方式、设施接口、可用性目标和适用法规共同决定。

## 1. 系统边界与架构视图

AMR系统通常不止车体本身。应先明确项目边界是否包括车队管理、充电设施、自动门/电梯、输送线、仓储或制造执行系统，以及现场网络和运维平台。典型系统可按以下视图拆分；其中云端、边缘节点和特定感知设备均为可选配置。

```
┌────────────────── 业务与车队管理（可选/可分布式部署） ──────────────────┐
│ WMS/MES/ERP/工单 │ 车队任务与交通协调 │ 设备管理/遥测/远程运维 │ OTA管理 │
└───────────────────────┬──────────────────────────────────────────────┘
                        │ 有边界的任务、状态、配置与运维接口
┌───────────────────────┴────────────── AMR车端 ────────────────────────┐
│ 任务与应用层：任务状态机、作业流程、HMI、人机权限、载荷/工装控制        │
├──────────────────────────────────────────────────────────────────────┤
│ 自主能力层：定位/建图、环境感知、全局/局部规划、行为决策、运动控制接口   │
├──────────────────────────────────────────────────────────────────────┤
│ 设备与实时控制层：底盘控制器、驱动器、制动/转向、传感器接口、诊断       │
├──────────────────────────────────────────────────────────────────────┤
│ 机电与安全相关系统：车体/载荷/能源、保护装置、安全控制器及执行元件       │
└──────────────────────────────────────────────────────────────────────┘
       │现场接口（按项目适用）              │环境与人员
       ├─ 充电站/自动充电                  ├─ 地面、坡道、门槛、照明
       ├─ 自动门/电梯/输送线               ├─ 人员、其他车辆、障碍物
       └─ 站点网关/工业网络                └─ 标识、禁行区、消防与疏散设施
```

图中是逻辑分层，不代表进程、ECU、网络分区或安全功能的物理部署。实际系统可能将多个逻辑层合并到同一计算平台，也可能把安全控制、底盘控制和任务应用部署在不同控制器上。架构评审必须另行给出物理部署图、网络拓扑、供电分区和安全相关控制链路。

### 1.1 主要子系统及职责边界

| 子系统 | 典型职责 | 设计输入与输出 | 不应默认承担的职责 |
|---|---|---|---|
| 车端任务/应用 | 作业状态、任务执行、操作员交互、载荷业务 | 任务目标、设备状态、作业结果 | 不应替代底层运动控制或安全功能 |
| 自主导航 | 定位、地图、环境理解、路径/轨迹生成 | 传感器数据、地图、目标位姿、速度约束 | 普通导航节点不自动构成安全防护功能 |
| 底盘与运动控制 | 运动学/动力学控制、驱动命令、反馈与故障诊断 | 速度/转向目标、编码器、电机和制动反馈 | 不应绕过独立安全链执行危险动作 |
| 安全相关控制 | 按风险评估实现保护性停止、速度/区域监控等安全功能 | 安全传感器、急停、联锁、驱动安全输入 | 不应由普通ROS话题、云端指令或HMI软件单独替代 |
| 车队/业务系统 | 多车任务协调、交通资源、订单与设施联动 | 任务、地图/区域、车辆能力与状态 | 不应假定能取代车端本地安全决策 |
| 设施与站点系统 | 充电、门禁、电梯、输送线、站点互锁 | 设施状态、预约/授权、完成反馈 | 接口连通不等于安全互锁已验证 |
| 运维与云平台 | 设备注册、遥测、诊断、配置和受控升级 | 身份、授权、版本、审计日志 | 不应成为车辆实时运动闭环或唯一安全停机路径 |

### 1.2 关键架构决策

设计阶段至少记录以下决策及理由：

- **自主程度与运行设计域：** 地图/标识依赖、动态环境、照明、地面、坡度、通道宽度、人员密度、速度和载荷范围。
- **定位与感知组合：** 激光、视觉、惯性、轮速、反光标志、二维码、UWB或其他设施辅助；写明遮挡、退化和失效时的策略。
- **运动学与底盘：** 差速、舵轮、阿克曼、全向或其他形式；明确可实现的速度、加速度、转弯半径、制动和载荷边界。
- **计算与实时分区：** 哪些任务运行在通用计算机、实时控制器或安全控制器；接口的周期、超时、故障检测和恢复行为。
- **部署与网络：** 车端自治能力、边缘/云依赖、网络分区、身份认证、授权、时间同步和断网行为。
- **车队协同：** 单车自治与集中式/分布式任务协调的责任边界；冲突区、窄通道、电梯和充电位等共享资源如何预约和释放。

## 2. 车端典型数据流与接口

下表描述常见逻辑流，不规定统一频率、延迟或协议。频率和时序必须由传感器规格、控制带宽、计算负载、网络拓扑、控制稳定性分析和实测确定。

| 数据流 | 典型路径 | 接口选择示例 | 必须定义的工程属性 |
|---|---|---|---|
| 感知数据 | 传感器 → 驱动/时间戳 → 感知/定位 → 地图或障碍表达 | ROS 2 Topic、共享内存、厂商SDK | 时间戳来源、坐标系、标定版本、丢帧/延迟、QoS、数据有效性 |
| 运动命令 | 任务/导航 → 速度或轨迹命令 → 底盘控制器 → 驱动器 | ROS 2 Topic/Action、CAN/CANopen、EtherCAT、串口或厂商协议 | 单位、坐标系、限幅、更新周期、命令超时、看门狗、使能/禁能语义 |
| 运动反馈 | 编码器/驱动器 → 底盘状态估计 → 定位/诊断/应用 | 总线反馈、ROS 2 Topic | 采样与发布时间、方向约定、轮径/轮距标定、异常值与断线处理 |
| 任务与状态 | RMS/业务系统 ↔ 车端任务管理 | VDA 5050、厂商API、消息队列或定制接口 | 任务生命周期、幂等、确认、重试、取消、状态一致性和版本兼容 |
| 设施协同 | AMR ↔ 门/电梯/输送线/充电站 | PLC协议、现场总线、REST或消息接口 | 互锁责任、授权、占用/释放、超时、故障恢复和人工接管 |
| 运维与遥测 | 车端 → 边缘/云；受控配置/升级 → 车端 | MQTT/HTTPS等 | 设备身份、ACL、TLS、离线缓存、数据保留、升级签名和回滚策略 |
| 安全相关信号 | 安全传感器/急停/联锁 → 安全控制器 → 安全输出/驱动安全输入 | 经风险评估选定的安全相关硬件与通信接口 | 安全功能、性能等级/完整性要求、故障反应、复位、验证与配置控制 |

### 2.1 ROS 2通信模式的选择

在采用ROS 2的实现中，接口类型应按语义选择，而不是把所有交互都设计成Topic：

- **Topic：** 连续或周期性数据流，例如传感器数据、状态和诊断。
- **Service：** 期望快速完成的请求/响应，例如查询或短时配置操作；不适合承载长时间任务。
- **Action：** 有明确目标、持续反馈、结果和取消语义的长时操作，例如导航到目标点。

ROS 2 QoS需逐连接核对History/Depth、Reliability、Durability、Deadline、Lifespan和Liveliness等策略。发布者与订阅者QoS不兼容时可能无法建立通信；Reliable也不意味着端到端业务事务已经完成，更不代表实时性或安全性得到保证。具体行为依赖ROS发行版、RMW/DDS实现和部署配置。

### 2.2 时钟与时间戳

不要将“NTP全网同步”或某个固定时差写成所有AMR项目的通用验收指标。应区分：

- 传感器采集时间、驱动接收时间、消息发布时间和主机系统时间；
- 同一车体内部多传感器融合所需的相对时间精度；
- 多车协同、跨设备事件追踪和云端日志所需的时间一致性；
- NTP、PTP/IEEE 1588、硬件时间戳或设备内部时钟的适用条件。

应记录时钟源、同步拓扑、硬件时间戳支持、漂移/偏移监控、失锁告警和失效降级。阈值必须由传感器融合误差预算、控制/协同需求和现场测量确定；日志时间对齐不能替代实时控制同步验证。

## 3. 车队、网络与弱网行为

车端、边缘节点和云端的职责分配取决于业务连续性、网络可用性、车队规模、现场设施和网络安全约束。云端不应被默认放入运动控制闭环；车端应明确哪些功能在失去上位系统或网络后仍可执行。

“断网自治”不是无条件继续完成当前任务。项目必须为每种网络故障定义状态机和风险控制，例如：

1. 检测链路中断、消息过期、认证失败或上位系统不可用，并区分短暂抖动与持续故障。
2. 按任务阶段、载荷状态、所在区域、交通冲突和设施依赖判断是否允许继续、暂停、撤离或安全停止。
3. 对缓存任务、重复指令、过期命令和恢复重连进行版本、时效、幂等与授权检查。
4. 恢复通信后协调状态对账，避免重复执行、任务丢失或多方同时控制。
5. 保留本地安全功能，不允许云端或业务应用屏蔽急停、保护装置或安全联锁。

网络设计应明确车内网络、车队网络、设施网络和外部运维网络的信任边界、访问控制、密钥管理、日志和升级通道。具体协议及安全配置须按产品威胁模型、部署环境和供应商接口验证。

## 4. 故障域与降级设计

故障域应按实际进程、控制器、供电、网络、传感器和设施依赖划分。下表是分析起点，不是预先认可的故障反应：

| 故障域/异常 | 需要检测的证据 | 设计时需定义的反应 |
|---|---|---|
| 单进程/节点异常 | 心跳、生命周期状态、资源耗尽、输出超时 | 重启策略、状态恢复、命令失效保护；评估重启期间的运动状态 |
| 定位/感知退化 | 传感器健康、定位协方差/创新量、观测覆盖、时间戳和一致性检查 | 限速、受控停止、重新定位或人工介入；阈值须经试验验证 |
| 底盘/驱动异常 | 驱动故障码、编码器合理性、命令/反馈偏差、制动反馈 | 由控制与安全架构确定停止/保持策略，不得仅依赖导航软件 |
| 通信异常 | 链路状态、消息年龄、序列号、租约/心跳、认证错误 | 本地自治、任务冻结、状态对账或停止；按故障场景验证 |
| 云/边缘服务异常 | 服务健康、连接状态、任务确认与数据积压 | 限制上位业务，不影响本地必要安全功能；定义人工运营流程 |
| 电源/BMS异常 | 电压、电流、温度、BMS告警、接触器/制动状态 | 按电池、驱动和安全设计规定的能量管理与停止策略 |
| 设施异常 | 门/电梯/充电站PLC状态、互锁反馈、占用状态 | 不进入未授权区域，不执行未确认的设施动作；定义现场恢复程序 |

协方差监控、心跳或进程重启都只是诊断机制的一部分，不能单独证明故障已被安全检测或风险已受控。故障反应必须与危害分析、控制器能力、制动/保持特性和现场工况关联，并用故障注入、台架和实机测试验证。

## 5. 安全与标准适用性边界

对于工业场景的无人驾驶工业车辆/AMR，应评估ISO 3691-4及其适用的关联标准、法规和国家/地区采纳版本。ISO 3691-4:2023是已发布版本；ISO/DIS 3691-4第三版目前处于标准制定流程，不能将草案当作已发布标准或直接据此宣称符合性。其适用范围、排除场景和具体条款必须结合产品类别、运行区域及完整正式文本确认。

安全架构应由风险评估确定危险源、保护措施、安全功能、性能要求、验证方法和责任边界。急停、保护性停止、速度/区域监控、驱动安全输入、机械制动、软件停止和业务暂停是不同概念；普通ROS节点、云端命令或任务状态机不得被描述为独立安全功能，除非整个安全相关系统按适用标准设计并完成相应验证。

ISO 3691-4并不覆盖所有移动机器人应用。公共区域、医疗、特殊环境、爆炸性环境、军用或其他排除场景应另行识别适用法规与标准，不得将工业AMR模板直接套用。

## 6. 架构评审与验证清单

在详细设计前，至少完成以下检查，并将结论、责任人、版本和证据链接纳入架构决策记录（ADR）或系统工程基线：

- [ ] 运行设计域、任务剖面、载荷、人员/其他车辆共域条件和设施边界已定义。
- [ ] 逻辑架构、物理部署、网络拓扑、供电分区和安全相关控制链分别绘制。
- [ ] 每条跨层接口定义数据模型、单位、坐标系、时钟语义、超时、QoS/协议和版本兼容策略。
- [ ] 任务/导航/底盘/安全/设施各层的命令权限、仲裁者和失效默认状态明确。
- [ ] 断网、定位退化、传感器失效、驱动异常、云端故障和设施故障均有可执行场景。
- [ ] 保护装置、急停、停止时间/距离、制动保持和复位逻辑有风险评估与适用验证证据。
- [ ] 正常、边界、异常、恢复、长期运行和现场验收测试均有需求追踪关系。
- [ ] 供应商SDK、固件、ROS发行版、RMW/DDS、地图格式和配置均有版本基线。
- [ ] 网络安全、身份/授权、日志、OTA签名与回滚策略有设计和验证责任人。

建议验证层级：模型/离线分析 → 软件单元与集成测试 → SIL/仿真 → 控制器台架/HIL → 车体实测 → 设施联调 → FAT/SAT及运行期监测。每一级只能对其实际覆盖的需求和配置给出结论，仿真通过不能替代制动、保护装置、人员共域和现场设施验证。
