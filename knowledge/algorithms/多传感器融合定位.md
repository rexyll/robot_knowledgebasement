# 多传感器融合定位

> 本文讨论运行期状态估计：利用传感器观测、运动模型和（可选）环境地图估计机器人位姿、速度及相关状态。融合不是“传感器越多越好”，也不存在所有机器人都适用的固定传感器组合。是否融合、融合哪些变量，取决于任务、环境、传感器误差、时间同步、坐标系、可观性和安全要求。

## 1. 先区分定位、航位推算与 SLAM

- **航位推算（odometry / dead reckoning）**：根据轮编码器、IMU、视觉里程计等估计短时间运动。通常连续，但误差会随时间积累。
- **地图定位（localization）**：在已有地图、地标或全球参考中估计当前位姿。它可以抑制长期漂移，但观测重捕获或地图匹配可能带来位姿修正。
- **同步定位与建图（SLAM）**：在地图未知或不完整时，同时估计轨迹和地图。SLAM 系统可以提供定位结果，但不应把 SLAM、纯里程计和已知地图定位混为一谈。
- **状态估计（state estimation）**：更广义的概念，状态可以包含姿态、速度、位置、IMU 偏置、传感器偏置等，不仅是二维/三维位置。

单一传感器在某些受限任务中可以足够；多传感器融合的价值在于利用互补观测改善可观性、连续性或鲁棒性。若传感器噪声相关、时间戳不一致、外参错误或协方差设置失真，增加传感器反而可能使估计变差。

## 2. 传感器观测及其误差边界

| 观测来源 | 常见可用信息 | 有利条件 | 主要误差/限制 | 融合前检查 |
|---|---|---|---|---|
| 轮编码器/轮里程计 | 轮转角、轮速、底盘速度或积分位姿 | 结构化地面、轮地接触稳定、轮径/轮距标定可靠 | 打滑、轮胎变形、地面不平、轮径误差、编码器分辨率与安装误差 | 确认驱动器/底盘是否已在内部融合 IMU；核对单位、符号、协方差、轮径/轮距和时间戳 |
| IMU | 角速度、线加速度；部分 IMU 提供姿态解算 | 高频运动响应、短时姿态/运动预测 | 零偏、随机游走、温漂、振动、饱和、安装外参与重力补偿错误 | 核对坐标约定、单位、安装方向、采样时间、协方差及姿态解算来源 |
| GNSS / RTK | 全球或局部位置、部分接收机提供速度/航向与 fix 状态 | 开阔天空、天线安装与坐标基准明确 | 遮挡、多路径、电离层/大气误差、固定解丢失、天线杆臂与航向估计误差 | 同时检查 fix 类型、协方差、时间戳、基准/坐标系、天线外参和失锁行为 |
| LiDAR 扫描匹配/点云地图 | 相邻扫描相对运动、对地图的位姿约束 | 场景有足够稳定几何结构，点云时间与运动补偿可靠 | 长廊/平面等几何退化、动态物体、反射/吸收材质、遮挡、运动畸变和地图变化 | 核对点云时间戳、去畸变、外参、地图坐标系、匹配残差与退化检测 |
| 相机/视觉里程计/VIO | 特征跟踪、视觉相对位姿、深度或视觉惯性约束 | 纹理和光照足够、运动模糊可控、标定与同步可靠 | 弱纹理、重复纹理、光照变化、动态物体、滚动快门、尺度/初始化与跟踪失败 | 核对相机模型、内外参、曝光/时间戳、图像同步、特征质量及重定位能力 |

**禁止跨型号照搬频率、精度和漂移数字。** 数据表中的采样率、分辨率或实验室精度不等同于系统定位精度。比较传感器或算法时，应固定准确型号、配置、安装、温度/运动工况、时间同步、算法版本、数据集与统计指标。

## 3. 移动机器人常用坐标系：map、odom、base_link

REP-105 为 ROS 移动平台定义了常用坐标系语义。它是移动机器人约定，不意味着所有机械臂、飞行器、水下机器人或其他机器人必须采用完全相同的 TF 架构。

```
map  ─────►  odom  ─────►  base_link
 长期参考       局部连续          机器人本体
```

| 坐标系 | 含义 | 典型特性 | 常见用途 |
|---|---|---|---|
| `base_link` | 固定在机器人底座/机体上的参考坐标系 | 随机器人运动；具体原点和朝向由平台定义 | 传感器外参、车体速度、局部控制 |
| `odom` | 世界固定的局部里程计坐标系 | 位姿应连续、无离散跳变；漂移可随时间累积且无统一上界 | 短时运动、局部感知与控制 |
| `map` | 世界固定的长期参考坐标系 | 目标是长期不显著漂移；允许因定位修正而离散跳变 | 全局定位、地图与全局规划 |

注意：

1. `map` 不一定是地理意义上的绝对坐标系。它可以是应用自定义原点；若与 GNSS、测绘或多机器人坐标对接，必须明确基准、单位、轴方向、datum 和变换关系。
2. `odom` 的“连续”不代表“长期准确”；`map` 的“长期参考”也不代表其更新永远平滑。
3. TF 树中每条变换边应有明确、唯一的权威发布者。不要让 AMCL 和另一套全局 EKF 同时发布同一条 `map→odom` 变换。
4. 在 ROS 约定下，局部估计常发布 `odom→base_link`，全局定位来源或全局估计常负责 `map→odom`；实际架构应以所用节点的参数和 TF 发布行为为准。

## 4. 定位架构选择

| 架构 | 核心方法 | 适用情况 | 主要权衡 |
|---|---|---|---|
| EKF / UKF | 递归状态估计；按运动模型预测，再用带协方差的观测修正 | 状态维数和运动模型明确、需要连续在线估计 | 计算开销通常可控；线性化/模型误差、异常观测和初始化会影响结果 |
| 粒子滤波 | 用带权样本近似可能多峰的后验分布 | 例如在已知 2D 地图中使用激光扫描的 AMCL | 可表达多峰位姿假设；粒子数量、观测模型和场景会影响算力与收敛 |
| 因子图/平滑优化 | 把状态与观测写为因子，联合优化一段轨迹或地图 | 需要回环、历史约束、多传感器联合优化或离线/增量平滑 | 计算、内存和数据关联复杂度更高；鲁棒核和优化器本身不能自动消除错误数据关联 |
| 组合架构 | 高频里程计/滤波与低频全局定位、回环或图优化配合 | 需要同时满足局部连续性和长期全局约束的系统 | 需要明确状态接口、时间基准、TF 所有权、协方差传递与失效切换 |

“滤波派/图优化派”不是精度高低的简单排名。某些 LIO 系统内部使用迭代滤波，并不意味着它天然就是“滤波 + 独立后端图优化”的组合架构；是否存在回环、全局地图优化和重定位，应逐个软件实现核对。

## 5. ROS 2 robot_localization：输入配置与数据质量

`robot_localization` 提供 `ekf_localization_node`、`ukf_localization_node` 和辅助 GNSS 集成的 `navsat_transform_node`。它支持多个传感器输入，但支持多输入不代表可以不分析测量相关性、坐标系或协方差。

### 5.1 先核对每条输入

- **消息和变量**：确认输入类型及需要融合的状态变量。配置数组描述的是消息中的状态分量，不是传感器产品功能清单。
- **坐标系**：配置变量按输入消息的 `frame_id` 语义理解；位姿、速度所在坐标系不同，必须存在正确 TF 变换。
- **单位和约定**：遵循 ROS REP-103 等坐标/单位约定，确认角度单位、角速度单位、正方向、ENU/NED 转换及 IMU 安装方向。
- **协方差**：协方差不能随手填零或用任意常数。缺失、低估或不合理的协方差会改变融合权重；必须基于设备规格、标定和数据评估。
- **时间**：核对传感器时间戳来源、同步误差、延迟、乱序数据及 TF 可用时间。时间偏移会使空间上正确的观测也对应错误时刻。
- **二维模式**：只有在系统确实可按平面运动建模、且忽略高度/滚转/俯仰不会破坏任务要求时，才启用 `two_d_mode`。

### 5.2 不要把“同一变量”与“重复信息”混为一谈

同一个状态变量可以由多个独立传感器测量；在协方差可信、误差模型合理且相关性得到处理时，可以融合。例如两个独立 IMU 都提供姿态，并不意味着必须舍弃其中一个。

真正危险的是**把同一来源的信息重复当成独立观测**。例如底盘驱动器发布的里程计可能已经在内部融合编码器和 IMU；若又把其位姿、原始编码器积分结果及同一 IMU 观测都作为独立数据输入，可能重复计算同一信息并造成过度自信。应检查数据链路、驱动实现、协方差和误差相关性，而不是机械地规定“yaw 只能来自一个传感器”。

### 5.3 differential 与 relative 不是同一个开关

- `_differential`：将连续两次姿态观测之差转为速度观测。适用于特定多源绝对姿态冲突场景，但会改变误差随时间累积的方式；尤其对角度变量要检查长期协方差行为。
- `_relative`：将该传感器后续观测相对其第一次观测表达，用于建立相对零点；它不会把姿态差分成速度。
- 融合经 `navsat_transform_node` 产生的 GNSS 里程计时，按官方说明将对应输入的 differential 设为 false，并核对数据坐标系和 datum 配置。

### 5.4 navsat_transform_node 的真实数据流

`navsat_transform_node` 不是简单的“GPS 坐标转 map”函数。官方接口说明它接收：

1. `nav_msgs/Odometry`：通常为状态估计节点输出的机器人里程计；
2. `sensor_msgs/Imu`：机器人航向估计（或按配置使用 odometry 航向）；
3. `sensor_msgs/NavSatFix`：GNSS 位置观测。

它生成与机器人 world frame 一致的 `nav_msgs/Odometry`，可再融合进 EKF/UKF；可选发布的 Cartesian/UTM/local ENU 变换需按配置理解。落地前必须确认 GNSS 基准、datum、航向约定、天线安装杆臂、协方差和失锁行为。

## 6. 失效模式与安全退化

| 失效/异常 | 可观测信号 | 工程处理原则 |
|---|---|---|
| 全局位姿修正跳变 | `map` 位姿突变、创新量/残差异常、规划路径不连续 | 确认局部控制使用的连续参考系；检查地图定位、时间戳和 TF 所有权；是否暂停、限速或停车由风险评估和产品安全策略决定 |
| 几何退化或视觉跟踪退化 | 匹配残差增大、信息矩阵病态、特征数下降、协方差上升 | 检测退化并评估辅助观测是否真正增加可观性；不应无条件依赖轮计“盲走”通过 |
| 全局定位丢失 | 估计协方差/创新异常、粒子分布发散、重定位超时 | 进入经验证的受限行为，按产品风险策略减速/停止并执行重定位；不得把未经验证的低速行驶当作通用兜底 |
| 时间同步或 TF 错误 | TF extrapolation、观测延迟、残差周期性增大 | 检查时钟来源、传感器时间戳、缓存、外参和消息 frame_id；修复后重新做时延/同步验证 |
| 多机器人地图不一致 | 同一地点的位姿偏差、地图版本或基准不同 | 管理地图版本、坐标 datum、地图间变换、传感器标定与时间基准；共享残差只是诊断线索，不是充分的同步机制 |

定位异常后的具体动作涉及速度、制动、人员暴露和运行场地，必须由风险评估、系统安全需求和验证结果确定。本文不提供通用“失联后继续行驶”或固定停车距离。

## 7. AMCL 工作流（ROS 2 / Nav2，二维已知地图）

AMCL（Adaptive Monte Carlo Localization）是基于粒子滤波的概率定位模块，用二维激光扫描在已知地图中估计机器人位姿。它不是通用 3D SLAM，也不负责构建未知地图。

### 7.1 数据流

- **输入**：地图（通常为 `nav_msgs/OccupancyGrid`）、二维激光扫描（`sensor_msgs/LaserScan`）和 `odom→base_link` 运动变换；还需要初始位姿或可用的重定位初始化机制。
- **估计**：运动模型根据里程计更新粒子假设，激光传感器模型根据地图匹配评价粒子权重，再按粒子滤波策略更新分布。
- **输出**：地图坐标系下的位姿与协方差；当 `tf_broadcast=true` 时，AMCL 发布 `map→odom` 变换。Nav2 版本的具体 topic 名称与消息类型以目标发行版文档为准。
- **生命周期**：Nav2 AMCL 节点使用 Lifecycle Node 生命周期接口；它不是导航行为树里的一个 BT action 节点。

### 7.2 参数不能照抄

Nav2 AMCL 参数包括运动模型噪声项（如 `alpha1…alpha5`）、最小/最大粒子数、激光模型、更新运动阈值、恢复行为和 `transform_tolerance` 等。官方示例默认值只适合作为配置入口，不是任何底盘/雷达组合的通用最佳值。调参应基于目标地图、激光型号、扫描频率、里程计误差、动态环境和计算预算，并保留评测数据。

### 7.3 五步直觉

1. 初始化：根据已知初始位姿或全局重定位机制生成粒子假设。
2. 预测：用里程计运动模型传播粒子。
3. 观测更新：按激光扫描与地图的匹配程度计算权重。
4. 重采样/恢复：按滤波器实现与参数更新粒子分布，必要时引入恢复样本。
5. 输出：由粒子分布计算位姿估计和不确定性。

粒子数量、重采样间隔和恢复参数受地图规模、运动模型、激光模型、失定位方式与算力约束影响，不存在跨系统适用的固定参数组合。

## 8. 双 EKF 是可选架构模式，不是“高级导航标配”

在需要同时维护连续局部估计和全局修正时，可以使用两个状态估计器：

| 实例 | world_frame | 输入示例 | 可能输出 | 约束 |
|---|---|---|---|---|
| 局部估计器 | `odom` | 轮里程计、IMU、视觉里程计等连续观测 | `odom→base_link` | 不应融合会产生离散跳变的全局位置修正 |
| 全局估计器 | `map` | 局部运动信息 + GNSS/地标等全局绝对观测 | `map→odom` | 需要另一个权威来源持续提供 `odom→base_link` |

实现细节：

- 两个实例不是必须条件。单一 EKF、AMCL + 局部里程计、VIO、图优化或其他架构在不同产品中都可能合适。
- 如果 AMCL 已负责发布 `map→odom`，不要再让全局 EKF 同时发布同一 TF 边；若采用全局 EKF，则必须明确由哪个定位源提供其绝对观测。
- “局部规划器用 odom、全局规划器用 map”是常见移动底盘设计模式，具体消费者与坐标系由 Nav2/其他导航栈配置决定。
- 只有在 TF 所有权、时间戳、初值、协方差、延迟数据和异常切换均经过验证后，才可将该架构用于产品。

## 9. 工程验收建议

一次可复核的融合定位验证至少应定义：

1. **系统边界**：机器人构型、传感器准确型号/固件、安装外参、软件版本/commit、坐标基准和目标环境。
2. **数据质量**：各传感器频率与丢包、时间同步误差、协方差来源、标定记录、TF 完整性。
3. **精度与一致性**：APE/RPE 或任务相关误差、统计方式、真值来源、对齐方式、置信区间/分位数。
4. **动态性能**：启动/重定位时间、端到端延迟、CPU/GPU/内存、长期漂移和温度工况。
5. **失效验证**：遮挡、打滑、动态物体、GNSS 失锁、传感器断连、时钟偏移、地图变化和恢复行为。
6. **安全边界**：定位质量下降时的报警、限速/停止策略、操作者提示、故障记录与复位条件。

没有目标设备、数据集、真值或测试环境时，只能给出方法与验证计划，不能宣称已经达到某个定位精度或通过安全验证。

## 12. 本轮定向复核与未关闭事项（2026-11-03）

本轮重点纠正以下高风险表述：

- 删除编码器、IMU、LiDAR、相机和 GNSS 的通用采样频率与定位精度区间；改为逐型号、逐工况核验。
- 纠正 `map` 是绝对坐标、`odom` 永不漂移和固定频率发布等过度简化说法；按 REP-105 解释坐标系语义。
- 纠正“map→odom 只由定位层发布”和“双 EKF 是高级导航标配”；明确每条 TF 边唯一权威发布者，并说明双 EKF 是可选模式。
- 纠正“不能重复融合相同维度数据”的过度概括；重点审查信息是否来自同一底层测量、误差是否相关、协方差是否可信。
- 纠正 `navsat_transform_node` 的简化解释，明确其输入/输出接口和 GNSS 坐标基准约束。
- 删除“冻结 map→odom 后低速盲行”“预存盲区靠轮计通过”等未经产品风险评估支持的兜底建议。
- 纠正“AMCL 深度集成在行为树”的描述：Nav2 AMCL 是 Lifecycle Node，不是 BT action 节点。
