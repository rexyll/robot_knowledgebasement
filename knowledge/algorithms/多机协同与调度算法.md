# 多机协同与调度算法（MRTA / MAPF / Fleet Traffic）

> 多机器人系统至少包含两个彼此耦合、但不可混为一谈的问题：**任务分配与调度**（哪台机器人在何时执行哪个任务）以及**交通/路径协调**（机器人如何在共享空间中无冲突运行）。实际车队还要处理异构能力、充电资源、基础设施、通信异常、任务依赖、人工优先级与安全状态。分配层给出“谁做什么”并不代表路径已无冲突；MAPF 得到无碰撞图路径，也不代表底层机器人能够直接跟踪。

## 1. 问题分层和数据模型

| 层级 | 主要决策 | 典型输入 | 输出 |
|---|---|---|---|
| 任务分配（MRTA） | 任务给哪台机器人、任务间是否可并行/协作 | 机器人能力、位置、电量、任务类型、优先级、截止时间 | 机器人—任务指派 |
| 任务排序/车辆路径（VRP） | 每台机器人按什么顺序执行任务、如何安排取送货/时间窗 | 路网距离/时间、容量、服务时间、任务依赖、时间窗 | 多站点访问顺序与时间计划 |
| 多智能体路径规划（MAPF） | 多个 agent 在图/离散时间模型下怎样无冲突到达目标 | 路网、起终点、障碍、冲突模型、代价目标 | 每个 agent 的时空路径 |
| 交通管理/资源预约 | 哪个机器人何时占用走廊、路口、电梯、门和窄道 | 预约表、预计轨迹、实际位置、设施状态 | 时空资源预约、冲突协商与通行授权 |
| 车队执行与恢复 | 如何下发、监控、重规划和处理故障 | 机器人状态、任务状态、通信/定位质量 | 任务状态转换、重规划、恢复/人工接管 |

推荐先统一核心实体：
- **Robot/Fleet**：机器人 ID、所属车队、位置/速度、运动模型、footprint、载荷、电量、健康状态、可执行技能和地图/坐标版本。
- **Task**：任务 ID、取货/送达/作业点、能力需求、时间窗、优先级、截止时间、服务时长、先后依赖、取消/暂停策略。
- **Resource**：路段、交叉口、窄道、门、电梯、充电桩、工位、缓冲区；定义容量、方向、占用区间、互斥规则与失效状态。
- **Plan/Reservation**：分配结果、预计路线、时间区间、版本号、租约/过期规则、冲突状态和提交确认。
- **Execution/Event**：机器人实际位置与任务阶段、确认/拒绝、迟到、阻塞、故障、人工干预、恢复与审计事件。

**时间和空间约定必须一致**：定义地图版本、坐标基准、机器人时间戳/时钟同步、路段/资源 ID、预计到达时间、预约时间窗和不确定性裕度。不同车队共享空间时，不能只共享任务 ID 或二维位置而忽略坐标、footprint、定位质量和时间基准。

## 2. 多机器人任务分配（MRTA）

### 2.1 常用模型与算法

| 方法 | 决策机制 | 适用情况 | 主要边界 |
|---|---|---|---|
| 贪心/最近可用机器人 | 对每个任务选择当前代价最低的可行机器人 | 低复杂度基线、任务独立、需要快速响应 | 局部决策可能破坏后续全局效率；需要防止机器人/任务饥饿与频繁重分配 |
| 线性指派/匈牙利方法 | 对机器人—任务成本矩阵求最小总成本一对一匹配 | 一轮内每台机器人至多接一个任务、每个任务至多分给一台机器人等简单指派 | 不直接解决多站点任务排序、容量、先后依赖、时间窗、多个机器人协作或持续在线调度；常见 O(n³) 是经典方阵指派算法的复杂度表达，不代表所有扩展问题的求解复杂度 |
| 最小费用流 | 将任务分配写成网络流 | 有单位容量、供需和费用结构可表达的分配问题 | 更复杂的逻辑约束/非线性成本不一定能直接表达 |
| MILP / CP-SAT | 以二进制/整数变量建模指派、容量、任务依赖、时间窗和资源约束 | 约束组合多、需要明确优化目标与可行性 | 规模扩大后求解时间可能增长；设置时限时必须区分 OPTIMAL、FEASIBLE、INFEASIBLE、UNKNOWN 等状态 |
| 拍卖 / 市场机制 | 机器人按任务收益/成本出价，由中心或分布式规则确定赢家 | 需要将机器人本地代价、能力和自治性纳入分配 | 出价函数、冲突消解、任务捆绑、消息时序和通信故障决定结果；不能简单视为“弱通信下天然可靠” |
| CBBA（Consensus-Based Bundle Algorithm） | 每个 agent 构建任务 bundle 并通过本地通信一致性解决竞标冲突 | 分布式任务分配、任务可并行且可用收益函数表达 | 收敛和性能保证依赖论文中的评分/收益函数等假设；冲突自由的任务指派并不意味着机器人路线无碰撞 |

Google OR-Tools 的官方任务分配指南将简单 assignment 定义为 worker—task 成本匹配；对更一般的分配问题推荐 MIP/CP-SAT，并另有含任务规模/容量约束的 Generalized Assignment 示例。这说明“匈牙利 / CP-SAT / VRP”不是可以互换的同一个求解问题。

### 2.2 成本函数怎么建模

一个可解释的分配成本可以由以下量构成：

`cost(robot, task) = estimated_travel_time + service_time + energy_cost + lateness_penalty + capability_mismatch_penalty + congestion_cost`

实际目标不一定是简单加权和；有时应把安全/能力/时间窗作为硬约束，将路程、能耗和负载均衡作为软目标。建模时要明确：

- **可行性过滤**：机器人是否具备载荷、末端执行器、温度/洁净等级、楼层/电梯权限和任务技能。
- **时间代价**：路程不能简单用欧氏距离，宜来自可通行路网/导航估计，并纳入服务时间、等待和拥堵不确定性。
- **能耗与回充**：估计剩余任务能耗、回充路线能耗、充电占用与电池健康状态；BMS 限值和电芯策略优先于通用 SOC 区间。
- **公平与防饥饿**：考虑任务等待时间、长期未被分配的任务和机器人负载，避免短期高收益任务永久挤占低优先级任务。
- **重分配抑制**：引入切换成本、最短保持时间或任务状态门槛，避免估计值微小变化导致任务在机器人之间反复抖动。
- **执行中任务保护**：在途取货、已开始操作、载货运输或需要双机协同的任务，取消/迁移需要经过明确的状态机和恢复流程。

### 2.3 一次性指派、在线派单与 VRP 的区别

- **一次性指派（assignment）**：为一批任务和机器人求一次匹配，通常不包含每台机器人多站点访问序列。
- **在线派单（dynamic dispatch）**：新任务、延误、故障和电量变化不断到来，需要增量重优化，并管理已承诺的任务。
- **VRP / VRPTW**：决定多台车辆访问一组节点的路线/顺序，考虑车辆容量、需求、服务时长和时间窗等约束；通用 VRP 属于组合优化问题，通常需要接受计算时间、目标质量和问题规模之间的权衡。
- **取送货/多阶段任务**：还需处理 pickup-before-delivery、任务前置/后续依赖、同车/不同车约束及多机器人协作。

OR-Tools Routing 提供 VRP、容量约束、时间窗等建模组件；求解器返回的结果应检查状态、目标值、时间窗和任务约束，不应把找到可行解等同已证明最优。

## 3. 多智能体路径规划（MAPF）

MAPF（Multi-Agent Path Finding）研究多个 agent 在共享图上从各自起点到目标的无冲突路径。经典离散 MAPF 通常假设 agent 在离散时刻占据图节点、可以等待，冲突模型包括顶点冲突、边交换冲突等；不同论文对跟随冲突、环冲突、目标占用、不同速度和不同时间步的定义可能不同。

### 3.1 目标函数

- **Sum of Costs（SoC）**：所有 agent 路径代价之和。
- **Makespan**：所有 agent 完成时间中的最大值。
- **Flowtime / 服务目标**：可能涉及等待、到达时间、吞吐和任务完成率。
- **资源/安全约束**：对关键通道、交叉口、门、电梯和充电位增加容量/时间窗限制。

最优性只针对明确定义的图、时间步、冲突模型、代价函数和目标约束成立。忽略车体尺寸、转弯半径、加减速度和制动距离的抽象 MAPF 路径，不能直接视为真实机器人运动轨迹。

### 3.2 代表算法

| 方法 | 核心机制 | 性质与适用边界 |
|---|---|---|
| 优先级规划（Prioritized Planning） | 按优先级顺序规划，每个后续 agent 避免已规划路线/时间占用 | 计算简单、可快速得出部分解；通常不完备，也不保证全局最优；优先级次序会显著影响能否找到解 |
| CBS（Conflict-Based Search） | 高层冲突树添加约束，低层为受约束 agent 规划路径 | 在经典 MAPF 假设、完整低层搜索及指定代价目标下可求最优解；最坏情况下搜索树可能指数增长 |
| ECBS（Enhanced CBS） | 使用 focal search 等机制限制搜索次优程度 | 可在算法假设下提供有界次优解；w 是次优界参数，不是跨场景通用“实用范围” |
| SIPP（Safe Interval Path Planning） | 在动态占用时间轴上搜索节点的安全时间区间 | 可作为带动态障碍/预约的单 agent 规划器或 MAPF 子程序；依赖安全区间构造、时间模型和运动约束 |
| LaCAM | Lazy Constraints Addition Search，用两层搜索及延迟约束生成来寻找 MAPF 解 | 原论文描述为 complete、sub-optimal；在经典图 MAPF 设定下可快速找到解，但不应简单标注为“新 SOTA”或“全局最优” |
| LaCAM* | LaCAM 的 anytime 变体，在已有可行解后继续改善 | IJCAI 2023 论文指出在累计转移代价等条件下 eventually optimal；具体最优性条件需按论文定义，有限时间返回的当前解未必已最优 |

**注意**：CBS 的“最优”与 LaCAM 的“完备”不是同一个性质；完备是指在其假设下若存在解则算法能找到解，最优还需保证解的代价达到全局最小。ECBS 的有界次优也不能简化为某个固定参数范围在所有任务上都实用。

### 3.3 运动学可行性

真实移动机器人需把图上的 MAPF 扩展到运动学/时空约束：

- 将旋转、倒车、等待和转弯动作建模为运动原语或状态扩展；
- 对机器人 footprint 做连续空间碰撞/扫掠体检查，不能只检查中心点是否处于不同节点；
- 根据速度、加减速度、制动距离、定位误差和通信时延为时空预约增加裕度；
- 处理不同车速、不同长度、不同载荷和不同停车/启动时间；
- 对定位偏差和延迟造成的“计划时间 vs 实际时间”差异设置监测与重新协商。

有研究专门将 turn action 等运动约束纳入 MAPF，指出忽略运动学约束后再事后修正，可能增加路线代价并降低搜索扩展性。故经典 MAPF 结果不应直接作为阿克曼、重载叉车或非圆形底盘的可执行保证。

## 4. 交通管理、路网与资源预约

在结构化建筑/仓储环境中，可以把地图抽象成 waypoint—lane 图，并为走廊、交叉口、门、电梯、工位和充电桩建立资源占用模型。这是一种常见的工程架构，不代表所有厂商或所有百台级车队都采用同一实现。

### 4.1 资源预约的基本结构

每一条资源预约至少包含：

- 资源 ID、容量/方向/互斥规则；
- 机器人/车队 ID、任务 ID、地图版本；
- 预约开始/结束时间、预计通过时间、时间不确定性裕度；
- 预约版本、确认状态、续约/取消状态；
- 实际进入/离开事件、定位质量与异常状态。

常见资源模型：
- **路段/走廊**：单向或双向、单车占用或分区通行、允许跟随距离；
- **路口/汇合区**：互斥冲突区、预约顺序、占用容量；
- **窄道/单通道**：入口等待区、占用权、对向冲突和退出确认；
- **门/电梯**：设备状态、楼层、请求/授权/进出确认、异常停机；
- **工位/充电桩**：设备容量、任务服务时长、排队位置和释放确认。

**预约超时不等于资源已释放。** 如果机器人可能仍占用窄道、门、电梯或工位，不能仅因租约到期就让另一机器人进入。释放应结合实际位置/退出确认、通信状态、资源传感器和故障恢复状态；无法确认时应进入保守锁定/人工处理路径。

### 4.2 死锁和拥堵处理

- **预防**：资源按统一顺序申请、单向通道/会车点设计、保留缓冲区、避免机器人带着不可释放的资源请求另一资源。
- **检测**：构建等待图，分析循环等待；同时检测资源预约过期、机器人停滞、实际位置与预测路线偏离。
- **恢复**：选择安全退让/回退/等待/任务撤销或人工介入；涉及物理占用的锁释放必须验证机器人确已离开。
- **稳定性**：对重规划设置节流、滞回和最小计划保持时间，避免拥堵状态下大量机器人同步重规划造成“重排风暴”。
- **通信故障**：区分中心失联、车队管理器失联、单车失联和时间同步异常；定义状态上报心跳、预约租约、命令幂等、版本冲突和恢复对账机制。

死锁次数、拥堵率和重规划时间可以作为运营指标，但不应写成跨产品固定 KPI。建议记录单位运营小时/任务数的死锁与人工恢复率、资源排队时间 P50/P95、任务延误、吞吐量、利用率、机器人停滞时长和计划稳定性，并结合安全目标分别管理碰撞、险情和保护停机。

## 5. Open-RMF：异构车队交通协同参考架构

Open-RMF 是 ROS 2 生态中的开放框架，关注异构机器人车队和共享设施的互操作、交通调度/协商及任务分派。

核心组件/概念：
- **Traffic Schedule**：保存参与者计划执行的未来轨迹，监测空间—时间冲突；计划可因延误、取消或路线变更而更新。
- **Negotiation**：出现冲突时，相关 fleet adapter 提交可行 itinerary proposal，并在协商规则/裁决逻辑下确定计划。
- **Fleet Adapter**：连接厂商车队 API 与 RMF，提供机器人状态、任务能力/可用性、导航命令和门/电梯等设施交互。
- **Traffic/Nav Graph**：用 waypoint 与 lane 表示允许的交通路线；图的覆盖性、方向、门/电梯属性和坐标变换需要现场配置。
- **Task Dispatch**：向车队询问可执行机器人/报价，再按调度规则选择车队并下发任务。

Open-RMF 不会自动适配所有机器人：每个车队仍需实现 adapter 并对接厂商任务/导航 API、状态、时间和坐标系。官方文档指出其 traffic schedule 记录的是预期轨迹；冲突出现后通过 negotiation 进行协调。它是交通协调框架，不是独立安全认证系统，也不保证任意底盘都能严格按路径跟踪。

## 6. 充电与能源调度

电量不是一个固定 SOC 阈值触发的 if-else，而是车队任务规划与可用性约束的一部分。

建议考虑：
- 剩余电量/电池健康、温度、充放电限制和 BMS 告警；
- 当前载荷、路线长度、地面/坡度、任务类型与估算能耗；
- 回充路线是否可达、充电桩类型/功率、桩位占用和排队；
- 任务截止时间、剩余任务与充电等待的机会成本；
- 故障备用车、任务转移和充电失败恢复策略。

“机会充电”适合在空闲或任务间隙补能，但是否值得充电取决于充电时间、后续任务、电池策略和充电资源容量。不要将 SOC 20–80%、充电排队 2–3 台或夜间满充作为所有电池化学体系、BMS 与运营策略的通用准则；应遵循电芯/电池包厂商规格及产品使用策略。

## 7. 评测和验收

多机系统的评测不能只看单机导航成功率或总吞吐量。建议分层记录：

| 层级 | 指标 | 测试重点 |
|---|---|---|
| 任务分配 | 分配可行率、任务完成率、分配耗时、重分配次数、任务等待时间 | 异构能力、任务依赖、时间窗、优先级和任务到达突发 |
| 路径协调 | 无冲突规划成功率、SoC/Makespan、规划耗时、超时率 | 顶点/边冲突、目标占用、窄道、交叉口和图变化 |
| 交通运行 | 资源利用率、排队时长、拥堵持续时间、死锁/人工恢复事件 | 资源预约、双向会车、电梯/门异常、通信中断和预测轨迹偏差 |
| 车队运营 | 任务吞吐量、任务时长 P50/P95、空驶率、充电等待、设备利用率 | 不同车队规模、班次、任务负载、充电桩配置和故障车比例 |
| 安全与可靠性 | 碰撞/险情/保护停机、急停响应、失联行为、定位偏离与人工接管 | 独立安全链、资源占用不明、心跳丢失、时钟错误和故障恢复 |

测试报告至少记录：地图/路网版本、机器人数量与车型/footprint、任务集与任务到达分布、算法/求解器版本、参数、随机种子、通信条件、硬件、运行时长、重复次数、统计口径、失败日志和人工干预。仿真中无碰撞不等于真实场地安全；实机测试还需覆盖定位误差、制动距离、通信抖动、载荷、地面摩擦和设施响应。

## 9. 本轮定向复核与未关闭事项（2026-11-03）

本轮纠正：

- 删除最近邻 O(NM)、匈牙利 O(N³) 等被当作所有扩展问题的通用复杂度描述；限定经典简单指派模型。
- 将 assignment、在线派单、VRP/VRPTW 和多机器人协作任务区分；补充容量、时间窗、先后依赖及可行/最优求解状态边界。
- 删除任务批处理 1–5 秒、效率提升 10–30% 等无测试条件的数字。
- 纠正 CBBA“弱通信友好”的无条件描述，补充收敛依赖收益函数/评分假设；冲突自由任务分配不等于无碰撞路线。
- 纠正 CBS/ECBS/LaCAM 算法性质：CBS 仅在经典 MAPF 假设与指定目标下求最优；ECBS 有界次优；LaCAM 原始算法 complete/sub-optimal；LaCAM* 在论文条件下 eventually optimal，不能笼统称原始 LaCAM 为 SOTA/最优。
- 删除“百台以上几乎都用路网+预约表”的行业普遍断言；将路网+时空预约作为一种常见工程架构并明确其适用边界。
- 补充真实机器人 footprint、运动学/制动约束和时间不确定性；指出离散 MAPF 路径不是可直接执行的机器人轨迹。
- 删除预约过期后强制释放资源的危险暗示，要求基于实际占用/退出确认、安全状态和人工恢复决定是否释放。
- 纠正统一死锁=0、拥堵率 15%、SOC 20–80%、充电队列 2–3 台和夜间满充的通用化建议；改成可测量的运营指标和电池规格约束。
- 增加 Open-RMF 的 Traffic Schedule、Negotiation、Fleet Adapter 与导航图作用，明确框架仍需车队适配与设施集成，且不等于安全认证。

## 10. Open-RMF 集成接口与发行版快照（2026-11-05）

前述架构说明还需要落到“RMF 如何与既有车队控制系统对接”。Open-RMF 的 Fleet Adapter 是车队边界适配层，不是机器人底盘驱动本身，也不是替代厂商 FMS 的通用控制器。

### 10.1 Fleet Adapter 的责任与接口契约

依据 Open-RMF 官方 Fleet Adapter 教程，Adapter 至少承担以下交互责任：

- **向 RMF 提供状态**：机器人位置、当前任务/执行状态、电池状态及车队可用性；状态上报必须注明坐标系/地图版本、时间戳、机器人 ID 和数据新鲜度。
- **接收任务并参与派单**：RMF 请求车队报告可执行性/可用性，Adapter 按能力、任务状态和车队规则响应；获选后将导航或任务指令转换为厂商接口可理解的命令。
- **控制接口映射**：将 RMF 的导航、停止和任务动作映射到厂商 API；把命令确认、拒绝、执行中、完成、失败、取消及超时映射回统一状态机。
- **设施交互**：在地图/导航图和业务流程定义的基础上协调门、电梯、充电或其他设施；Adapter 需对接设施接口并验证真实状态，不能仅凭发出请求就假定设施已就绪。
- **异常和一致性**：定义命令幂等键、任务/计划版本、重复/乱序消息处理、心跳超时、状态过期、断网恢复对账和人工接管路径。

官方 Python 教程使用 REST API 作为示例 Fleet Manager 接口，并明确可替换为项目所需的其他 API；模板字段和实现必须保持一致，修改配置字段时也要同步修改解析代码。因此，教程中的 REST、示例机器人参数、发布频率和充电阈值都是演示配置，不是跨厂商默认值或推荐产品指标。

### 10.3 调度/交通/单机导航的责任边界

- **任务分配层**决定任务由哪个车队/机器人承接；竞价/报价策略取决于任务能力、可用性和代价模型。
- **Traffic Schedule / Negotiation**处理参与者提交的预期轨迹与时空冲突协商；计划轨迹不是机器人实时占用的直接测量，也不保证底层控制器严格跟踪。
- **单机导航栈**负责局部障碍感知、避障、轨迹跟踪和执行器控制。RMF 交通协商不能代替 Nav2/厂商导航系统的局部避障。
- **独立安全系统**负责风险降低所需的安全功能、保护停机和安全状态；RMF Adapter、ROS 2 topic/service、Traffic Schedule 或调度优先级不能代替安全 PLC、安全激光扫描仪、安全制动链或经验证的安全控制设计。

对无法动态改变路线、只能沿预定义图运行或能自主绕行的异构机器人，Adapter 能力模型和交通参与方式必须分别验证；不可把所有车队假设成同等控制能力。地图坐标转换、footprint、速度/加速度限制、可逆行能力、充电模型、任务能力和设施接口都应逐型号/逐车队配置并实测。

### 10.4 集成验收检查项

1. **状态闭环**：注入位置丢失、时间戳过期、SOC异常、任务状态跳变，确认调度端不会继续使用陈旧状态做无条件承诺。
2. **命令闭环**：测试 navigate/stop/action 的接受、拒绝、重复、乱序、超时、取消及重启恢复；验证命令幂等与任务状态对账。
3. **坐标和地图**：用已测量的控制点验证坐标变换、楼层/地图切换、航向角、地图版本和机器人 footprint。
4. **交通协商**：构造对向窄道、交叉口、计划偏离、通信延迟、机器人停车和参与者退出等场景，记录计划冲突、协商结果及实际资源释放证据。
5. **设施联动**：门/电梯/充电桩分别验证请求、授权、状态反馈、超时、故障和人工恢复；演示模拟器通过不能替代现场设施验收。
6. **版本兼容**：在锁定的 ROS 发行版和 RMF commit 上执行构建、API/消息兼容、集成回归和升级回滚测试，并归档依赖清单与结果。

**未关闭事项**：本次仅依据 ROS Index 与 Open-RMF 官方教程补充发行版快照和接口责任边界。未构建 Jazzy/Kilted/Lyrical 任一 RMF 工作区，未运行 fleet adapter、traffic schedule、negotiation 或任务派发；未接入厂商 API、真实机器人、门/电梯/充电设施和现场地图，未执行多车并发、断网/乱序、死锁恢复或安全验证。所有版本信息均需在具体部署时重新锁定；本文不构成互操作认证、性能保证或产品验收。
