## 4. 初步缺口清单

### 4.1 面向零基础学习者

- 没有统一的 A0 零基础入口和能力自测。
- 数学、物理、编程、Linux、机械识图、CAD、电路和工程测量缺乏系统先修课程。
- 现有 90 天路线默认具备编程基础，且时间/预算假设需要明确适用范围。
- 缺少按知识点组织的练习、题目、示例答案、工具清单和能力验收。

### 4.2 从工程样机到量产

- 现有 AMR 主线主要覆盖样机设计、集成、导航和基本回归。
- 缺少完整的需求冻结、设计评审、配置基线和跨专业接口控制。
- 缺少 EVT/DVT/PVT 阶段门和阶段评审标准。
- 缺少 DFM/DFA/DFT、MBOM、工艺流程、工装、作业指导书和产线测试工位。
- 缺少 PFMEA、Control Plan、IQC/IPQC/OQC、MSA、SPC、良率、返工、CAPA 和批次追溯体系。
- 缺少量产放行、供应商质量、客户交付包、售后服务、保修、备件和 EOL 退役的完整主线。

### 4.3 技术板块

- 操作、抓取、末端执行器和机械臂实践内容较弱。
- 电子电路、PCB、线束、嵌入式固件/BSP/驱动、通信网络等仍需拆分深化。
- 软件工程、接口设计、配置/发布、可观测性、软件供应链和安全工程需要系统化。
- 医疗、无人机、农业、建筑、矿业、空间、水下、外骨骼和软体机器人等类型需进一步扩展专题与适用法规。
- 标准法规、产品认证、网络安全、隐私和 AI 治理必须按地区/产品范围建立正式矩阵。
- BOM 需要区分 EBOM/MBOM/SBOM/服务 BOM，并连接物料变更、供应商质量、生产成本和生命周期成本。

### 8.1 已具备可复用基础的领域

- **机器人类型**：工业、协作、移动、仓储物流、清洁、服务、人形、足式/无人机、医疗和特种机器人已有概览文章；普遍包含分类表、技术栈、行业用途和上下游链接。
- **传感与执行**：LiDAR、深度相机、IMU、编码器、毫米波/超声、电机、驱动器、减速器和充电/能源已有原理与参数内容。
- **算法**：SLAM、激光/视觉 SLAM、融合定位、卡尔曼滤波、路径规划、局部避障、轨迹优化、视觉感知和学习算法已有主题文章。
- **软件与系统**：ROS/ROS 2、Nav2、实时嵌入式、构建 CI、云端通信、RMS、仿真、AMR 架构及建图/导航/功能安全流程已有实践性内容。

### 8.2 内容质量的共性问题

1. **教学层次不统一**：不少文章有分类、参数和工程经验，但缺少明确先修知识、分步讲解、完整推导、练习、答案/检查标准和常见错误。它们适合工程师速查，不足以让 A0 新手独立学习。
2. **来源到事实的映射不足**：文章通常在末尾列厂商资源或链接台账编号，但具体参数表格行、市场判断和量产声明不一定能对应到直接来源。后续应要求关键数值和安全/法规结论逐项指向证据。
3. **示例与通用规范边界不清**：样机 BOM、典型电源树、固定联调阈值和现场剧本中的数字需要标记平台、工况、样本和是否仅为教学示例；不得自动推广为通用产品验收标准。
4. **知识主要围绕 AMR/ROS 展开**：这是当前积累最完整的路线，不代表工业臂、协作臂、医疗、无人机、足式、人形、软体、水下、农业和特种机器人已达到同等深度。
5. **生产导入内容薄弱**：现有 BOM 偏教学样机采购快照；测试偏研发联调；未形成完整 MBOM、工艺路线、工装、作业指导书、PFMEA、Control Plan、MSA/SPC、过程能力、批次追溯、CAPA 和产线放行资料。
6. **知识目录存在占位与混合归属**：manipulation、troubleshooting 目前主要是 README 占位；software 中混合 OS、嵌入式、网络、云和车队主题，需按 00-02 统一边界后渐进拆分。
7. **元数据 Schema 与写作标准需要同步**：现有 parser 只支持部分扁平 YAML；新增嵌套元数据前必须验证解析器与测试，不得把概念 Schema 当作已支持功能。

### 11.1 第二轮发现

1. **车队与系统流程已有可用基础**：多机任务分配、OTA、调度时序和云端流程已有系统级文章，但仍需对协议版本、性能指标和业务边界核验。

3. **产业与市场数据需单独审计**：厂商名录、产业链、趋势文章包含市场份额、销售、产品参数和量产声明；每个关键数字需建立“主张—来源—时间—口径”对应。
4. **标准法规需逐条适用性核对**：现有标准列表可作为检索入口，但不能仅凭列表断定某标准适用或产品已合规；需要官方现行版本、地区、产品边界、强制属性和认证路线。

## 13. 新发布互操作标准及北美移动机器人安全标准更新（2026-11-03）

### 13.1 新标准 ISO 21423:2026

ISO 官方页面显示 ISO 21423:2026（Robotics — Industrial mobile robots — Communications and interoperability）于 **2026-10** 发布，版本状态为 Published。其范围规定共享工业环境内两个或更多参与方之间的通信要求，参与方包括工业移动机器人（IMR）、IMR 车队管理器（IMRFM）以及其他机器、设备和应用；官方列举的场景包含 ERP、升降机、报警系统和自动门（链接台账 #158）。

**范围限制必须一并记录：** ISO 官方明确该标准不属于安全标准，不包含安全要求，也不覆盖导航要求。因此它补充的是互操作通信层，不替代 ISO 3691-4、ANSI/A3 R15.08 等安全规范，也不能证明导航性能或安全功能合规。与 VDA5050 或各厂商 API 的实际映射尚未完成，不能宣称完全兼容、互相替代或谁取代谁。

已将 ISO 21423:2026 加入标准索引、RMS 知识页，并在 10-07 和 17-07 增加正式文本研究、接口映射和多厂商互操作验证任务。

## 24. P1 ROS 2 QoS、实时性、组件组合与中间件主张定向复核（2026-11-03）

本轮对 knowledge/software/ROS与ROS2.md 中影响软件架构、通信互操作与控制时序的主张开展官方文档定向复核。来源登记于链接台账 #186–#194。此次处理仅覆盖下列主张，不代表全文每个 API、软件包、版本和产品适配声明均已审查。

### 24.1 QoS 兼容性纠错

ROS 2 QoS 的兼容性按发布者 OFFERED 与订阅者 REQUESTED 判定，而不是要求两端设置完全相同。官方可靠性兼容表给出的结果是：

| 发布者 Reliability | 订阅者 Reliability | 兼容性 |
|---|---|---|
| Best Effort | Best Effort | 是 |
| Best Effort | Reliable | 否 |
| Reliable | Best Effort | 是 |
| Reliable | Reliable | 是 |

原文“Reliable 发布者 + BestEffort 订阅者会直接收不到数据”与官方表相反，已纠正。补充默认 Reliable/Volatile 与 SensorData BestEffort/较小队列的语义区别；transient_local 用于有意保留历史样本的场景，不能把它不加区分地当作运动指令的默认 durability。瞬时指令的迟到重放、时效性、watchdog 和失效安全仍须做系统设计与验证。

### 24.2 实时性边界

删除“ROS 2 支持 executor 级实时”的笼统表达。实时计算的核心是指定任务在 deadline 内完成并限制 jitter，而不是仅有较低平均延迟。ROS 2 官方实时教程强调控制循环中避免 page fault、动态内存分配/释放和可能无限阻塞的同步操作，并通过内存锁定、调度权限、latency 与 page-fault 统计开展验证。ROS 2 Design 背景进一步强调实时 OS 与确定性用户代码缺一不可。

因此，使用 ROS 2、选择某个 executor 或启用 PREEMPT_RT 本身均不能自动证明硬实时。产品需要给出目标周期、允许最大抖动、最坏执行时间、负载/干扰、CPU 亲和性/优先级、内存策略和实测数据；安全相关快速保护链路还应根据风险分析决定是否由独立硬件/安全控制器实现。

### 24.3 Composition 与零拷贝边界

将“组合节点等于共享内存零拷贝、点云吞吐提升 3–5 倍”这一没有可迁移基准条件的表述删除。官方 Composition 文档说明组件可以部署在同一进程或独立进程，进程布局可在部署时选择；同进程组合可减少部分开销，但会改变进程/故障隔离边界。Intra-process communication 是相关但不同的机制，必须显式启用。官方演示仅在特定 C++ std::unique_ptr 发布/订阅通路展示零拷贝，不支持推广成任意消息类型、任意所有权方式或所有 RMW 都零拷贝。

知识页改为要求在目标负载下测量端到端时延、CPU、内存、消息丢失和故障隔离效果，不再保留通用倍数。

### 24.4 DDS、Zenoh 与平台支持

- 将 rmw_zenoh_cpp 从“DDS 替代/弱网方案”模糊描述改为“映射 ROS 2 RMW API 的 Zenoh RMW 实现”，并记录其设计文档中的 Router/发现拓扑；不能据此推断目标产品部署零配置或自动满足安全要求。
- 删除“Cyclone DDS 多机发现更稳、Wi-Fi 推荐切换”的无条件推荐；要求在实际网络拓扑和目标负载上比较发现时间、吞吐、尾延迟、丢包、断线恢复、CPU/内存和安全配置。
- Fast DDS 作为常见默认 rmw_fastrtps_cpp 的描述保留并明确需要核对具体发行版及安装清单。
- 依据 REP 2000，将 OS、CPU 架构和 RMW 的支持等级按具体 ROS 2 发行版组合检查；Tier 1/2/3 的持续测试强度不同，不能将 Linux/Windows/macOS/RTOS 说成所有发行版的统一保证。
- 将 ROS Noetic EOL 日期更正为 2025-05-31。

### 24.5 其他工程主张处理

- 删除“20 万点/s 固定等于约 20 MB/s”的无数据结构假设换算；改为基于 PointCloud2 实际字段布局、每点字节数、频率和传输封装计算。
- 多机通信问题先检查网卡、VLAN/路由、防火墙、组播、ROS_DOMAIN_ID 和 DDS discovery 配置，再选 Discovery Server、静态 peer 或 Zenoh；不把跨网段场景简单归结为“切换某中间件”。

- Action 仅作为需要反馈/结果/取消语义的长任务接口选项；不把 OTA 升级视为固定的 Action 应用。

- 两篇文章均明确安全功能必须由具体机器边界、预期用途、危险识别和风险评估驱动，不将通用PLr/SIL或保护区数值套用到所有机器人。
- 安全器件文章区分普通导航传感器与安全相关防护装置；要求核对完整型号/订货号、证书、检测能力、响应时间、安装限制、配置及系统级验证。旧版未逐型号核验的nanoScan3、microScan3、OS32C、UAM-05LP性能比较已明确不作为选型依据。
- 功能安全文章区分PLr（所需性能等级）与PL（实现能力），并强调单个器件标识不能推断整机安全等级；普通Linux/ROS/导航代码不因独立进程或处理器而自动成为安全功能。
- 急停、STO、机器停止与维护能源隔离的职责边界已明确；未将STO等同于机械停止或重力负载保持，也未把急停等同于锁定挂牌。
- 两篇文章中的停止距离表达式均标注为简化教学模型，明确实际保护区需按适用标准、制造商资料和最不利工况实测确定；没有将表达式伪装成标准完整公式。
- 未发现本轮可凭文档本身证据确认的明显危险性通用数值承诺。需要进一步独立核实的事项包括标准现行版本/修订状态、具体安全扫描仪证书与型号资料、目标机器人PLr及停止性能；这些不得由本文审查代替。
