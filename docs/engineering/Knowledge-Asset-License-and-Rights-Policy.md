# 知识资产许可证与权利来源治理规范

- 状态：执行中；作为 00-01 全库资产盘点的强制审查规则
- 建立日期：2026-11-15
- 适用范围：Knowledge Vault、Python Toolkit、知识文章、工程案例、代码/脚本/测试、配置、标准与厂商资料、图表/图片/CAD、数据集、模型、历史记录和外部项目内容
- 关联根计划：00-01；Guide G-08、G-11、G-15、G-20；Limit 7、8、10、17、18

> 本规范是仓库内部的发布治理流程，不是法律意见，也不替代权利人授权、律师审查或目标市场法律判断。没有证据的事项必须保持“未知/阻塞”，不得靠目录位置、文件名、来源链接、CI 通过或根目录 LICENSE 推断授权。

## 1. 基本原则

1. **先确认来源和权利人，再判断许可。** 文件存在于仓库、由某位贡献者提交、或能公开访问，都不自动证明本仓库有权修改、复制、公开或再分发。
2. **逐资产、逐来源判断。** 混合内容必须拆分到具体文件、代码块、图表、图片、数据表或模型；不可把一个项目的许可证推广到其依赖、子模块、引用资料或整个目录。
3. **区分版权许可与事实来源。** 参数/事实需要标明来源、版本、工况和核验状态；事实来源引用不能自动赋予转载厂商表格、手册页面、图片或标准文本的权利。
4. **默认链接、不镜像。** 许可或转载权限不明时，优先保存原始 URL、commit、标题、访问日期和独立撰写的分析；不复制完整手册、标准、付费内容、受限 SDK 或外部源码。
5. **贡献者权属不可推定。** “Robot Knowledge Basement Contributors”等集合性版权署名不是贡献者名册，也不证明每位贡献者对所提交文件拥有完整权利或已授权仓库按某许可证发布。
6. **AI 辅助不等于自动拥有版权。** 保留生成工具/人工编辑情况和输入来源；由维护者确认人工贡献、引用来源及适用司法辖区的权利状态，不自动标记为原创或 MIT。
7. **未知即不放行。** 只要权利人、许可、通知义务或分发范围不清楚，该资产不得被标为可再分发，不得因项目整体需要而先复制后补手续。

## 2. 资产类别和最低审查范围

| 类别 | 常见资产 | 必须核验 |
| --- | --- | --- |
| 原创文字/图表/教程 | 技术文章、教程、架构图、工程说明 | 作者与贡献记录、人工原创范围、第三方引文/图片/表格、发布授权 |
| 原创代码/配置/测试 | Python/C++/脚本、CI、配置、测试夹具 | 作者/来源、复制或生成代码、依赖与模板、文件级许可、NOTICE/版权/专利条件 |
| 外部源码/示例 | vendored、复制片段、patch、fork、submodule | 上游 URL 和精确 commit、逐文件许可例外、改动、NOTICE、传递依赖、目标分发方式 |
| 厂商/标准/出版资料 | 数据手册、用户手册、标准、白皮书、论文、网页 | 允许的访问/引用方式、版权声明、使用条款、可否复制表格/图/文字；不确定时只链接 |
| 事实/测量/派生数据 | 参数表、性能数据、测试结果、价格/市场数据 | 采集者、来源、型号/版本/工况、数据授权、个人/商业机密、可复现性 |
| 图片/CAD/模型/音视频/数据集 | 产品图、示意图、机械模型、训练数据、模型权重 | 创作者、来源、许可证、肖像/商标/专利或数据库条件、派生和再分发权 |
| 用户/组织/客户项目材料 | BOM、日志、需求、项目图纸、内部故障记录 | 用户授权、组织/客户授权、保密义务、个人信息/凭证/网络拓扑与脱敏 |
| 历史记录/审计产物 | TaskPlan 历史、审查报告、日志、证据包 | 原作者和提交权限、内含第三方材料、是否包含仅供审查的私有/敏感信息 |

## 3. 根目录 MIT 声明的当前解释边界

截至 2026-11-15，仓库根目录有 MIT 文本，版权字段为 “Robot Knowledge Basement Contributors”；`pyproject.toml` 使用 `license = { file = "LICENSE" }` 并声明 MIT classifier。既有审查同时记录 GitHub repository license detector 返回 `Other / NOASSERTION`。

当前证据只支持以下描述：

- 仓库有一份 MIT 格式的根许可证文本。
- Python 包元数据引用该文件并声明 MIT。
- 不能据此断定全部 Knowledge Vault 文章、标准/厂商材料、历史记录、第三方代码、模型/数据、引用图表或项目案例均由贡献者拥有并可按 MIT 再分发。
- 目前没有完整的贡献者权利名册、逐文件权属记录、全资产许可范围映射或所有第三方资料的授权凭证。

因此，在维护者明确授权范围并逐项审核前，根 MIT 不能被宣传为“全仓库所有内容均为 MIT”。不得为了让 GitHub 自动识别而随意修改 LICENSE、批量添加 SPDX 标记或删除第三方版权信息。GitHub 的 NOASSERTION 是仓库元数据/自动识别状态，不单独证明合法或不合法。

Python Toolkit 与 Knowledge Vault 必须分开描述：Python 包发布时实际包含哪些文件，要以 wheel/sdist 构建清单核实；不能仅凭 `pyproject.toml` 推导所有知识文档都属于 Python 包发布物，也不能推导包发布物内任何第三方文件均已获 MIT 授权。

## 4. 每项资产的登记字段

许可证/权利登记至少包含：

- 精确路径、仓库基线 commit、Blob SHA-256 或 Git Blob SHA、文件类型和内容类别；
- 原始作者/权利人、提交者、贡献或委托关系及授权证据；
- 原始来源 URL、上游仓库/commit/文件路径、取得日期和内容改动；
- SPDX 标识符或权利人许可文本；无法识别时标记 UNKNOWN，不得猜测；
- 第三方代码、图片、表格、数据、文档、SDK、生成内容和依赖的逐项清单；
- NOTICE、版权声明、专利条款、商标/数据库权利、再分发限制和署名要求；
- 许可是否覆盖修改、二次分发、商业使用、目标渠道和衍生作品；
- 审查者、日期、证据位置、结论、阻塞原因和下一步。

Git Blob SHA 只用于固定仓库对象身份，不是权利证明、作者签名或数字签名。

## 5. 状态枚举与放行门

- `UNREVIEWED`：尚无资产级权利审查记录。
- `PROVENANCE_PARTIAL`：来源已部分追溯，但作者、许可或第三方内容仍待审。
- `RIGHTS_EVIDENCE_PENDING`：来源/许可线索已知，仍缺权利人或授权证据。
- `LINK_ONLY`：保留链接和独立分析，不在本仓库复制/再分发原文或代码。
- `REDISTRIBUTION_APPROVED`：权利人、许可范围、通知义务及目标分发方式均有可复核证据。
- `BLOCKED`：存在禁止复制/分发条款、权利冲突或授权缺失。
- `NOT_APPLICABLE`：经审查确认不涉及可主张的第三方权利，仍应记录判断依据。

技术审查状态与许可状态分离。例如，一篇文章已完成 P0 参数边界复核，并不代表其图片、表格、手册摘录和文字转载权已通过。CI/测试通过也不能改变许可状态。只有明确为 `REDISTRIBUTION_APPROVED` 的具体文件/内容片段，才可按记录的范围进入相应发布物。

## 6. 引用、摘录与资料保存规则

- 优先登记官方页面、原始 PDF、规范目录和上游源码 commit 的链接/摘要，不以本地副本替代原来源。
- 只保留解释技术事实所必需的最少摘录，标注原作者/机构、页面/章节、版本、日期和链接；最小摘录也不自动构成许可，具体情况仍需适用法律审查。
- 付费文章、标准全文、商业手册、受限 SDK、第三方图片/模型不得整份复制。许可未明时只链接。
- 对产品参数和事实数据，分别记录来源、SKU/版本、测量条件和核验级别；不得将“引用事实”伪装成可转载原始数据表。
- 外部代码必须先完成 `docs/engineering/External-Project-Integration-Policy.md` 的源码准入门，知识化摘要与源码引入是两条不同路径。

## 7. 当前放行规则和维护责任

1. 新资产进入仓库时，作者必须提交来源、许可和权利人字段；未知项标为阻塞。
2. 审阅者先核验原始来源，再确认权利人/授权，最后评估许可兼容、NOTICE 和目标分发。
3. 混合许可文件应拆分登记；不能仅在目录 README 里写一个统一许可覆盖所有子文件。
4. 文件移动、复制、改写、生成或上游更新后，必须复核来源链并保留旧版本记录。
5. 公开发布前执行高风险资产复核：第三方源码、供应商图纸/手册、标准摘录、外部模型/数据、用户/客户项目材料、历史日志和二进制资产。
6. 维护者负责维护登记表；没有足够证据时不得把“进行中”改成“通过”。
