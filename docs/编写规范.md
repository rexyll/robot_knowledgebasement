# 知识库编写规范

> 本规范执行仓库根目录 TaskPlan.md 的全局 Guide / Limit，特别是 G-03（统一文档结构）、G-21（零基础友好）、G-22（阶段门）和 G-23（工程成果物）。本规范只细化文档写法，不另设全局约束。

## 1. 文档类型与读者层次

根据内容选择一种或多种类型，并在摘要或元数据中明确：

- **入门教学**：解释概念、先修知识、术语、学习目标、例题、练习和能力检查。
- **技术参考**：记录原理、接口、参数、实现、限制、测试和上下游依赖。
- **工程流程**：说明责任角色、输入、步骤、异常分支、输出、记录和验收。
- **成果物模板**：提供可填写的需求、设计、BOM、测试、质量、生产或交付表单。
- **型号/厂商/标准卡片**：记录来源、版本、地区、适用范围、时效和核验状态。
- **项目案例/故障案例**：区分事实、推断、教学示例和待确认信息。

不要假设所有读者都具备机器人专业知识。专业文档可以面向有经验工程师，但必须给出概念入口、先修知识和相关基础页链接。

## 2. 技术笔记的基础结构

按主题适用程度选择以下结构，不为凑格式编造内容：

1. 标题、摘要、一句话定位、适用范围和不适用范围。
2. 本主题解决什么问题、为什么需要、常见使用场景。
3. 先修知识、关键术语、中英文缩写和学习目标（面向入门者时必填）。
4. 分类、原理、关键组成和工作流程。
5. 架构图、接口图、数据流、状态机或拓扑。
6. 关键参数、公式、单位、变量定义、假设和计算示例。
7. 选型方法、设计步骤、工程权衡和典型应用。
8. 接口与兼容性：机械、电气、通信、软件、数据和版本。
9. 测试方法、评价指标、边界条件、失败模式和排障。
10. 安全、法规、网络安全、隐私和环境约束（适用时）。
11. BOM、供应链、厂商、代表型号（适用时）。
12. 代码、仿真、工具、开源项目与许可证（适用时）。
13. 上游板块、下游板块、关联章节和下一步学习路径。
14. 来源、发布日期/访问日期、适用版本、更新记录和待确认项。

## 3. 零基础教学层（面向新手的关键知识页必填）

### 3.1 先修知识与学习目标

在正文前或专门小节明确：读者需要什么基础；没有基础时应该先读哪一页；学完以后能解释什么、计算什么、设计什么或完成什么；本页不覆盖什么；哪些内容需要专业人员参与。

### 3.2 概念讲解顺序

优先按“问题与用途 → 直观解释/类比 → 规范术语 → 工作原理 → 公式或代码 → 工程实践 → 局限与风险”的顺序讲解。首次出现专业缩写时给出中英文全称；公式中的变量必须解释含义、单位、假设和使用边界。

### 3.3 例题、练习和达标检查

适用时至少提供一个带完整过程的计算或配置示例、一个可在安全受控环境完成的练习、预期结果和检查方法、常见错误及定位方法，以及下一步应该阅读或实践的主题。

资源链接不能替代讲解；只引用视频/课程而没有解释和练习的文章，不视为完成零基础教学要求。

## 4. 工程流程与成果物写法

工程流程必须让读者清楚“谁在什么条件下做什么，留下什么证据”。适用时说明输入与前置条件、责任角色和审批角色；工具、设备、软件/固件版本和安全前提；分步操作、关键参数、异常分支、回退和恢复；输出文件/图纸/代码/数据/记录及其版本关系；评审问题、验收标准、准入/退出条件和遗留风险。

需求、设计、测试、制造、质量和交付类文档应优先使用 docs/templates/ 中的模板，并链接回对应 TaskPlan 节点。

## 5. 上游板块 / 下游板块

上游 = 本页依赖或消费的板块；下游 = 依赖或消费本页的板块。

每条格式：Wiki 页面链接 + 一句话说明依赖关系（类型：硬件/软件/算法/流程/行业/制造/验证）。硬件、软件、算法、制造、验证和应用页面要互相建立可追溯关系。没有明确下游时可以写“待建立”，不得为了凑数虚构链接。

## 6. 代码实例与开源项目

记录项目、语言、许可证、来源版本或 commit、用途、限制和链接。代码摘录和再分发严格遵守根 TaskPlan G-08 / Limit。许可不明确时只链接、不复制。原创示例须注明硬件、OS、编译器/SDK、依赖、构建方法、测试结果和安全限制。

## 7. 厂商、型号与标准资料

硬件和产品页记录制造商、正式型号、订货号/版本、数据手册/SDK、兼容性、支持周期和价格快照（若有）。标准/法规页记录发布机构、正式编号、版次、发布日期/生效日期、地区、适用产品、强制属性和官方来源。不要把“参考某标准”写成“符合标准”或“已认证”。

## 8. 来源与链接纪律

1. 外部来源登记到 链接台账：URL、标题、来源机构、引用页面、访问日期、核验状态和版本。
2. 没有实际访问的链接不得标为已验证；登录限制、反爬和网络失败要区分标注。
3. 价格、产品参数、软件版本、生命周期、法规和标准信息必须标注快照日期。
4. 内部知识互链使用 Obsidian WikiLink；跨目录 Markdown 链接按相对路径规范维护。
5. 自动链接校验、重复检测和元数据检查归 00-05 执行；自动化检查不能替代专业事实审查。

## 9. 内容成熟度与状态

建议在审计台账中为文章标记：

- **M0 占位**：只有标题、README 或计划描述。
- **M1 概览**：有基本定义和分类，但缺少实践/证据。
- **M2 可学习**：有先修说明、原理、术语、示例和练习。
- **M3 可工程参考**：有选型/设计步骤、接口、边界、测试和来源。
- **M4 可用于项目阶段评审**：成果物模板、验收证据、异常路径和专业审查记录齐全。
- **M5 经项目验证**：在明确的平台、版本和工况中完成复现或验证，并保留可追溯证据。

成熟度是内容质量标记，不等同于安全认证、产品放行或量产资格。

## 10. 历史内容修订与勘误

1. 保留历史内容和迁移轨迹；修订必须保留日期、原因和依据。
2. 发现错误时，不得为了保留历史而继续传播错误结论；应明确标注勘误、更正结论、来源和影响范围，并记录变更。
3. 需要拆分或迁移时，先更新迁移映射和内部链接，再调整文件路径。
4. 新增任务节点使用对应章节未使用的新 ID；不得引用不存在的旧节点编号。
